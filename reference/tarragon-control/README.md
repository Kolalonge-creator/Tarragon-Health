# Tarragon Control

Cardiometabolic detection-and-control platform for Nigeria. Built to `docs/tarragon-build-spec-v3.md` (Phase 1) and `docs/tarragon-build-spec-v3-phase2.md` (Phase 2).

**Read the spec before touching this code.** Section 3 (Invariants) overrides everything else. Do not infer product decisions from prose — if it's not in the spec, stop and ask.

## Real gaps found while building M1 (not guessed around — flagged for a founder decision)

1. **§6.1's clinician "caseload" access has no backing column anywhere in §5.** Only `enrolments.assigned_coordinator_id` exists (coordinator-specific); there is no clinician equivalent. Implemented only the fully-specified half — the shared needs_review+ exception queue — for both clinician and coordinator. A dedicated caseload-assignment model (e.g. an `enrolments.clinician_id` column) needs a decision before M5/M8 build clinician-specific worklists beyond the shared queue.
2. **§5.7's `escalations.breached` column, as literally specified (`generated always as (resolved_at is null and now() > due_by) stored`), is invalid Postgres** — `now()` is not immutable, so a stored generated column can't use it (error 42P17, confirmed against the real database). Replaced with `escalations_with_breach_status`, a `security_invoker` view computing the same thing at read time.
3. **A real RLS bug, caught by the exit test against a live fixture, not by review:** the first draft of `readings_select_staff` granted `ops_admin` blanket read access to reading values, directly contradicting §6.1's explicit "no readings values" for that role. Fixed in `0005_ops_admin_readings_exclusion_fix.sql`.
4. **A real bug found while building M2's activation guard, not requested by the spec but necessary for the guard to mean anything:** `clinicians_update_self` (0002_rls.sql) row-scopes to "your own clinician row" but placed no restriction on *which columns* — a clinician could self-edit `active`/`mdcn_expiry`/`indemnity_*` and simply reactivate themselves after a suspension. Fixed with a trigger (`0008_clinician_self_update_column_guard.sql`) restricting clinician self-edits to `scope` only; superadmin and system-level writes (the nightly guard) are unrestricted.
5. **Spec says "a nightly Edge Function" for the clinician activation guard (§5.2); this uses `pg_cron` + a plain `plpgsql` function instead** (`private.suspend_expired_clinicians()`, scheduled nightly). Same behaviour, directly testable without Docker. Swap the cron target for a real Edge Function later if the job ever needs to call an external API (e.g. a live MDCN registry lookup) — the suspension logic itself doesn't need to move.
6. **Phase 2's L3 guard was built now, not deferred** — it's tightly coupled to what M2 introduces (real `clinical_notes` signing) and Phase 2 §1 explicitly says these guards are built alongside Phase 1, not after. `app_config.accountability_model` seeds at `tech_layer` with `set_by = NULL`; a `BEFORE INSERT` trigger on `clinical_notes` blocks signing until a superadmin deliberately sets `set_by`. L1/L2/L4 were **not** built yet — they belong with the milestones that actually need them (triage/M5, enrolment, referrals/M8).
7. **§5.10's `screening_participants` has no column for name or phone**, even though §8 explicitly requires capturing both — and neither `patients` nor `profiles` can hold them either for a walk-up participant with no `auth.users` row yet. Added `full_name`/`phone_e164` directly to `screening_participants` (`0010`).
8. **§5.10's `screening_participants.patient_id` is commented "null until they convert," but `readings.patient_id` is `NOT NULL`** — a screening-day measurement has to attach to *something*. Read `patient_id` as filled immediately at capture (a `patients` row created the same way an under-18 dependant's is, `profile_id = NULL`), with `converted_to_enrolment_id`/`converted_at` as the real, separate, later commercial-conversion signal the attach-rate metric actually cares about. Documented in `0011`'s header, not silently assumed.
9. **`consent_scope` has no value for "consent to be measured at a screening event"** — its five values are all downstream data-sharing scopes. Used `clinical_share` (closest fit) with `capture_method = 'field_tablet'`, which already existed in the spec's own enum specifically for this scenario — treated as strong evidence for the intended path, not a guess pulled from nowhere.
10. **A real access bug caught only by the M3 exit test, not by review:** `0002_rls.sql` revoked `ALL` (including `USAGE`) on the `private` schema from `authenticated`, which blocks resolving *any* `private.*` name at all — not just calling one without `EXECUTE`. Every function in that schema was already individually `EXECUTE`-gated with its own internal role check, so this wasn't a security hole, just a hard block; fixed by granting `USAGE` back (`0016`).
11. **`private.suspend_expired_clinicians()`'s "previously undiagnosed" isn't a term defined anywhere in Phase 1** — there's no "diagnosis" concept outside the clinical/triage pipeline. Read as: no `enrolments` row started before the screening event's `held_on` date, i.e. not already an active Tarragon patient walking in. Flagged as an interpretation, not an authoritative definition.
12. **§5.4's "a `devices` row of the matching `device_kind`" implies a pathway→device_kind mapping that doesn't exist anywhere** — `programme_code` is just `control`/`concierge`, not per-condition (hypertension vs. diabetes), so there's no way to know which device_kind a given enrolment "requires." Read as: any active enrolment needs **at least one** `devices` row, of any kind. Revisit if programmes ever gain a condition dimension.
13. **§21.4 names the validated-device list source as an open decision** ("which published list `packages/protocol/devices.ts` checks against") — not guessed at. `validated_devices` is a real, writable reference table, seeded empty; every unlisted device is correctly `unvalidated_advisory` by design until ops populates the real list.
14. **M4's enrolment-activation gate is a real, retroactive tightening relative to M3's own test fixture** — `supabase/tests/m3_exit_test.sql` activated an enrolment for a patient with zero devices, which ran and passed before this gate existed. That test file is not edited (shipped tests stay as committed); a from-scratch replay of the full migration+test history in strict order would need that one patient given a device first. Flagged in `0018`'s migration header.

## Relationship to the existing Tarragon Health platform

This is a **separate repository and a separate Supabase project** from the existing `apps/web`-based platform (90+ shipped features, no live users yet). This repo is a deliberately leaner rebuild — see Phase 1 §19 and Phase 2 §5 for what is explicitly out of scope. The two are being run side by side for comparison, not merged.
