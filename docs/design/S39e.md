# S39e: shared work queues under the care tie

Found while checking the 41 staff screens listed in `docs/design/S39b.md` section 6 (no staff login was used: code and live data read, then a database role simulation). Seven screens are pooled queues across the organisation: lab results inbox, abnormal screening results, lifestyle red flags, lifestyle reviews, annual check reviews, therapy approvals, vaccination verification. Under S39b a clinician sees only queue items for patients on their own care team, so a pooled item nobody is tied to would be invisible; the admin caseload page shows a false zero for async consults. All queues are empty today (4 real patients, 2 clinicians), so nothing is broken yet.

## Decision (founder, 2026-10-07)
The queue shows the name and the item; opening the item is logged. Admin sees counts only.

## Design
- `public.clinical_worklist()`: any active clinician, own organisation, the open items of the seven queues (100 per queue, oldest first) with patient name and number, kind, label and date. No result, note or answer. Coordinators, admins, patients and anon are refused.
- `public.org_open_work_counts()`: admin or active clinician, organisation totals per queue and for async consults.
- Web: `/clinician/worklists` (in the console search) lists the queues with a link to each patient's chart, which writes the S39c log; the admin caseload page reads the async consult count through the counts function. The existing queue pages are unchanged: they still show the tied detail.

## Limits
The existing queue pages still list only tied items; the worklist is the safety net that shows all of them. Therapy approvals could not be built as a proof fixture (a psychology provider is required) and is named in the proof output. The per-queue cap is 100. Writes on the tied tables are still organisation-wide (OQ-279).
