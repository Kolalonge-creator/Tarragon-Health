## 2. Backup codes

- Ten codes (`backup_code_count`, PROPOSED, founder said ten), `XXXXX-XXXXX`, drawn in the database from 32 symbols (no 0 O 1 I), returned once to a signed-in patient, stored only as an HMAC-SHA256 under a Vault secret (`account_backup_code_pepper`), so a table dump cannot be ground offline. Regenerating deletes the old set at once. Three sets a day.
- Redeem is `public.redeem_backup_code(kind, identifier, code)`, **service role only**. Only a VERIFIED email or phone identifies an account. Every failure (unknown identifier, wrong code, used code, non-patient, locked) returns the same `{ok:false}`; ten wrong tries on one account in an hour lock redeeming for that account whatever IP they come from. The hash is computed before the account is looked up so timing does not separate known from unknown.
- The code does not log anyone in. It lets the person SET A NEW PASSWORD: the server (`recoverWithBackupCode`) validates the new password first (so a weak one never spends a code), redeems, sets the password with the admin API, releases the code if that failed, then `complete_backup_code_recovery` deletes every other session and tells the owner. The person then signs in with the new password. This works for a phone-only account, which a magic-link approach would not.
- Every step is audited (no code in the event) and the owner is told in-app and by email: new codes made, a code used.
- Surfaces: web `/forgot-password` "Backup code" tab; phone sign-in recovery "Backup code" tab (calls the public route); generation card on `/patient/profile`.

## 3. Care Circle recovery contact (the safest flow)

1. The patient names ONE confirmed Care Circle member (`propose_recovery_contact`). The member must say yes in their own signed-in session (`respond_recovery_contact`). Either side can end it. A member who leaves the circle or whose access lapses stops counting (`private.circle_member_is_live`, checked at propose, respond, confirm and claim).
2. Locked out, the patient names their verified email or phone on the recovery page (`request_contact_recovery`, service role, answers the same whether or not anything exists). The contact is told in-app and by email, the patient on the channels they can still read. Two requests a week at most.
3. The contact confirms in their OWN signed-in session (`confirm_contact_recovery`) with a tick that they spoke to the person themselves. That starts a wait (`contact_delay_hours`, 24, PROPOSED), enforced by data (`release_at` cannot be set within an hour of confirmation) and by the claim function. The patient is told when the wait ends and can cancel from any signed-in device (`cancel_contact_recovery`).
4. After the wait, the patient asks for the link (`claim_contact_recovery`, single use). The server then sends Auth's one-time recovery email to the address ON FILE (read from Auth, never the request), or, if there is no verified email, a verification code to the verified phone through the normal hook. **Never to the contact.** If sending fails the request is reopened. The contact never receives a link or a code.
5. A released request also lifts the 72 hour text-code pause for two hours (the contact plus a delay is the second confirmation).

Limit, stated plainly (OQ-S03B-03): the link goes to a channel the patient already verified, so the route cannot help someone who lost every verified channel.

## 4. Eligibility first (spec 1.8, closes OQ-41)

- `private.handle_new_user()` keeps everything it did except the roster claim.
- `private.claim_programmes_for_verified_user()` runs (a) from an `auth.users` AFTER UPDATE OF `email_confirmed_at`, `phone_confirmed_at` trigger on the first verification, and (b) at the end of `handle_new_user` for an account created already verified. It joins the pending cohort code (through `private.join_cohort_core`, which `public.join_cohort` now calls, same rules) and claims a roster slot matching a VERIFIED phone or email. An account an admin placed in an organisation through `app_metadata` is left where it was put.
- The sign-up forms (email and phone) carry an optional programme code. `check_cohort_code_for_signup` (service role only, rate limited per IP) answers one thing: valid now. The code is held in `raw_user_meta_data.cohort_code`. That metadata is user-editable; it grants nothing a signed-in person could not get by calling `join_cohort`, because the code is re-checked by the same rules at claim time and the claim runs once, on the verification transition.
- A pending code that no longer works (expired, full, closed) never blocks verification; the person is told in-app. A claim that errors is audited as `signup.programme_claim_failed`, never silent, and never blocks sign-up.
- Sign-up edits are two small calls in `signup/actions.ts` and one component per form (`CohortCodeField`), kept apart from the adult-only date-of-birth check S04b adds.

## 5. Change number and the pause (closes OQ-43)

- Web card, three steps: confirm it is you (a 6-digit code to the confirmed current number, or to the verified email), the new number, the code sent to the new number. The first step is skipped when the account has nothing confirmed to confirm with.
- **The gate is in the database**: a BEFORE UPDATE trigger on `auth.users` (`private.enforce_phone_change_authorisation`) refuses to start a number change unless a fresh (15 minutes), single-use row exists in `phone_change_authorisations`. Only the server, after Auth accepted the code, writes that row (`authorise_phone_change`, service role). So a stolen access token cannot call Auth directly to skip the step. Resends of the same number and the clearing of the pending number are not gated. It covers every active role, staff included.
- A second trigger tells the owner (in-app and email, not SMS) when the number actually moves, whoever moved it. The old number is not texted (INV-08).
- **The pause**: after the number moved, recovery by a text code is paused for 72 hours (`number_change_hold_hours`, PROPOSED). `my_phone_recovery_hold()` is asked right after a recovery code is accepted (web `verifyPhoneReset`, phone `enforcePhoneRecoveryHold`); if held, or if the answer cannot be read, the session is ended and the person is told when, in Lagos time, and which other ways work. Fails closed.
