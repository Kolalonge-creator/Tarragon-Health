# S12 Design: triage wiring (events, patient tasks, on-device red, emergency guidance)

Spec 4.6, 5, 6.1, 6.2 (recheck flow), 7.9 step 5, 8.3, safety cases 1 and 5. Depends on S11 and S07 (both closed). Invariants touched: INV-01 (the same pure engine on phone and server, no model), INV-05 (a red result is an urgent `triage.graded` event carrying `page_on_call`), INV-06 (red is graded on the phone from bundled rules with no network), INV-07 (the patient task and every notification key stay neutral), INV-13 (`is_test` carried), INV-14 (nothing new acts on a draft rule set), INV-16 (every triage event records the rule set id and version).

## What already exists
- `packages/clinical` engine and the draft `triage_rule_sets` row (S11). `public.get_approved_triage_rule_set()`.
- Event bus (S10): `observation.recorded` and `triage.graded` are seeded types; no producer, no subscriber.
- `vitals_readings.triage_event_id` (S05, no foreign key yet), `observations` view, `symptoms`, `care_tasks` with `kind` and the `patient_tasks` view (S07), `private.patient_home_bp_target()`.
- The live pipeline: `private.classify_bp_level`, `vitals_readings_bp_red_flag`, `emergency_events`, `clinician_alerts`. It pages and escalates today. **It is not touched** (OQ-67 decision: live bands stay until the CMO signs the new rule set).
- Mobile: `bp-log.ts` `TriageEvaluator` seam, the bundled `EmergencyGuidanceModal`, the offline outbox and mirror, `today-model` (empty task title falls back to a kind line).

## Decision: shadow until signed (OQ-88)
The rule set is a draft. Until a row is `approved`, the server grades with the draft, records `triage_events.rule_set_status = 'draft'`, and emits `triage.graded` with `shadow: true`. Subscribers added later (S16 tasks, S19 paging) must ignore shadow events, so nothing new pages or opens a clinical task off an unsigned rule set; the live pipeline keeps doing that. On the phone the engine can only add to what the existing check shows: the severity shown is the stricter of the existing on-device check and the engine, never weaker (INV-06 is a floor, not a replacement). The repeat-reading prompt is shown from the draft because it only asks the patient to rest and measure again.

## Data model (migration `s12_triage_events_and_wiring`)
- `triage_events` (spec 4.6): `id`, `organisation_id`, `patient_id`, `trigger_type` (`observation`, `symptom_report`, `silence`, `adherence`, `result`), `trigger_id` (the reading id), `grade`, `rule_id`, `rule_set_id` (FK `triage_rule_sets`), `rule_set_code`, `rule_set_version`, `rule_set_status`, `explanation_key`, `actions jsonb`, `matched_rule_ids`, `task_key`, `shadow`, `is_test`, `created_at`. Unique on (`trigger_type`, `trigger_id`, `rule_set_id`) so a redelivered event cannot grade twice. Append only. `vitals_readings.triage_event_id` gets its foreign key (`on delete set null`).
- `triage_pending_rechecks` (`observation_id`, `patient_id`, `due_at`, `state` pending, resolved, timed_out): the first elevated reading waiting for its repeat. A one minute pg_cron sweep emits a `observation.recorded` event with `recheck = timed_out` for every due row (spec 6.2: no repeat in 15 minutes grades the first reading as if repeated).
- Patient repeat prompt = a `care_tasks` row (`kind log_bp`, `source triage_recheck`, empty title so the app shows its own translated line, `owner_role patient`), closed when the repeat is graded or the window passes. `patient_tasks` exposes `source`.
- RLS: a patient reads their own `triage_events`; admins read; nobody signed in writes; clinicians get no direct read (INV-12: they reach a patient through a task or page, S16 to S19). `triage_pending_rechecks` has no API access at all.

## Events and flow
1. Insert on `vitals_readings` (blood pressure) emits `observation.recorded` (idempotency key per reading). A red-flag symptom inserted within 10 minutes after a reading re-emits it for that reading (key includes the symptom) so a late symptom still regrades.
2. Subscriber `triage.grade_observation` (edge function, handler key registered in `process-events`): loads the context through service-role `public.triage_context_for_observation` (reading, symptoms near it, 14 day history, target, age, pregnancy, pathway state, open task keys, recheck state), runs `grade` with the approved rule set else the draft, then calls `public.record_triage_result`.
3. `record_triage_result` (one transaction): rejected writes nothing; `recheck_required` stores the pending recheck and creates the repeat task; `graded` inserts the `triage_events` row, links the reading, resolves any pending recheck and its task, and emits `triage.graded` (urgent for red) with the ids and actions only.
4. Task and page actions travel inside `triage.graded` (`actions`). S16 and S19 subscribe; S12 registers no subscriber for them.

## Phone
`evaluateOnDevice` is replaced by an engine evaluator: bundled (or cached approved) rule set, history from the phone's own readings (unsent ones included), the cached home target, a stored pending repeat. Output adds grade, rule id, explanation key, emergency code (EMG-001 or EMG-001L) and a placeholder audio id (the clip id as text until S32). The patient sees EMG guidance at once on red, a "rest then measure again" card with the time left on a first elevated reading, and the TRI message otherwise. A repeat left open past 15 minutes is graded on the next open as `timed_out`.

## Safety rules
No model call anywhere. The edge handler and the phone run the same source file. A failed server grade never blocks saving a reading and never hides guidance already shown. Events carry ids and the grade, never a reading value.
