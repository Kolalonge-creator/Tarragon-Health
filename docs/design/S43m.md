# S43m design note: the Health Passport on the phone

Closes the gap recorded in `docs/BUILD-PROGRESS.md` for S43 and S44 ("mobile screens for capture, trends, history, share not built") and for S09x. Spec: `docs/BUILD-SPEC-v5.md` Module 2 (2.1 to 2.9, 2.14). Research: `docs/research/S43m.md`. Invariants in play: INV-02/11 (nothing unconfirmed is the record), INV-03/04 (released, non-sensitive results only), INV-07 (no clinical content in notifications), INV-14 (guards). Part D: D.1 (honest offline), D.2 (screen reader, 44 pt, dynamic type), shared phones.

## 2. Screens, data sources and states

State vocabulary used by every read screen (`passport-parts.tsx`): **loading** (spinner with a label), **ready**, **stale** (a saved copy shown under a one-line notice that says why, offline or refresh failed, and when it was saved), **failed** (nothing saved to fall back on: says offline or failed, with Try again; never an empty list, because a failed read is not "none"), **empty**, **own only** (the screen is not offered while acting for someone else where the data is keyed on the signed-in person), **writes need a connection** (said in words, buttons disabled while showing a stale copy).

### PR 2: results over time
`patient_biomarker_list` and `patient_biomarker_trend` (released, non-sensitive, the lab's own range). A chip row of tests, one SVG line per unit (never joined or converted), the lab's range band only when every point shares one, the care team's target as words only (a target has no unit, so it is never drawn against a result: OQ-S43m-4), a table under the chart so the chart is never the only way to read a result, a one-sentence summary for the screen reader. No "optimal" range, no meaning, no colour judgement. Offline: last copy.

### PR 3: sharing and the emergency card
Share my record: sections, expiry (from the config mirror), PIN, open once, recipient label and view cap; the link and PIN are shown once, apart, with a native share sheet and a copy button; list of active links with revoke. Emergency card chooser: the ten fields, "use the minimum", "show everything", lock-screen opt-in kept as the web does. Both need a connection to change; the card itself keeps its offline copy and now refreshes it after a save.

### PR 4: documents and data exchange
Add document: type, then camera, photo library or a PDF (system pickers only, nothing scans the roll), then **turn and trim** (rotate left or right, four edge steppers with a shaded preview and a spoken value, so no gesture library is needed), then save: shrunk to at most 1600 px, JPEG, location data stripped, uploaded to the private `patient-documents` bucket under the person's own folder, one `patient_documents` row, one id per attempt. Document list (metadata only) and a per-document view with the per-field confirm UI. While the go-live guard `document_capture_enabled` is off the screen says "reading is not switched on yet, your photo is saved" and no reading is asked for; when it is on, the new bearer route `POST /api/mobile/document-reading` runs the same code as the web action. Records from other places: per-system consent grant and withdraw, records received, who made a copy; the FHIR download opens the website (OQ-S43m-11).

## 3. Safety rules kept
OCR output is only ever a suggestion; a rejected reading leaves no values; nothing outside the capture module reads `patient_documents.extracted` (a phone scan test, `lib/document-capture/readers-scan.test.ts`, allows only the capture module and its screens; the web scan is unchanged). Share links default to the configured expiry and never include mental health or reproductive data unless the person adds it (there is no such section). A detail hidden from the emergency card is "not shared", never "none". Nothing clinical goes in a notification, a share sheet message names no record contents, and the lists are not exposed to the OS (no widget, no screenshot-friendly summary).

## 4. Accessibility and low-end phones
Every control has a role and a label (`a11y-scan.test.ts` covers touchables); targets are the kit's 44 to 48 pt; text uses `AppText` so dynamic type applies up to the app's cap; state never relies on colour alone (notices carry an icon and words); heading order is screen title, then section titles. Lists are bounded (100 rows at most) and drawn as plain views; no images except the user's own cropped document photo (resized to at most 1600 px on the long edge, JPEG 0.7); no audio; the cache is one small table.

## 5. Not built here, on purpose
Lock-screen widget and wallet passes (native). A second-device pairing flow. Editing a procedure (remove and add again, as on web). Audio "What is this?" on the new screens (D.2 gap recorded since S43). Any device or simulator verification beyond what is stated in `docs/BUILD-PROGRESS.md`.
