# S16 Design: clinical_tasks, state machine, task types and priority classes

Spec 7.3 and 7.4. Depends on S10 (event bus, done) and S15 (credentialing, merged as #921). Invariants touched: INV-05 (a red event never waits for a pull), INV-07 (no clinical content in a task's notification), INV-10 and INV-12 (a clinician reads only tasks tied to them), INV-13 (`is_test`), INV-16 (every task records the task-type version and the triage rule-set version it used). Founder decisions applied: F-03 and OQ-01 (one table, employed doctors are pushed tasks, freelancers pull), F-05 (one doctor tier plus the CMO: eligibility uses `doctor_tier`, not `credentialing_level`), 2026-10-06 (fee fields stay empty until S30; an adapter view over the older task tables; email, not SMS, is the paging fallback, see OQ-S16-3). Research: `docs/research/S16.md`.

## What already exists (extended, not rebuilt)
- Push model today: `private.auto_assign_escalation()` picks a named doctor for each escalation, skipping people on leave (`private.clinician_on_leave`, `clinician_deprioritised_now`). It stays untouched. S16 reuses the two availability functions for the push path.
- Task-like tables, all left as they are: `clinician_alerts`, `escalations`, `alert_follow_up_tasks`, `care_outreach_tasks`, `chronic_programme_coordinator_tasks`, `care_tasks` (patient and coordinator tasks). They are read through one adapter view (below), not merged.
- S15 gives `private.clinician_is_eligible(profile_id)` (S17 calls it), `clinical_staff.doctor_tier`, `employment_type`, `max_concurrent_claims`, `clinician_competencies`.
- S10 gives `private.emit_domain_event`, `event_subscribers` and the handler registry in `supabase/functions/process-events/handlers.ts`.
- S12 gives `triage_events` (`shadow`, `actions`, `rule_set_version`, `task_key`) and the `triage.graded` event.
- Live task keys the engine emits today (`urgent_bp_review`, `bp_review`, `low_bp_review`, `referral_review`, `adherence_review`, `silence_check`) do not match the spec's nine task types. They are mapped in data, see below, and OQ-S16-1 records the two without a spec type.

## Data model (one migration, `*_s16_clinical_tasks.sql`)
- `task_types` (data, not code): `code`, `priority_class` (1 to 9), `default_due_minutes`, `min_doctor_tier`, `required_competencies`, `lead_window_minutes`, `claim_timeout_minutes`, `pushable`, `source_task_keys text[]` (triage keys it answers), `version`, `is_active`. One active version per code. Mirrored in the code registry as `queue.task_types`; a Jest test fails if the two drift.
- `clinical_tasks`: the spec columns, plus `organisation_id`, `task_type_version`, `triage_event_id`, `rule_set_version`, `dedup_key`, `merged_count`, `delivery_path` (`push` or `pull`), `pushed_to` (profile), `priority_overridden_by/_reason`, `is_test`, `created_at`. `fee_kobo_at_completion bigint` and `fee_schedule_version_id` exist and stay null until S30 (INV-15: bigint). A partial unique index on `dedup_key` for live tasks means a repeat trigger merges into the open task and bumps `merged_count` (recorded, never dropped).
- `clinical_task_transition_rules` (the only legal moves) and `clinical_task_transitions` (append only log with actor, reason, from, to). `state` changes only through `private.apply_task_transition()`; a guard trigger refuses every other change, including by the table owner.
- `task_claims` (claim log: claimed_at, expires_at, ended_at, end_reason `completed|handed_back|expired|cancelled`) and `task_handbacks` (reason code, note) are created now so S17 only adds the RPCs. S16 writes the `handback_count` and `claim_expires_at` fields through the transition function only.
- `queue_config` (versioned, one active): `class3_promotion_window_minutes` (240), `overdue_grace_minutes`, `sweep_every`. Mirrored as `queue.rules`.
- Adapter view `legacy_clinical_work_v` (security_invoker): one row per open `clinician_alerts` and `escalations` with `source_table`, `source_id`, `patient_id`, `assigned_to`, `status`, `created_at`. Read-only, for the queue screens in S35 and for reconciliation. It is deliberately not named `clinical_tasks`.

## State machine (spec 7.4, enforced in the database)
created -> offered_to_lead (offered to a named clinician: the patient's lead, or an employed doctor the task was pushed to; ends at `lead_window_ends_at`) or open. open -> claimed (S17). claimed -> completed, claimed -> open (hand-back or timeout), open -> escalated, and any non-terminal state -> cancelled (clinical lead only, reason of at least 10 characters, audited). completed and cancelled are terminal. escalated -> claimed is allowed, so the on-call clinician can still take it. Actor kinds: `system`, `clinician`, `lead`. Red events never use `offered_to_lead` (INV-05): a task of class 1 is created `open` and `escalated` is the next legal step.

## Behaviour
- `public.create_tasks_from_triage_event(triage_event_id)` (service role): does nothing for `shadow = true` (also checked in the handler, two layers, OQ-88), maps each `create_task` action through `task_types.source_task_keys`, takes the due time from the action's `dueMinutes` (the rule-set version is the source, INV-16) and falls back to the type default, then creates the task via `private.create_clinical_task()`. A `page_on_call` action creates no task here; S19 owns paging and `red_event_unacknowledged`.
- `private.create_clinical_task()` routes: if `pushable` and the patient's care-team clinician is an active employed doctor, eligible and not on leave, the task is pushed to them (`delivery_path = push`); otherwise it goes to the pool. Lead windows (S18 sets the lead) are respected by `private.initial_state_for()`.
- `private.promote_due_soon_tasks()` (cron, every 5 minutes): an open `amber_bp_review` within the configured window of its due time moves to class 3, logged as a priority change, once.
- `private.escalate_overdue_tasks()` (cron): open tasks past due move to `escalated` and emit `clinical_task.escalated` for S19. S16 does not page.
- Events: `clinical_task.created`, `clinical_task.state_changed`, `clinical_task.escalated` (ids and neutral facts only, INV-07). A subscriber `queue.create_from_triage` on `triage.graded`.
- Priority override: `override_task_priority(task, class, reason)` by the clinical lead, audited. The deterministic class is kept in `priority_class_original`.

## Safety rules
1. Shadow triage events never create tasks (OQ-88) and the CMO's signature is what turns that on.
2. A task row holds ids and neutral facts only. No reading, condition or result is ever copied into a task, a notification or an event payload (INV-07). Clinicians read the clinical facts through the audited chart functions.
3. RLS: patients have no access. A clinician sees only tasks pushed to them or claimed by them, plus pool tasks through `public.next_task_preview` in S17. The clinical lead and admin read all. Staff cannot write directly: every change is a definer function. `anon` and `PUBLIC` have no execute on anything.
4. `private.can_staff_read_patient_identity` is extended so a clinician holding an active task for a patient may open that patient's identity through the audited read (INV-12). Nothing else widens.
5. Level 1 limits: `min_doctor_tier` is stored here and enforced by S17's eligibility check. Doctor tier is the only gate (founder decision); `credentialing_level` is not used.
6. A cancelled or escalated task is never silent: both write the transition log and an event, and a failed sweep opens an ops incident rather than skipping.
7. Test patients' tasks carry `is_test` and are excluded from every metric (INV-13).

## Screens
None in S16. The console queue screens are S35 and S36. A minimal read of queue health is `queue_health()` (admin), counting open, escalated and oldest-open age.
