# Provider layer completion (design note)

Follows `docs/design/S11-S15-p4-providers.md` (what was built) and `docs/research/build-provider-layer.md` (vendor audit, competitor study). Goal: finish everything about the provider layer that does not need a live vendor account, and turn everything that does into one command for the founder. Nothing here is applied, deployed, merged or switched on by the author; no live vendor was called; no signed configuration value changed; the AI scribe stays OFF (AI-017) and INV-11 holds.

## 1. Fixes found by the audit
| Where | Problem | Fix |
|---|---|---|
| `zoom-webhook/handler.ts` | A validly signed request of any age was accepted (no replay window); signature compared with `===` | Constant-time compare; a signed request more than 5 minutes off is acknowledged with 200 and ignored (a 401 would make Zoom count the endpoint as failing) |
| `video-zoom.ts` | `start_time` sent with milliseconds | Stripped to the documented `...ssZ` form |
| `_shared/notifications/resend.ts` | Svix timestamp accepted `1e3` or padded text | Whole seconds only |
| All three webhook functions | Body read whole before anything else | `readCappedBody`: 1 MiB cap by declared length and by counted stream, answers 413 before any signature work |
| `payouts/handler.ts` | After a timeout or 5xx on `POST /transfer` the payout was recorded "error" without asking whether Paystack had accepted it (money possibly moving while our state said "approved") | Look the reference up first; found means record what Paystack says, not found means a safe retry with the same reference |
| `release_payout_batch` (SQL) | Only required a different person from the maker, so two admins could pass a batch between them; OQ-338 says the CMO is the second approver | Exactly one of maker and checker must be the CMO (migration `p4y`) |
| `payouts_enabled` guard vs `payout_batch_maker_checker` flag | The flag was a configuration control: any admin could turn it off and send without a batch | The guard cannot be switched on while the flag is off, and while the guard is on the flag cannot be turned off (migration `p4y`; both still OFF) |
| Zoom host user | A Server-to-Server token cannot resolve `me` | Not changed at runtime (production may already be configured); the sandbox check FAILS with the explanation and the closeout lists it first |

## 2. Fixture contract tests (`packages/integrations/src/provider-fixtures.test.ts`, 31 tests)
Payloads under `packages/integrations/src/fixtures/{zoom,paystack,resend}` are written from the vendors' published shapes (never captured from a live account). For each vendor: a good event of every type we act on, a forged signature, a missing header, a tampered body, a replay outside the window (both directions, and the exact edge), the same event twice (same answer, same key), events out of order (each parses alone; reversal after success keeps its own key), malformed JSON, an unknown event type, an event with no identifiers (keyed by body hash), and an oversize body. `provider-branches.test.ts` finishes every remaining branch. `check-adapter-coverage.mjs` runs after Jest and fails the package test unless the eleven vendor-facing modules (`payment-paystack, video-zoom, email-resend, http, webhook-inbox, webhook-forward, webhook-body, webhook-challenge, crypto, result, from-env`) have 100 percent of branches, lines, functions and statements. (Jest cannot gate files outside the package by path, hence the small script.) The mocks and the partner calendar keep the looser global bar (95 percent branches).

## 3. Sandbox check (`scripts/provider-sandbox-check.mjs`, runbook `docs/runbooks/provider-sandbox-check.md`)
Runs the real adapters against each vendor's sandbox or test mode from environment variables and prints PASS / FAIL / SKIP per capability. Refuses a live Paystack key in any variable; masks every secret in all output (whole value and tail); Resend only to `@resend.dev`; Termii read only; Zoom (which has no sandbox) only with `--allow-zoom-meeting`, creates one five minute meeting under the test host and deletes it. Webhook signatures are cross-checked against independent `node:crypto` implementations of each vendor's documented algorithm, so a mistake in the adapter's WebCrypto code cannot hide behind the same mistake in its own test. Tested against the repo's fake vendors, with sabotage cases (a vendor that pays twice for one reference, one that mints a new id for a repeated idempotency key, a wrong key, no host user).

## 4. Audio fallback measurement (`scripts/audio-fallback-measure/`)
`probe.html` is one offline page a tester opens on a handset: handset and condition, 30 timed requests (a rough loss stand-in), a join-time stopwatch, a loss ladder (0 to 30 percent, tester marks clear / choppy / cannot understand / dropped), and a bad-link-to-audio-only stopwatch; downloads one JSON per run. `report.mjs` turns a folder of runs into a table and a CANDIDATE `video.audio_fallback` value, but only with enough evidence (5 runs per stressed condition, 2 handset models); otherwise it says what is missing. The candidate changes only `poorAudioLossPercent` (half the lowest loss that broke speech, to a multiple of 5, at least 5) and flags a ladder that is more than twice as slow on a handset as the configured values imply. A test reads the registry so the "current" values it compares to cannot drift. It never edits a configured value.

## 5. Speech gold-set gate (`scripts/asr-eval/`, spec `SCORING.md`)
`gate.mjs` applies the Q19 pass mark (95 percent, decision OQ-343) to drug names and numbers each on its own, needing 20 clips and 30 occurrences of each; `FAIL` stands however small the set; accent gaps, invented entities and dropped negations are reported and never netted off. `scaffold.mjs` makes a 24-slot gold-set folder across 12 scenarios, 5 accent tags and 3 conditions. Scripted clips only, no real patient audio. `run.mjs` exit codes: 0 pass, 3 fail, 4 not enough data. `--pass-mark none` restores measure-only.

## 6. Payout controls re-audit
Re-read end to end: S31 state machine, `approve_payout` (four eyes, payee cannot approve, ledger re-read), `payout_prepare_send` (guard, state, test accounts, batch and limits at send), `payout_record_send`, `apply_payout_transfer_event` (idempotent, out-of-order safe, GL on success and exact opposite on reversal, flag), limits (per payout, per clinician rolling 7 days under an advisory lock, per batch total and count, at proposal, release and send), reconciliation (read only, never posts), TypeScript `sendPayout` (reference as idempotency key, conflict then verify). Gaps found and fixed are in section 1. Accepted: the rolling 7 day window reads `payouts.updated_at`, so a later touch of an old payout can keep it in the window (conservative, never loose); no UI to propose or release batches (RPC only, from P4); GL posting stays OFF pending the accountant (OQ-340); `payouts_enabled` stays OFF. Proof: `packages/db/tests/p4y_payout_controls_reaudit.sql`, with the S31x proof updated so its second approver is the CMO (59 checks still pass).

## 7. Provider health on the chain-health page (migration `p4z`)
`public.provider_layer_health()` (admin or CMO, read only): webhook inbox open/oldest/dead per provider, events waiting longer than a retry can take (nothing is draining the inbox: the state `provider-event-drain` not being scheduled produces), rejected deliveries in the last day (shown, never judged), breakers open, reconciliation breaks older than the configured limit, payout ledger postings needing finance. It adds no setting: every limit is read from the existing `providers.layer` configuration (`backoffMaxSeconds + leaseSeconds`, `unsettledAfterHours`). Rendered as a card on `/admin/ops/chain-health` and `/clinician/chain-health`. No cron was added. A reply that cannot be read shows as unreadable, never healthy.
