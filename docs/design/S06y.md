# S06y design note: encrypted queues (PR 1 of 2)

Follows `docs/design/S06x.md` (offline trust). Two separate PRs: (1) move the plaintext upload queues into the SQLCipher store, (2) show how old the offline copy is. JS only: no native module, no config plugin, no `runtimeVersion` change.

## 1. Data

### PR 1: queues in the encrypted store

`apps/mobile/src/lib/offline-queue.ts` kept three lists as JSON in AsyncStorage (clear): health-store sync pages, BLE device readings, photo-confirmed readings. They now live in the shared store opened by `secure-db.ts` (`getStoreWithSchema`), in `offline_queue_v1` (one row per entry: queue, owner account, id, enqueued_at, payload). The public API of `offline-queue.ts` is unchanged, so no caller changes.

Rules:

- **Per account.** Every read, write and remove is scoped to the signed-in account. Signed out shows nothing and a new entry is refused (`enqueue*` returns false, as before when storage failed). Signing out does not delete. Entries from before this change have no account: the first signed-in account that touches the queue claims them (that account is who would have uploaded them before).
- **Copy, verify, then delete.** On first open of each queue, the old AsyncStorage list is copied in chunked single statements (no transaction: the outbox shares the connection and must not be rolled back with a queue copy), read back and compared with the source (count and an order-sensitive checksum, the same `rowsChecksum` as S06x). A mismatch deletes the copied rows. Only a verified copy writes the marker (`offline_queue_migration`, the commit point) and only then is the old key removed. A crash mid-copy leaves rows without a marker; the next start clears them and copies again from the untouched old list. If the delete alone fails the marker stays `verified`: next start only retries the delete, never copies again.
- **Escape hatch.** On any failure the old list stays where it is, readers keep merging its entries into the list and removals reach it, new entries go to the store, and the existing `migration_held` notice is shown (a code, no health value). The next start retries a fresh copy. A queued reading is never stranded or dropped.
- **Damaged lists are kept, not dropped.** An element that is not a valid entry, or a file that is not a list, is copied as an opaque row (`readable = 0`): never listed, never uploaded, never counted, but encrypted and wiped with the store instead of left in clear.
- **Lost key.** Handled by S06x: a new generation starts empty, `key_lost` notice with a code. The old rows are unreadable by design. Nothing here resurrects or hides them.
- **Cap.** Same as before: 500 per queue per account, drop oldest, recorded in sync diagnostics. Migration itself is not capped.
- **Remote wipe.** The store file holds the rows, so `destroyStore` removes them. `wipeThisPhone` already clears every AsyncStorage key except notices, meter and lease records, which also removes an old list still waiting to move. Queued entries now count as unsent in the per-account wipe count (counts only, never marked urgent).

### Recorded risks

- **Shared phone, old entries.** Pre-change entries carry no account. They are stamped with the account signed in when the move first runs (or claimed later by the first account to touch the queue). If account A queued readings, signed out, and B opens the app first after the update, B's token uploads them into B's record: the same attribution the old queue had, now written down. Not solvable without per-entry history that was never stored.
- **Offline with an expired token.** The auth client answers "no session" with a fetch error; the queue then uses the last account seen with a live session (an id kept in `@tarragon/offline-queue-owner/v1`, no health data). A real sign-out has no error and shows nothing. The outbox and drafts still depend on a live session (S06x risk d).
- **Key loss now also costs queued device readings.** The old AsyncStorage queue survived a keystore reset or a restored backup; the encrypted one does not (S06x decision D1, same as the outbox). The patient sees the existing `key_lost` notice with a support code and is asked to log again. This is the price of encryption at rest and is not mitigated here.
- **A failed local save is an error, not a quiet success.** `health-sync` now returns an error status when a page could neither upload nor be saved; the server-held cursor has not moved, so the next sync reads those samples again.
- **Plain fallback.** If S06x could not encrypt (no keystore or SQLCipher in the build) the queues sit in the same plain file the outbox uses and the patient has been told "not encrypted". "Encrypted" is true only in the encrypted mode.
- **Ordering and cap.** Oldest is by insertion order, not clock. Migration is not capped (the old queue was capped at 500).

## 2. Screens

None. The queues have no UI of their own. Existing wording (pending counts, `migration_held`) is reused.

## 3. Safety rules

- Never fall back to AsyncStorage when the store cannot open: enqueue fails and says so.
- No health value is logged, noticed or sent in any error path (codes and counts only).
- No AI in this path. No go-live guard touched.

## 4. NOT verified on a device

SQLCipher, the keychain flags, the two-phase delete and the real size of a 500-entry queue have never run on hardware. Jest uses the S06x SQLite stand-in (real SQLite engine, modelled key behaviour). A real device must check: migration of a phone that already holds a queued BLE reading, airplane-mode enqueue then reconnect flush, and a remote wipe.

Part 2 (how old the offline copy is) is a separate PR with its own note, `docs/design/S06y-freshness.md`.
