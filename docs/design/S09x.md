## Security findings fixed on the way (existing behaviour)

1. `record_shares_org_staff_select` let any org staff read every share row, including `token`: staff could open any patient's shared record. Dropped.
2. `authenticated` had INSERT/UPDATE/DELETE on `record_shares`, bypassing the RPC's caps. Revoked; the RPCs are the door.
3. New `pin_hash` is excluded from every client read by column grants (table-level revoke first; a column revoke is a no-op under a table grant).

## (a) Hub and access log

- `/patient/my-health`: cards for Timeline, Emergency card, Passport, Share records, Lock-screen card, and the list "Who has looked". Nav entry under "Your health". Mobile: `myHealth` section with the same.
- `public.my_access_log(p_limit, p_before)`: SECURITY DEFINER, scoped to `auth.uid()`, newest first, keyset paging. Output per row: `at, kind, actor_label, actor_name, categories, status, ends_at`. Never a reason, value or clinical name. `reproductive_health` appears nowhere (break-glass never opens it; no row names it).
- While acting for someone else the page says the list is for the signed-in account only, rather than showing the supporter's list under the dependant's name.
- No new console page needs a search entry beyond the CMO sign page and its read-only admin twin (added to `admin-search.ts`).

## (b) Safer sharing

- `create_record_share(sections, hours default null, use_pin, one_session)`: default expiry from config (12 hours, was 24 in the UI), 30-day cap kept. PIN is random, 6 digits, bcrypt with its own salt, returned once, shown apart from the link with a "send it a different way" warning.
- `record_share_by_token(token, pin, client_key)`: `null` for unknown, short, revoked, expired, locked and closed-session links alike. `{status:'pin_required'}` only for a valid PIN-protected link (a 256-bit token has to be known first). 5 wrong PINs lock the share; 3 from one client (SHA-256 of the address) in 15 minutes returns `try_later`. Row lock serialises guesses. Every attempt is a `record_share_lookups` row with an outcome; the patient sees them in the log.
- One-session: the link stops working 30 minutes after its first open.
- App: `/share/[token]` shows the PIN form (server action, PIN in the body, never the URL), then the record. Wrong-format PINs never reach the database.

## (c) Lock-screen presence

Built: patient setting (`patient_lock_screen_pass`, off by default, mirrored on the phone), `my_lock_screen_facts()` (database minimiser), `buildLockScreenPayload` (second whitelist, validated shapes), the patient's printable card, mobile toggle and preview, governed field list `my_health_config.lock_screen_pass` (C8, **unsigned**), a dormant generator with pure Apple/Google layouts, go-live guard `wallet_pass`.

Not built, and why: Apple Wallet signing needs a Pass Type ID certificate; Google Wallet needs an issuer account. Neither exists, none was fabricated. The guard has no conditions branch, so it cannot be switched on. No lock-screen widget: it needs a native build that cannot be verified here.
