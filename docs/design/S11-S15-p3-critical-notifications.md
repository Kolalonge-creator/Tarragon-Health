# S11-S15 P3 design: critical path for red alerts (plan R3 part, R4)

CMO answers Q10 to Q13 (2026-10-07), OQ-91, OQ-92, OQ-94. Research: `docs/research/S11-S15-p3-critical-notifications.md`. Invariants: INV-05, INV-07, INV-08, INV-12, INV-13, INV-16; nothing here is required for any patient-side function.

## Reconciled with what is live (2026-10-13, read only)
- The live red path is `emergency_events` (before-insert trigger `handle_emergency_event` pages clinicians on a Member, nobody on Free). The new S12/S19 path (`triage_events` red, `pages`) is built but has 0 events. Both stay.
- `private.escalate_unconfirmed_critical_notifications()` hops a critical row `push, email, sms` by default and by `escalation_slas` (tokens `whatsapp` map to `email`). A database trigger `notifications_suppress_sms_voice` already turns every sms or voice insert into `failed` (critical) or `suppressed`. So today SMS is dead for patients AND for clinician paging; the patient ladder ends in a failed hop and an admin "exhausted" alert, not in an in-app row.
- The sender lets any critical row through its SMS rule (`isClinicianPage = priority === "critical" || role clinician`). That is OQ-92.
- A receipt failure (`failed`, `token_dead`) only writes an event; the notification row stays `sent`, so the ladder waits a full hop before moving on. Receipts are first checked after 15 minutes, every 10 minutes.
- No patient-facing notification exists for a Member red; the patient sees the acknowledge-gated dialog (`emergency_events.acknowledged_at` is the patient acknowledgement). Free has `free_red_*` notices.

## Decisions
1. **Q10, patient ladder.** New `private.patient_critical_channels(recipient, channels)`: for a recipient whose role is `patient` (or has no profile) it drops `sms` and `voice`, de-duplicates, and makes `in_app` the last hop. Used by the escalation function (rewritten from the live definition) and by `enqueue_critical_notification` (first hop). Any other role keeps its configured ladder unchanged. Sender: `isClinicianPage` becomes "recipient role known and not patient"; priority no longer opens the door. One named exception is kept so an open question is not decided here: `emergency_contact_alert` (sms to a patient's contact, OQ at the emergency-contact line in OPEN-QUESTIONS). The DB trigger is left alone (clinician SMS stays dead until a sender ID exists; raised as an OQ).
2. **Q11, red unconfirmed timer.** `public.red_alert_watch` (one row per red source, unique on kind+id; states watching, confirmed, clinician_acknowledged, outreach_created, skipped_free). Opened by additive after-insert triggers on `emergency_events` and on red non-shadow `triage_events` (never edits `handle_emergency_event` or `create_red_page`); the opener never aborts the red insert (exception block writes `audit_log`). A Free patient (`private.patient_may_page_doctor` false) gets a `skipped_free` row only: the Free path keeps its own notices and no clinician is paged. A Member gets a fixed-wording critical notice on every channel they have (push, email to a confirmed address, in-app), like S19's page does.
   `private.sweep_unconfirmed_red_alerts()` (pg_cron every 5 minutes, offset minute 3) decides, per watch: patient confirmed (any watch notice opened, patient acknowledged the guidance, patient replied, or a push receipt says delivered when `deliveredCountsAsConfirmed` is true) or clinician acknowledged (page acknowledged, alert no longer open, task claimed) closes it; otherwise at `due_at` = opened + 30 minutes (config) it creates ONE class 1 task `red_patient_outreach` through `private.create_clinical_task` (dedup key per patient, so a second red merges) and alerts the on-call clinician (leadership when nobody is on call) with a fixed-wording critical notice. If every push ticket for the watch ended in a receipt error and no email was delivered, due time is pulled forward to failure time + `undeliveredMinutes` (5): a receipt that will never come does not hold the clock. Later confirmation cancels an unclaimed outreach task. The task type is `needs_confirmation`; **no task is created until the CMO confirms the type on the sign-off hub** (the watch and patient notice still run).
3. **Receipts.** `record_notification_delivery_event` (rewritten from live) marks a critical push notification `failed` when its last pending Expo ticket resolves with a receipt error and none was delivered, so the existing ladder hops to the next channel on its next run instead of waiting out a hop. `claim_expo_receipt_checks` (same signature, rewritten from live) hands out a critical notification's ticket from `criticalReceiptCheckMinutes` (2) instead of 15, and one extra cron schedule of the same job (`expo-push-receipts-critical`, minutes 3-59/5) makes that useful. `expo-push-receipts` itself is unchanged.
4. **Q12, wording.** Reds keep fixed generic text on every surface (templates `red_guidance_waiting`, `red_outreach_task`); a new Jest file renders the whole red path with real clinical values and asserts none appear (safety case 20 style). The push envelope for a red is fixed words even when discreet mode is off.
5. **Q13, response.** Append-only `public.red_care_responses` (`client_id` unique, response `sought_care` or `could_not_get_care`), written by `record_red_care_response` (own account only, idempotent, `shown_to_clinician` false for Free). It never touches `pages`, claimed tasks or acknowledgements. The phone does not know the server's event id (the reading may not have synced), so the function may be called with no event id and then links the answer to the patient's latest alert of the last day; with none yet it raises `P0002`, which the outbox treats as retry. `could_not_get_care` also brings the outreach forward when `couldNotGetCareOutreachNow` is true (PROPOSED; CMO to confirm, it adds work, it never removes any). The on-call page and the outreach task card read it through `public.latest_red_patient_response(page, task)` (no patient identity in the result). Web: two buttons on the emergency dialog when a doctor was alerted. A patient answer is matched to an alert by patient and time (an hour before the alert opened), not by event id, so a reading that raised both a legacy event and a triage event is covered once. Mobile: same two buttons on `EmergencyGuidanceModal`, queued in the existing SQLite outbox as kind `red_care` (durable, oldest first, idempotent by client id) and sent with the RPC.
6. **OQ-91.** The two PDF attachments are gone from the sender. The email carries a fixed sentence and a link `/d/<kind>/<id>?s=<hmac>` signed with `NOTIFICATIONS_LINK_SECRET` (HMAC-SHA256, 7 day expiry, no content); the web route `/d/[kind]/[id]` verifies the signature and expiry (a bad link is a 404), then sends a signed-in owner to the existing in-app PDF route and anyone else to sign in. After sign-in the person lands on their home screen, not on the document (login only honours role-home redirects); the in-app copy is unchanged. In-app PDF unchanged.
7. **OQ-94.** `public.check_notification_text(text)` (admin or service role) wraps `private.notification_text_violations` (the DB copy of the INV-07 list, already drift-tested). A `before insert or update` trigger on `notification_broadcasts` refuses a hit (message lists the matched terms); the composer also calls the RPC first so the reason shows before saving. The lifestyle messaging gateway calls it for the LLM free text and refuses a hit or an error (fail closed, it is not a safety message).
8. **Delivery reliability.** iOS: `interruptionLevel` is `time-sensitive` for safety rows; `critical` (and a critical sound) only when the secret `IOS_CRITICAL_ALERTS_ENABLED=true`; `app.config.js` adds the entitlement only when `IOS_CRITICAL_ALERTS_ENTITLEMENT=1` at build. Android: channel `urgent` (importance MAX) created before the permission prompt, `channelId`, `priority: high`, 24 hour `ttl`; full-screen intent not used. S13b card gains "send me a test alert" (`public.send_my_test_alert` queues a fixed-wording in-app plus push test that travels at critical priority so it tests the real path, at most 6 a day, never laddered). Handset matrix runbook for QA.

## Config (PROPOSED, `notifications.rules` v4, mirrored in migration seed and registry, drift test)
`redUnconfirmed: { enabled: true, unconfirmedMinutes: 30, undeliveredMinutes: 5, deliveredCountsAsConfirmed: true, couldNotGetCareOutreachNow: true, criticalReceiptCheckMinutes: 2 }`, all other keys copied from the live active row.

## CMO hub
A line `red_outreach` on `/clinician/clinical-signoff` (key in `cmo-signing-hub.ts`, panel `red-outreach-panel.tsx`, action `red-outreach-actions.ts`) while the task type awaits confirmation. It calls the existing `confirm_task_type`. No new page, so no new console search entry. Side effect to know: `approve_triage_rule_set` refuses while any task type awaits confirmation, so the CMO confirms this one before approving the BP triage draft.
