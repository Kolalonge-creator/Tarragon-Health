## 3. Behaviour
- **Donations (INV-09)**: a signed-in patient pledges (amount at least the minimum, optional named item); operations confirm receipt of a bank transfer with the bank reference and a reason; `donation.received` fires once. Nothing can spend a donation: no foreign key points at `donations`, no function takes a donation id except the four donation functions, the donor reads only their own rows with no pool or grant field, and a donor's quote is the ordinary price.
- **Grants**: operations (admin) approve against a published criterion with a written reason (audited; no second approver, decision S72-3). The Fund must hold the money: gifts restricted to the item first, then general gifts not needed by other items (`fund_general_needed`). Approval creates a 100 percent `access_grant` programme with the ceiling as budget and per-person cap; `sponsor_match` matches it only for the named person, only while approved and unexpired, only while the Fund's guard is open. A grant is therefore an order-bound sponsor entitlement through the S71 path: full cover has no payment step, part cover pays the rest, cancel releases, a refund returns the grant, expiry closes the programme. The **hardship seam stays 0 on purpose** (OQ-423): a reduction there could not be bound to one order, reserved or reversed.
- **Public report**: `access_fund_public_report` (service role only; the website calls it): non-test only, small groups withheld whole, folded into "other" if that reaches the minimum, totals withheld with them otherwise; a closed Fund shows no figures. Minimum cell is `private.fund_min_cell()`, reading S38b's platform value; swap for S75's `private.suppress_cell` when merged (OQ-422).
- **Payment requests**: `create_payment_request` (patient or a caregiver with `manage_payments`; only what a supporter may buy, the yearly Membership; limits); `payment_request_preview` (service role; generic item key, price, fee split, expiry; per-visitor rate limit); `create_request_order` (payer; item, person and price come from the request; refused for expired, cancelled, used, in use, own, other world, sponsor-covered); `orders_payment_request_guard` refuses any order not matching its request. Paying marks the request paid and the person gets the entitlement; an unpaid order that ends reopens the link. `order-checkout` accepts `payment_request` instead of an item code.
- **Entitlements**: `my_entitlements` returns source (paid, supporter, sponsor, access_fund), uses and days left; shared wording in `@tarragon/commerce` (`entitlements.ts`).
- **Orders**: `my_orders` gains `is_buyer` and `refund_state`.

## 4. Screens
Web: `/patient/membership` (entitlements card, Fund support card, Health Points choice, refund button only for the buyer, refund state in words), `/patient/payment-requests` (new), `/checkout/pr_...` (link page, no referrer), `/access-fund` (public report, criteria, pledge), `/admin/access-fund` (pledges, grants, expiry) with navigation and search entries. Mobile: payment requests (the phone's own share sheet), entitlements section, refund request and order list on Receipts, Health Points switch with the database's quote, Wellness no longer offers redemption. All strings in `packages/i18n`, English only, no em dashes.

## 5. Safety rules proved
A sponsor-paid item never shows a payment step (amount 0, no payment row, no Paystack reference). A donation cannot be a stored balance (see 3). A request cannot pay another item, person or its own requester; the code is never stored in clear; the preview carries no person; the link fails closed without the pepper. Test and real never mix (pool, report, links). The older guards still answer through the wrappers.
