# S98 design note: the preventive engine issues the test request

Founder requirement 2026-10-27: when a patient is due a specific test they are alerted, download the PDF request, take it to any lab, upload the result; the request must be issued automatically. Invariants in play: INV-03 (uploaded document hidden from patient until reviewed), INV-04 (sensitive tests), INV-07 (ids only in events and generic inbox text), INV-10/12 (tied staff reads), INV-14 (guards off).

## S98b: sensitive tests by opt-in (founder decision 2026-10-27)
A sensitive test (`screen_types.sensitive`, plus hiv/hep_b/hep_c/syphilis/chlamydia_gonorrhoea) gets an automatic request only when: `screening_request_automation_enabled` AND `screening_sensitive_request_optin_enabled` are on (test patients exempt, as everywhere), the patient has an `opted_in` row, the schedule came from a signed rule set, and the normal insert passes (`enforce_lab_order_origin`; a refusal is skipped and logged without the test name). Self-arranged orders carry no home-collection fields so `home_kit_sensitive_enabled` is untouched and still governs home collection only.
- Opt-in store: a one-row-per-patient table, not the consent matrix (the matrix needs new enum values and a wording pass in every locale). Own-row read, writes only via `set_my_sensitive_request_optin` (audited, adults only, opting in needs the guard open, withdrawing always allowed, never deletes a request). Registered in `data_registry` (PROPOSED `consent`).
- INV-07: `enqueue_lab_order_requested_notifications` calls a sensitive bundle "a lab test" in both payloads; `queue_screening_reminders` calls a sensitive screening "a screening test"; the audit entry for a sensitive issue omits the test. The email subject and body were already neutral; the PDF (owner download, or the signed-link/service-key route) is the only place a name appears.
- INV-04 results handling is untouched; no new surface shows a sensitive result. UI: switch on web Privacy and mobile Privacy, hidden while the guard is off.
- CMO and DPO review owed before the guard is switched on.

## Review fixes (2026-10-27, after a high-effort code review)
1. **Self-bookable bundles.** `enforce_lab_order_origin` refuses a `screening_schedule_id` on a self-bookable bundle, and live single_hiv, single_hep_b, single_hep_c, single_fit, single_ferritin, single_vitamin_b12 and the cervical smear bundles are all self-bookable (the manual "Get & print" button hits the same wall for them; not changed here). Fix: the job sets a transaction-local `tarragon.screening_request_job`; the trigger, patched from its live definition, lets such an order through its self-bookable branch ONLY when that setting is on and no user is signed in, and then falls through to the full due-screening checks (own schedule, pending or overdue and due, exactly the single-test bundle). Patients are refused as before (proved). Bundle choice now prefers `single_*` non-self-bookable codes; the proofs use real self-bookable fixtures (ferritin, vitamin B12, HIV, FIT).
2. **Failures are durable.** The per-row exception handler only counts; after the loop one audit row (`screening_request.auto_issue_failed`, SQLSTATEs and a count) and one open `ops_incidents` row (technical, sev3, reference `screening_request_automation`, no patient or test named) are written outside any handler, so a failure to record it fails the whole run visibly.
3. **No PDF link for a sensitive request email.** The email goes with a signed `/d/` bearer link built from `order_id` (the old attachment was already replaced by the link, OQ-91). For a sensitive bundle the payload now carries no `order_id`; `documentLinkFor` returns null and the email goes without a link, text already neutral. The patient downloads in the app. No Edge Function change, no redeploy.
4. **Replaced uploads.** `screening_result_uploaded` and the upload count ignore superseded documents (the table has no rejected or unusable state). Proved.
5. **Caregivers.** `my_screening_requests` omits sensitive screenings for anyone but the patient; both request-PDF routes (web and mobile) refuse, as not found, a non-owner viewer for a self-service request holding a sensitive test (`generateLabRequestPdf(..., viewerId)`). Staff and the service-key route are unchanged. Gap kept: `lab_orders` itself is still readable by a caregiver with `view_results` (existing policy), including the order row; narrowing that policy is a wider change.
6. Migrations renamed to clock timestamps 20261027192259 and 20261027192341 (both unapplied).
7. One sensitivity source: `screen_types.sensitive`. Live, hiv, hep_b, hep_c, syphilis and chlamydia_gonorrhoea are all flagged, so the literal list was dropped.

## Why a nightly sweep and not a `screening.due` subscriber
`enforce_lab_order_origin` refuses a self-service order before the schedule's due date, but the scheduler creates rows up to 30 days early and bus handlers are TS workers. A sweep keyed on the schedule rows is idempotent, needs no worker, and reuses the existing patient-initiated due-screening path (no new origin, no doctor, nothing billed).

## Human-owned
CMO signs a screening rule set; a founder or CMO switches `screening_scheduler_enabled` and then `screening_request_automation_enabled`; redeploy `send-pending-notifications` if the email wording should mention the request. No lab partner contract is needed (self-arranged).
