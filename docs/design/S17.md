Spec 7.6 (and 7.2 `conflicts`, 7.4 states, 7.8 reliability), safety cases 17, 18, 19. Depends on S16 (open as PR #925; this branch is stacked on `s16/clinical-tasks`, retarget to `main-dev` when #925 merges). Invariants touched: INV-05 (red never waits for a pull), INV-07 (no clinical content in events), INV-10 and INV-12 (claim is audited, and is what ties a clinician to a patient), INV-13 (`is_test`), INV-15 (bigint, nothing monetary here), INV-16 (claim records the task-type version). ## As built (2026-10-06): where the build differs from the plan below
The plan below is kept for its reasoning. The build changed these points, and where they disagree this section wins.
1. **Founder answers (all recommendations accepted):** minimal `availability_blocks` now (a declared block counts); conflicts written by the clinician (pending until the CMO confirms or lifts) and automatically on a conflict hand-back; the spec's five hand-back codes; an idempotent retry returns the existing claim; one lease extension and `queue_last_seen_at`, no heartbeat, an expired claimant may reclaim; employed doctors take pushed work with no block and may also pull when they declare one; strict class order with the overdue escalation as the backstop; test clinicians see only test tasks.
2. **Release on suspension is not an event handler.** `private.expire_task_claims()` (every minute) also releases the live claims of anyone no longer eligible (`end_reason = cancelled`, no reliability event). The loss of chart access is immediate anyway because `is_org_staff` fails once the role flips.
3. **No per-call rate limit.** Replaced by a cooling-off in the gate: 3 counted hand-backs in 10 minutes close the queue for the rest of the window. `conflict_of_interest` and `technical_problem` do not count toward that, but a **hard cap of 6 hand-backs of any reason in 60 minutes** closes it too (found in review: the exempt reasons otherwise allowed unlimited re-rolling).
4. **Which hand-backs bar the task.** Only `conflict_of_interest`, `outside_competence` and `other` exclude that clinician from that task again (`handback_excludes_task_for`). A `technical_problem` or `needs_information` hand-back does not (review: a dropped connection must not lock the only eligible clinician out).
5. **Self-declared conflicts** are capped at five pending and tell the CMO and admins on declaration (`private.credential_notify_reviewers`, neutral text).
6. **Claim sweep race fixed:** the sweep only ends a claim that is still live (`ended_at is null`), so a completion or hand-back in the same instant is neither overwritten nor counted as a failure.
7. **Added beyond the plan:** `queue_extend_claim`, `queue_complete`, `queue_summary` (counts by class, why the queue is closed), `declare_availability` and `cancel_availability`, `declare_conflict`, `record_conflict`, `lift_conflict`; per-class oldest-open in `queue_health()`; indexes on `task_handbacks`.
8. **Known limits:** a clinician with `max_concurrent_claims` above 1 is not protected from a duplicate claim on retry (the retry returns the existing claim only at the cap); the 50-session race test is written and registered but not yet run (no Docker here, first run is CI); the edge functions have no tests of their own; a few small bounds (a 5 minute start slack, 31 day horizon, 24 hour block, note lengths) are fixed in SQL rather than config.
9. **Live status:** the migration is NOT applied. It was run inside a rolled-back transaction against production with the proof (187 checks pass, the sabotage check bites) and nothing was left behind.

## 2. Gaps found while planning (these change the build)
1. **`availability_blocks` does not exist anywhere** (spec 7.2). Spec 7.6 rejects a clinician with no current `queue` block, so S17 cannot work without it, but S18 owns availability and the rota. See OQ-A.
2. **`conflicts` does not exist.** S15 only keeps a free-text `conflicts_declaration jsonb` on the application. S17 must create the table and decide who writes to it. See OQ-B.
3. **Hand-back reason codes disagree.** Spec 7.6: `conflict_of_interest, outside_competence, needs_information, technical_problem, other`. S16's check constraint: `..., need_more_information, unavailable, other`. The spec wins; S17 migrates the constraint (table is empty). See OQ-C.
4. **Reliability needs a formula and a store.** `reliability_score` is a bare numeric with no inputs recorded. S17 adds an event log it can be recomputed from.
5. **Retries over a dropped connection** are the normal case in Nigeria; spec 7.6 says "reject if already holds max claims", which would make a retried call fail. See OQ-D.

## 3. Behaviour

### `public.queue_next()` (RPC), fronted by edge function `POST /functions/v1/queue-next`
The edge function only verifies the JWT, rate-limits, and calls the RPC as the user (RLS and grants apply). All decisions live in one SQL function so there is one source of truth. In one transaction:
1. **Gate (reject with a stable error code, never a partial result):** `private.clinician_is_eligible(auth.uid())`; `clinical_staff.status = active`; a live `queue` availability block covering now; fewer than `max_concurrent_claims` live claims.
2. **Select** the next task, `FOR UPDATE SKIP LOCKED`, `limit 1`:
   - `state = open`, **or** `offered_to_lead` and `pushed_to`/lead is me (my offered tasks come first, then the pool). Offered tasks are never visible to anyone else (OQ-112 option a).
   - `min_tier <= my tier` (map from `doctor_tier`), `required_competencies <@ mine`.
   - no row in `clinician_conflicts` for (me, patient), and `patient_id <> me` (a clinician is never their own patient).
   - not in `task_handbacks` for me on this task (never re-offered after a hand-back).
   - `is_test` matches my own `is_test` (a test clinician never claims a real patient's task, and the reverse).
   - order: `priority_class, due_at, created_at`; escalated tasks are claimable only by a tier 2 holder of `on_call` (S16 rule).
3. **Claim** through `private.apply_task_transition(open|offered_to_lead|escalated -> claimed)`; insert `task_claims` with `expires_at = now() + task_types.claim_timeout_minutes` (30 min review, 60 min titration); write `audit_log` (INV-10); emit `clinical_task.claimed` (ids only).
4. **Return the minimum**: task id, type, class, due time, claim expiry, patient id, and the neutral task facts. No name, reading or condition. The console opens the chart through the existing audited read, which now admits the clinician because of the live claim (INV-12). Before a claim the clinician sees only `queue_summary()`: counts of eligible tasks by class and the (S30) fee for the next one. They cannot browse or choose.
5. **Idempotent retry** (OQ-D): if I already hold a live claim and call again, return that same claim with `already_claimed = true` instead of failing. A second task is never handed out above the cap.

### `public.queue_handback(task, reason_code, note)` / `POST /functions/v1/queue-handback`
Only the live claimant. Reason is required; `other` requires text of at least 10 characters. In one transaction: end the claim (`handed_back`), insert `task_handbacks`, transition `claimed -> open` (counts in `handback_count`), emit `clinical_task.handed_back`. Effects by reason:
- `conflict_of_interest`: also inserts a `clinician_conflicts` row (source `self_declared`, `pending_review`) so the patient is never offered to me again, and the CMO sees it.
- `outside_competence`: neutral for reliability; flagged for the clinical lead as a possible competency mismatch.
- `needs_information` and `technical_problem`: neutral for reliability.
- `other`: counts, small weight.
- More than 3 in 7 days (config) emits `clinician.handback_review_flagged` to the clinical lead once per window. It informs a person; it never suspends anyone.
- The task is re-offered only to others; if nobody else is eligible it escalates by the existing due-time sweep, never silently.

### Claim timeout: `private.expire_task_claims()` (cron every minute)
Per task, in its own subtransaction (S16's isolation pattern; a failure writes an ops incident and the loop continues): live claims past `expires_at` become `ended = expired`, task `claimed -> open` (not counted as a hand-back, S16 fix), event `clinical_task.claim_expired`, reliability event written. If the task is past due, it goes straight to `escalated`. A task is never closed or dropped by a timeout (research). The expired claimant loses chart access immediately because the access rule keys on a live claim. Expired claimants are not barred from re-claiming (a power cut is not misconduct); see OQ-E.

### Also in scope (small, needed for the cases to be provable)
- `public.queue_extend_claim(task)`: one extension of the lease by the type's timeout, maximum once (config), for a clinician mid-consultation. Optional; dropped if OQ-E answers no.
- `public.queue_complete(task, outcome)`: thin wrapper over `claimed -> completed` that ends the claim and writes the reliability event. Without it nothing can finish until S22 to S24. Earnings stay S30.
- Handler `queue.release_on_suspend` on `clinician.suspended`: releases that clinician's live claims to `open`. (Patient reassignment is S18/S19.)
- `public.queue_summary()`: counts by class for the caller's eligible work; and an admin `queue_health()` extension: oldest open per class (the starvation measure).

### Reliability (spec 7.8), `private.recompute_reliability(clinician)`
- Append-only `clinician_reliability_events` (kind: `completed_on_time`, `completed_late`, `claim_expired`, `handed_back`, `audit_result`; weight; task id; counts_against boolean). The score is derived from this log, never edited by hand, so it can be explained and replayed.
- Formula in versioned config `queue.reliability` (PROPOSED, CMO-owned): rolling 90 days, exponential decay, a prior of N neutral events so a new clinician starts at the default and small samples do not swing it, reasoned hand-backs (`conflict_of_interest`, `outside_competence`, `needs_information`, `technical_problem`) weigh zero, `other` and silent expiries weigh against, audit results from S20 plug in later. Range 0 to 100.
- Use: a tie-breaker for S18 lead assignment only. It never gates a claim, never affects an emergency, and (S30) never changes pay without a person reviewing.
- Honest limit: with no heartbeat there is no evidence a clinician was online when a lease expired. v1 therefore weighs an expiry lightly and records `last_seen_at` on each call so a pattern can be reviewed by a human. A heartbeat is OQ-E.

## 4. Data model (one migration, `*_s17_queue_next.sql`; timestamp generated at creation with `date`, never hand-typed; check `list_migrations` on live first)

Clinicians can add against themselves; only the CMO lifts. `is_test`.
- `availability_blocks` (minimal, spec 7.2): clinician_id, starts_at, ends_at, kind, state, `minimum_guarantee_eligible`, `is_test`; overlap exclusion for one clinician and kind; RPCs `declare_availability` and `cancel_availability` only (S18 adds the rota screens, confirmation and the guarantee). Interim, flagged in OQ-A.
- `task_handbacks` constraint changed to the spec codes. `task_claims` gains `extended_once`, `last_seen_at`, `client_request_id` (unique per clinician, for idempotency).
- `clinician_reliability_events` and the `queue.reliability` config row (mirrored in the code registry with a drift test).
- Config additions to `queue_config`: `max_extensions`, `handback_flag_window_days`/`threshold` (already in the registry), `rate_limit_per_minute`.
- Grants: revoke from `public, anon, authenticated` on every function, then grant execute only on the public RPCs to `authenticated`; explicit select-only grants on new tables (the S16 proof found default privileges granting writes). RLS: a clinician reads their own claims, handbacks and reliability events; the clinical lead and admin read all; nobody writes directly.

## 7. Safety rules
1. Eligibility is one SQL function; there is no TypeScript copy of the rules to drift. A pure TypeScript model exists only for tests, and a parity test runs the same table of cases through both (below).
2. The claim is atomic: `FOR UPDATE SKIP LOCKED` plus the guard trigger plus the partial unique index on live claims. Three layers, so a bug in one cannot double-assign.
3. Red work never depends on this queue (INV-05). `red_event_unacknowledged` is class 1 and escalated by S19's page; the queue only serves it as a last resort.
4. A task never disappears: every exit from `claimed` writes a transition row, a claim row and an event.
5. No clinical content in any return value, event or audit note.
6. Hand-back cannot be used to re-roll: the handed-back task is excluded for that clinician and the call is rate-limited.
7. A suspended or expired-credential clinician cannot claim (S15 eligibility) and loses live claims.

## 8. Tests (the proof)
- **`packages/queue` (pure, 100 percent statements, branches and functions):** eligibility (every filter, tier map, competency subset, conflict, own patient, handed-back, `is_test`, offered-to-other), ordering (class, due, age, ties), claim expiry by type, hand-back validation (each reason, `other` needs text), the 3-in-7 flag, reliability maths (decay, prior, neutral reasons, bounds).
- **DB proof `packages/db/tests/s17_queue_next.sql`**, registered in `ci.manifest`, with a sabotage that removes `skip locked` or the conflict clause and must flip a check: safety case 17 (conflicted clinician never offered, including after a `conflict_of_interest` hand-back), case 19 (abandoned claim returns after timeout, score updated, access removed), tier and competency, offer exclusivity, idempotent retry, concurrency cap, availability gate, suspended release, RLS for patient, clinician, other clinician, lead and admin, execute grants for anon and PUBLIC, `is_test`.
- **Safety case 18 and the 50-parallel claim test (real contention):** a Node test using 50 separate database connections against the local Supabase stack in CI (the `supabase-db` job), 50 clinicians each calling `queue_next()` at once against fewer tasks than callers, asserting zero task assigned twice, zero claimant over cap, and every task claimed by exactly one. A second run has 50 callers racing for one task: exactly one wins. S16 recorded that real two-connection contention was never exercised; this closes it. It runs as a CI step, not in the SQL manifest (single-session SQL cannot prove concurrency).
- **Parity test:** a shared table of eligibility cases run through the pure TypeScript model and the SQL function; any difference fails.
- **Edge function tests** (Deno): bad JWT, rate limit, error codes, retry returns the same claim.
- Drift tests for `queue.reliability` and the new config rows.

| Starvation | Queue priority | Queue priority | Priority numbers | n/a | Unpublished | Class then due time; overdue escalates; oldest-open metric |
| Conflict of interest | No | No | No | Manual | No | First-class table, auto-added on hand-back |

Where we are deliberately stricter than all of them: no browsing at all, a conflict table, and a timeout that can never close work. Where we are weaker and know it: no heartbeat, so a silent expiry cannot be told from a power cut (OQ-E); and Manchester-style targets are PROPOSED until the CMO signs them.

## 11. Open questions to answer before building (also to be written into `docs/OPEN-QUESTIONS.md` as OQ-115 onward)
- **OQ-A availability_blocks:** (a) S17 creates a minimal table with declare and cancel RPCs, S18 adds rota and confirmation (recommended; spec 7.6 cannot work otherwise); (b) pull the whole availability feature into S17; (c) skip the availability gate until S18 (unsafe: offers work outside a shift). Also: does a `declared` block count, or only `confirmed`? Recommend declared counts, confirmation matters only for the pilot minimum.
- **OQ-B conflicts:** who may write. Recommend clinician self-declares, CMO confirms or lifts, hand-back adds automatically. Should the S15 free-text declarations be converted by hand by the CMO (recommended) or left unparsed?
- **OQ-C hand-back codes:** use the spec's five (recommended; table is empty so no data cost).
- **OQ-D idempotent retry** returns the existing claim instead of rejecting (recommended; deviates from the literal wording of spec 7.6, same outcome, safe on bad connections).
- **OQ-E lease extension and heartbeat:** (a) one extension, plus `last_seen_at` on calls, no heartbeat (recommended for v1); (b) a heartbeat call every minute with reliability that excludes offline gaps (better evidence, more build, drains data on slow connections); (c) neither. And: may a clinician whose claim expired reclaim that task (recommended yes)?
- **OQ-F employed doctors:** do they also pull through Next task (when they declare a queue block) or only receive pushed tasks (F-03 says pushed)? Recommend both, so an on-duty employed doctor can help clear a backlog.
- **OQ-G starvation:** keep the spec's strict class order with the overdue escalation as backstop (recommended), or add an aging rule that lifts a task's effective class with wait time (needs CMO sign-off on the numbers).
- **OQ-H reliability numbers:** window, decay, prior and the weight of `other` and silent expiries are PROPOSED and need CMO sign-off before the score is used by S18.
- **OQ-I test isolation:** a test clinician sees only test tasks and the reverse (recommended).
