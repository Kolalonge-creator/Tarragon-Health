# S04 design note: consent, dependants, "Set up for my parent" (proxy)

Branch `s04-consent-dependants-proxy`, off `main-dev` at PR 816. Depends on S02 (`proxy_setups`, `patient_consent_state`) and S03 (phone OTP hook). Invariants in play: INV-07 (no clinical words in notifications), INV-08 (SMS is a verification code only), INV-10 (audited reads), INV-12 (need-to-see access).

## 1. What exists (reused, not rebuilt)
- Consent: `consent_versions`, append-only `patient_consents` with `action` (accepted/withdrawn) and a withdrawal trigger, `patient_consent_state` view (S02), `private.has_required_consents`, one-checkbox onboarding step, re-consent panel and banner. **Gaps:** no `consent_versions` rows for the 8 optional or new types; `has_required_consents` demands every current version, so seeding optional types would block onboarding; web and mobile "outstanding" logic ignores `action` (a withdrawn row counts as accepted); no history view or two-tap withdrawal; mobile is display-only; no privacy summary strings or audio.
- Dependants: `profile_access` (+ `permissions`, `expires_at`), `profile_access_categories` and `set_care_access_categories`, `care_access_requests`, `is_dependent_account`, `dependent_kind`, the 18-year transition cron, the add-child/add-elder UI. **Gaps:** hand-over to the young person captures no consent; add-elder gives the proxy `manage` at once.
- Proxy: `proxy_setups` table and state machine only. No functions, UI or expiry sweep.
- Phone verification: S03 sign-up actions, `auth-send-sms-hook` (code only), `@tarragon/auth` phone helpers.

## 2. Data model (new)
- `consent_versions.is_required boolean not null default false` (true for the three originals). `has_required_consents` checks required types only. Seeds: the optional types (`care_circle_sharing`, `research`, `sponsor_reporting`, `marketing`, `device_data`, `wearable_device_data`) with `text_key`s, never invented legal text (OQ-49).
- `proxy_setups` unchanged. New SECURITY DEFINER functions, all `authenticated`-only, none callable by anon:
  - `create_proxy_setup(name, phone, ttl_hours, max_per_day)`: validates, caps ttl at 72, enforces a per-creator daily cap, stores one pending row. Returns the setup id only.
  - `my_pending_proxy_setups()`: what the PARENT sees after signing in on their own phone (matched on their verified `auth.users.phone` to `target_phone_e164`): creator first name and expiry. Nothing else.
  - `confirm_proxy_setup(id, categories[])`: parent only; creates the proxy's `profile_access` row **in the same transaction**, limited to the categories the parent chose; state to `confirmed`.
  - `decline_proxy_setup(id)`, `expire_proxy_setups()` (daily cron; also checked lazily).
- TTL (72 h) and the daily cap live in `packages/shared/src/proposed-config` (`proxy.setup`), passed in by the server action, capped again in SQL.

## 3. Safety rules
- **Safety case 23 is structural, not a UI rule:** before confirmation no `profile_access` row and no parent profile data exists for the proxy, so RLS has nothing to allow. The proxy can only read their own `proxy_setups` row (name and phone they typed, state).
- No enumeration: creating a setup answers identically whether or not the number already has an account. The parent confirms only as the holder of the number (code on their own phone), never through `find_profile_by_phone` or `request_care_access` (phone-matching oracles).
- The only SMS is the auth hook's verification code (INV-08). The proxy is never told the code.
- Withdrawal is append-only (`action = 'withdrawn'`), two taps, and immediately reflected in outstanding-consent logic.
- Existing behaviour that conflicts (add-elder grants `manage` at once; dependent claim sends an SMS notification) is recorded in OQ-47 and OQ-48, not silently changed.

## 4. Screens
Web: `/patient/family/set-up-for-parent` (name, phone, sent state, pending list); parent-side confirmation card on first sign-in (what your child will see, category choices, confirm or decline); consent panel with purpose toggles, history and two-tap withdraw; privacy summary. Mobile: consent capture and withdraw, parent confirmation. Strings in `@tarragon/i18n` (en, pcm); no audio files are in the repo (ONB-010 is S32 territory, OQ-19 needs native review).

## 5. Build order and scope of this PR
1. Proxy database layer + proof (safety case 23, RLS, sabotage). 2. Proxy web flow + tests. 3. Consent: `is_required`, withdrawal-aware logic (the live bug), optional seeds, history + withdraw. 4. Privacy summary strings. **Deferred, written down:** quiet hours and `discreet_mode` wiring, age-18 hand-over consent, self-serve deletion and export (OQ-50), mobile proxy flow.
