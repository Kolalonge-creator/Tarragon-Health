# S25 Design: catalogue, prices, orders, Paystack checkout and webhooks

Spec 4.8, 10 (Paystack rows), safety case 24, Module 19 and 20 rows in scope. Depends on S14 (adapters, done), S10 (event bus), S18 (`order.paid` subscriber). Invariants touched: INV-07, INV-09, INV-10, INV-13, INV-14, INV-15, INV-16. Research: `docs/research/S25.md`.

## 1. What exists (extend, do not rebuild)
- **Live commerce is per-domain** (OQ-23, live wins for commerce): `service_products` + `service_purchases`, `payment_transactions` (event log with a unique `(provider, provider_event_id)`), ten checkout kinds in `paystack-webhook/handler.ts`, GL posting triggers on `payment_transactions`. None of it is touched. The 2026-10-05 Membership pivot already marked per-item doctor-time SKUs dead.
- **No v5 table exists live** (checked 2026-10-06): `catalog_items`, `prices`, `orders`, `payments`, `entitlements` are free names. `refunds` is S26.
- `patient_memberships` + `private.patient_is_member()` (S22b, OQ-150): S25 is the "purchase" writer the table was built for.
- S14 `PaymentProvider` (initialise, verify, `parseWebhook`, `paymentMatchesOrder` with the fee pass-through rule from OQ-97). S10 `emit_domain_event` with `order.paid` registered (required key `order_id`). S18 `lead.assign_on_order_paid` acts on `care_pack = true`. `platform_modules` is the dormant-module gate (OQ-18). `private.log_audit`, `ops_incidents`.

## 2. Decisions taken in this build
1. **v5 orders sit beside the live purchase tables, not on top of them.** New tables, new webhook branch `metadata.kind = "order"`, handled before the legacy `payment_transactions` path. So no legacy trigger (service-purchase activation, GL posting, voucher) can see a v5 order. GL posting of v5 orders is recorded as OQ-170 (finance decides the accounts; nothing posts until then, which is visible, not silent: the finance reconcile can read `payments`).
2. **Kinds**: the spec's `consultation`, `care_pack`, `lab_panel` plus `membership` (founder pivot 2026-10-05). `entitlement kind` follows the item: `consultation_credit`, `care_pack`, `lab_panel`, `membership`.
3. **Entitlement table starts here**, minimal (one row per paid order, unique on `order_id`, which is what makes safety case 24 hold). Lifecycle (use decrement, expiry, 7-day reminder CON-010, refunds) is S26. A paid membership also writes `patient_memberships` with source `purchase`.
4. **Self purchase only for now.** `create_order` refuses a beneficiary other than the buyer (`order_beneficiary_not_allowed`). The columns exist; Care Circle "pay for a loved one" opens in S29 with its permission checks. Recorded as OQ-171.
5. **Sales are gated, dormant by default** (INV-14, OQ-127 option a): `platform_modules.v5_checkout` is off, items are seeded `active = false`, and a capacity kind (care pack, membership) also needs a free lead slot (`lead_capacity_status`). S37 adds the `on_call_cover_ok` guard on top.
6. **Prices are versioned and immutable** (INV-16): a new price closes the old one, an order snapshots `price_id`, `amount_kobo` and `components`. Money is `bigint` kobo (INV-15). The membership price (10,000,000 kobo) is the founder-confirmed 2026-10-05 value. The 12,000 naira care pack (spec line 696) is seeded inactive and marked PROPOSED in its note until the founder confirms it next to the Membership (OQ-172).
7. **The processing fee** follows OQ-97: the order stores the PRICE; `fee_kobo` and `total_kobo` are recorded from the verified payment; the fee never enters price or any earnings base. The checkout shows price, fee and total before pay: the fee is read from Paystack (`fees` on the initialised/verified transaction), never a fixed percentage.

## 3. Data model (one migration, real timestamp, `list_migrations` checked live)
- `catalog_items(code, kind, name_key, description_key, included_keys[], duration_days, uses, requires_capacity, active)`; RLS: authenticated read of active items; writes only through admin RPC (audited).
- `prices(catalog_item_id, amount_kobo, components, valid_from, valid_to)`: exclusion constraint (no overlap), components must sum to the amount, amount never updated.
- `orders(buyer_profile_id, beneficiary_patient_id, catalog_item_id, price_id, amount_kobo, components, fee_kobo, total_kobo, state, paystack_reference unique, client_key, expires_at, paid_at, is_test)`; state machine trigger `created -> paid | failed | cancelled`, `paid -> refunded`, `failed | cancelled -> paid` only when a verified payment arrives late (money received is never ignored).
- `payments(order_id, provider, provider_reference, amount_kobo, fee_kobo, total_kobo, status, source, event_key, raw, verified_at)`; `raw` is a minimised record (ids, channel, amounts, gateway message), never the card or customer block. Unique success per reference.
- `entitlements(patient_id, order_id unique, kind, starts_at, ends_at, remaining_uses, state)`.
- All tables: `organisation_id`, `is_test` (INV-13), RLS on, grants only to `authenticated` where a policy exists; buyer or beneficiary reads their own orders and payments, admin reads org, nobody writes directly.

## 4. Functions
- `create_order(code, client_key, beneficiary)`: authenticated, idempotent per `(buyer, client_key)`, checks module, item active, current price, capacity, not already a Member, max 5 open unpaid orders; returns order id, reference, price. Reference format `tho_<32 hex>`.
- `record_order_payment(...)` (service role only): the single point where an order becomes paid. Locks the order row, compares reference, NGN, and the PRICE (not the total) with the order, then `private.apply_paid_order`: state to `paid`, one entitlement (`on conflict (order_id) do nothing`), membership row, `order.paid` event keyed `order:<id>` (so a replay emits nothing new). Any mismatch writes a `mismatch` payment row, an `ops_incidents` row (sev2, financial) and returns `mismatch`; it never marks paid. A replay returns `replay`.
- `cancel_order`, `my_orders`, `order_for_checkout` (reference lookup for the return page, owner only), admin `set_catalog_item_active`, `set_item_price` (admin, audited, reason).
- `orders_needing_reconcile(limit)` (service role) for the sweeper; `private.expire_stale_orders()` cancels unpaid orders after 24 hours only after the sweeper has had a verified "not paid" answer.

## 5. Payment flow (three paths, one writer)
1. App calls edge function `order-checkout` with the user JWT: `create_order`, then the adapter `initializeTransaction` (metadata: `kind: "order"`, `order_id` only, no clinical term), returns `authorization_url` plus the fee line.
2. `paystack-webhook`: signature check (existing), then for `kind = order` and `charge.success`: adapter `verifyTransaction`, `paymentMatchesOrder`, `record_order_payment`. A failure to process returns 500 so Paystack retries (hourly, 72 hours), and nothing is written to the legacy dedupe table, so a retry is a real retry.
3. `order-verify` (return page) and `order-reconcile` (cron, every 5 minutes) run the same verify-then-record. A browser return is never proof by itself; USSD and bank transfer that settle late are caught by the sweeper.
The core is one pure module `commerce` (`processVerifiedPayment`, fee display, state helpers) used by all three, tested over fixtures.

## 6. Screens
- Web patient `/patient/membership`: what is included (plain language, `description_key` + `included_keys`), price, fee line, "Pay with Paystack", no auto-renew statement, receipt link back. Return page `/patient/membership/paid` polls `order-verify`.
- Mobile: a Membership screen with the same content, opens Paystack in the in-app browser, returns by deep link and verifies.
- Staff: `/admin/catalogue` (list, price history, switch an item on or off, set a price with a reason).
- All strings in `packages/i18n` (en, pcm), no em dashes, "your care team".

## 7. Safety rules
1. A replayed or concurrent webhook makes exactly one entitlement, one membership and one `order.paid` (safety case 24); proved in SQL (two calls) and in Jest (fixture replayed 3 times, concurrent).
2. Never mark paid on a browser return, an unsigned body, a wrong amount, a wrong reference or a non-NGN currency.
3. No stored balance (INV-09): every payment is one order for one item; no wallet table, no top-up path.
4. Notification and Paystack metadata carry opaque ids only (INV-07).
5. A late payment on a cancelled order is honoured (money received) and flagged.
6. No auto-renewal: an entitlement has an end date and nothing in S25 charges again.

## 8. Not built here (and why)
Refunds and the care pack lifecycle (S26); Care Circle payer (S29); GL posting for v5 orders (OQ-170); points discounts, instalments, HMO eligibility (later releases); retiring the legacy GBP/USD and plan code paths (OQ-97 decision says "if unreachable"; they are reachable from live code, so left and logged in OQ-173).
