# S62 design note: the pathway engine (Module 13, engine half)

Branch `s61-s62/pathway-engine`. Migration `20261007190627_s61_s62_pathway_engine.sql` (NOT applied). Nothing here is signed: every rule set, step table, task type and config value is a DRAFT or PROPOSED, and the CMO signs.

## What already existed (reused, not rebuilt)
`chronic_condition_programmes` and `chronic_programme_enrolments` are the pathway and enrolment tables (OQ-124). `triage_rule_sets` + `record_triage_result` + `create_red_page` are the one INV-05 path. `protocols` + `proposeTitration` + `care_plan_changes` are the step table and the signed-change machinery. `go_live_guards` (S37) gates features. `diabetes_complication_checks`, `lead_assignments`/`replace_lead_internal`, `outcome_snapshots` and the clinical task queue are reused as they are.

## Data model
- `pathway_definitions` (10 rows, mirrored from `packages/clinical/src/pathways/registry.ts` by a test): code, kind, the programme codes it enrols through, rule set code, step table code, guard key. No second enrolment table.
- One `go_live_guards` row per pathway (`pathway_<code>`), seeded OFF, switched by the CMO. Conditions: signed protocol (and approved step table), signed rule set, clinical safety case (CMO attestation), clinicians' competency attested. Done by wrapping `private.go_live_conditions` and `public.attest_go_live_condition` (renamed `_base`, unchanged bodies), so no live body is re-typed.
- Trigger `chronic_programme_enrolments_pathway_guard` checks the guard on every enrolment or re-enrolment, so every enrolment RPC is covered at once. Test patients pass (S37 test rule). Live: 0 enrolments exist; hypertension, diabetes and obesity programmes are active, so real patients are now refused until a guard is switched on.
- `pathway_baselines` (snapshot of latest BP, glucose, weight, medicines and default goals at enrolment, one per cycle) and `pathway_milestones` (enrolment, cycle, code, due, met), both `source`/`recorded_by`/`is_test`, written only by definer functions. Patient reads own rows; staff read only through `read_pathway_milestones_audited` (INV-10), no staff row policy.
- `pathway_lifecycle_events` (append-only) with `pause`, `resume`, `transfer`, `discharge`, `re_enrol` functions. Pause stops scheduled check-ins only; grading and paging of a reading continue. Transfer reuses `replace_lead_internal`.
- `pathway_config` carries the PROPOSED cadence (weekly automated, monthly while uncontrolled, quarterly when controlled; milestone days; complication-check intervals).
- OQ-172 closed: AFTER INSERT trigger on `care_plan_changes` creates a `titration_signoff` task for every engine proposal, with no exception handler (a proposal with no task must fail, not vanish).
- `outcome_snapshots.pathway_code` check now names all ten codes. The snapshot columns are still BP-shaped, so a non-BP snapshot writer is a follow-up.

## Engine (packages/clinical/src/pathways)
Generic, pure: `gradePathway(facts, ruleSet)`; rule sets are JSON built from the PROPOSED config; a red rule must carry `page_on_call` (validator refuses otherwise). Result shape matches the BP engine's for `record_triage_result`. Composition (`composeCardiometabolic`) takes the most urgent component; a property test proves extra components never lower urgency. Device/server parity: the same module runs on both, and tests prove the JSON round trip, the mobile classifier and the legacy web classifier agree with the rule set.

## Safety
INV-01 no model; INV-02 the DRAFT step table can propose only for test patients and only a clinician signs; INV-05 a draft rule set grades as shadow (pages nobody), an approved one pages, proven in the DB proof; INV-14 guards; INV-16 results name the rule set version. Weekly automated review = the engine grading each reading; `sweep_pathway_reviews` and `sweep_pathway_scheduled_tests` (service role, NOT scheduled here) add the monthly/quarterly clinician review task and eye/foot/kidney due dates.
