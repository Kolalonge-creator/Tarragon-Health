Branch `feat/s58-redemption-milestones`, on `origin/main-dev` at 2ca9bbfa5. One migration: `20261022104102_s58b_pending_credit_milestones_refund_restore.sql`. Not applied anywhere.

## What the brief assumed, and what is actually on main-dev
The brief asked to wire `apply_points_discount` / `release_points_discount` (S58) to checkout. **Those functions and `reward_redemptions` do not exist on main-dev.** S58 migration 3 was rebuilt on 2026-10-16 and its header records the decision: S71 to S73 already ship points at checkout, and a second path would be a second place a point could become money (INV-09). What is live in code and tests today:
- `private.price_quote_calc(..., p_use_points)` (S73): points lower only Tarragon's own service fee, in whole steps, capped by steps per order and a percent of the fee, floored so the third-party part is never touched. The switch is the pricing rule `points.enabled`, **false**.
- Reserve on order creation: `orders.points_applied` / `points_reduction_kobo`; a second quote subtracts the points held by open, unexpired orders. Nothing is spent yet.
- Finalise on payment: `private.orders_pricing_effects` spends the points once (ledger row `applied_to_order`, unique key) when the order is `paid`, including a late payment.
- Release: cancel, failure and expiry spend nothing, so no row is needed. The Paystack amount is `orders.amount_kobo`, already the discounted price; the order is immutable and the DB refuses a payment for any other amount. Finance posts the real cash received; points create no money and no journal line.
- Screens: web `membership-shop.tsx` and phone `membership-section.tsx` show the "use points" checkbox with the exact reduction, and the amount due, from the server quote.
So **no second redemption path was built.** A self-check at the end of the migration and proof check 9a assert it does not exist. The cap in `rewards.points_redemption_cap_kobo` (0) belongs to the unbuilt S58 path and is not read by the live one; the live switch is `pricing_config.rules.points.enabled` (OQ-S58b-01).

## What was built (A: the real gaps in that path)
1. **Refund returns the points.** Before: a paid order that spent points and was later refunded gave the cash back and kept the points. Now `private.orders_pricing_effects` has a `refunded` branch: it returns exactly what that order spent, once (ledger key `(patient, 'orders', order, 'order_refunded')`), as kind `release` (not earning, lifetime unchanged, not counted in tiers or caps). An order that spent nothing returns nothing.
2. **Pending credit.** `public.my_points_pending()` lists point-earning events recorded in the last `look_back_hours` that have no `points_award_decisions` row yet, with `expected_by` and `ask_support`. It invents no hold and no clearing delay: it shows the lag between the action and the awarder. Config `pending_credit` (proposed: 15 minutes, ask after 120, look back 72 hours).
3. **A calm route for a credit that has not appeared.** After the ask window the points card offers "Ask our team to take a look". Web goes to `/patient/support?topic=points` (only that one known topic pre-fills the technical-support form; nothing from the address enters the ticket). Phone hands a one-shot prefill to the Technical support screen. A danger-sign phrase in the text still goes to the emergency path, as for any ticket.

## B: milestone celebrations
- `milestone_definitions` (versioned, PROPOSED; CHECK refuses body-metric words in code, trigger event and params): `first_bp_logged`, `first_glucose_logged`, `adherence_4_weeks`, `first_lab_done`, `first_review_attended`, `first_lesson_completed`, `first_course_completed`. Reward kind is not a column: a milestone is a card, with no points, no variable element, no chance.
- `milestones_achieved` (RLS: the person reads own rows only; no write grant to anyone; append-only; `seen_at` and `dismissed_at` can each be stamped once; unique per person per milestone; registered in `data_registry`).
- Driven by the **same S10 events as points**. `public.points_award(event_id)` (the existing `points.award` handler's call) now also calls `private.milestones_evaluate_event`, in a sub-block: a milestone failure writes an `audit_log` row (`milestone_event.error`) and never undoes or blocks the award. No edge function change, nothing to deploy. Idempotent: existence check plus the unique key, so a replay or a later repeat writes nothing; one `milestone.achieved` event (ids only: `milestone_id`).
- Celebrates **doing the step, never the result**: any plausible first blood pressure or glucose counts (a dangerous but plausible value still celebrates the step; an implausible one does not; weight and waist emit no event at all). "First reading in range" is deliberately not a milestone.
- Four weeks of check-ins: distinct Lagos days with an answered check-in in the last 28, at least 28 minus the grace from `streak_grace` (1 missed day per 7 = 4), so 24 of 28.
- Card: `my_pending_milestone()` returns the oldest undismissed card (stamps `seen_at` once), stops 72 hours after it was first shown, and **returns nothing while the person has an open emergency** (the red flow always comes first). Web `MilestoneCard` and phone `MilestoneCard` on the Wellness screen: no animation (so nothing to switch off for reduced motion), no number, no rank, no streak wording, dismissible.
- Age gate: `milestone_display.show_to_minors` (PROPOSED, default false). Under `minor_age_years` no card is returned; the milestone is still recorded. The earlier "shown to minors" choice is reversed to the safer default while OQ-S58b-04 is open.
- Loud failure: a milestone evaluation error writes `audit_log` `milestone_event.error` and opens/updates ONE sev3 incident `milestone_event_failed` (`page_incident_sev` updates the open one, so it is rate limited by design).
- Pending credit ignores events older than `pending_credit.ignore_before` (set to the real rollout date at apply), so pre-rollout events never sit "on their way" forever.
- Event map (S85): `milestone.achieved` has no subscriber on purpose, like `points.awarded`; the S85 registry lists only expected gaps for pre-existing types and neither needs an entry (static test and DB conformance proof re-run, see report).
- Finance check: no GL/journal code reads `points_reduction_kobo` or `points_applied` for posting (grep of `apps`, `packages`, `supabase/functions`, and the finance RPCs found only quote/receipt display and the order columns). A refund posts the cash actually received; the points return is a ledger row only, creates no money and needs no journal line.
- Not built: the optional single in-app inbox item. It would be a notification about a clinical-adjacent action (INV-07), OQ-S58-09 says no points notifications exist, and the brief made it optional. See OQ-S58b-03.

## Safety rules and where each is enforced
- No body metric: table CHECK on `milestone_definitions`, emitter skips weight and waist, `milestones-mirror.test.ts` and the existing `rewards-mirror.test.ts` scan, copy tests on `points.milestone.*`.
- No money from points: no table, function, column or rate added; self-check and proof 9a; mirror test greps the migration.
- Red flow first: card suppressed in the database during an open emergency; awarding and milestones run off the outbox, after the reading.
- No loss framing, no leaderboard, no comparison: copy tests (`points.test.ts`, web component test).
- Minors: no variable reward exists anywhere (S58 CHECK), milestones are fixed cards. By default no card is shown under 18 (`show_to_minors` false, OQ-S58b-04).
