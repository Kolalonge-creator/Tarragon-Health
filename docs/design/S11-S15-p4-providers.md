# S11-S15 package P4: the provider layer (design note)

Plan items R5, R6 and the evidence parts of R7, plus S14 hardening. Research: `docs/research/S11-S15-p4-providers.md`. Closeout and apply order: `docs/design/S11-S15-p4-providers-closeout.md`. Everything that changes behaviour sits behind a feature flag that is OFF; nothing here switches a go-live guard.

## 1. What was reconciled first (reused, not rebuilt)
- S14 adapter layer (`supabase/functions/_shared/integrations`): payment, video, email and speech interfaces, mocks, contract tests. Extended, not replaced.
- Webhooks: `paystack-webhook` (1.2k lines, its own payment_transactions idempotency, S25 order branch, S31 transfer branch), `zoom-webhook` (own `zoom_webhook_events` dedupe), `resend-webhook`. All three kept, their handling code preserved.
- S10 event bus (`claim_event_deliveries` / `complete` / `fail`, lease, backoff, admin replay): the inbox mirrors it.
- S31 payouts: the state machine already allowed `succeeded -> reversed`, approve is already four-eyes (payee cannot approve; admin or CMO approves), `payout_prepare_send` is the send gate. What was missing: any ledger posting for a payout at all, anything that stops one approver both approving and sending, any limits. `order-reconcile` only verifies OPEN orders; it never compared Paystack's settlement report (confirmed by reading it), so reconciliation is new.
- Existing WER code in `apps/web/src/lib/scribe/wer.ts` (S35) scores a sample file pair with protected terms. The gold-set harness is a separate vendor-neutral tool under `scripts/asr-eval/` because it needs per-speaker, per-accent, drug and number mismatch output and an alignment; the S35 script stays.

## 2. Provider event inbox (migration `s14x`)
`provider_events(provider, event_type, idempotency_key, raw_body, content_sha256, signature_verified, status, attempt_count, delivery_count, lease_token, locked_until, next_attempt_at, replay_count, linked_entity_*)`, unique `(provider, idempotency_key)`.
- Append-only raw: a trigger refuses any change to body, hash, key, verdict, type or received time, and any delete or truncate. Only SECURITY DEFINER functions write; `service_role` runs them. Admin read through RLS and `list_provider_events` (no raw body); `get_provider_event` returns the raw body and writes an audit row.
- `record_provider_event`: verified and new becomes `received`; the same key again keeps the first body and bumps `delivery_count` (`body_differs` is reported); a bad signature is stored `rejected` under `unverified:<sha256>` so a forged body can never occupy the key of a real event and a flood of one forged body is one row. Body size is capped (config).
- `claim_provider_event(id)` (the receiver claims what it just stored, or a provider redelivery retries a failed event) and `claim_provider_events(limit)` (the drain, SKIP LOCKED) take a lease. A rejected, processed or dead event is never claimable; an expired lease is reclaimable; at the attempt limit the event goes `dead`.
- `complete` / `fail` need the lease token; `fail` backs off with jitter and goes `dead` on a permanent error or at the limit.
- `replay_provider_event`: admin only, reason of 10+ characters, refuses a rejected or unverified event and one with a live lease, resets it to `received`, audits. It re-runs the handler: handlers must be safe to run twice (the payout, order, notification and meeting writers are).
- TypeScript: `webhook-inbox.ts` (`receiveProviderEvent`, `drainInbox`, key derivation, `supabaseInboxStore`), pure and 100% line covered. Adoption: `resend-webhook` and `zoom-webhook` now go through it and, if the inbox cannot be reached, handle the event directly as before. `paystack-webhook` takes the inbox path only when `provider_inbox_paystack` is `on`; then the event is stored first, the same code that always handled it (`processVerifiedEvent`, extracted unchanged from `handleWebhookRequest`) runs, and the inbox row records the outcome. If the inbox cannot store the event the answer is 500 (Paystack retries) and nothing is processed.
- Known limit, stated: with the Paystack flag on, an admin replay of an event the old path already recorded in `payment_transactions` finds that row and answers "replay" without redoing the work (the old path's dedupe is the primary dedupe). Replay is a real re-run for events the old path never recorded or deleted for redelivery (the transfer branch does this on purpose). Moving that dedupe into the inbox is a money-path change left for the flag-on soak.
- `provider-event-drain` (new function) retries what is due and what was replayed. It is not scheduled (needs a vault secret and a cron entry; the production connection budget is tight and no per-minute cron was added).

## 3. Reconciliation (read only; migration `s14x`)
- Adapter: `listSettlements` and `listSettlementTransactions` on `PaymentProvider`, implemented in the mock and the Paystack adapter, with contract tests on both (the fake vendor and the mock), integer kobo, paging, id validation. No write method appears in that surface (a contract test asserts it).
- `settlement-reconcile` (new function, shared-secret header, not scheduled) pages Paystack, stores `settlement_reports` and `settlement_lines`, and asks the database to compare (`reconcile_settlement_report`, `reconcile_unsettled_charges`). Our side of a charge is `payments` (v5 orders, total kobo) else the legacy `payment_transactions` charge.success row; test rows never count.
- Break types: `missing_in_ledger`, `amount_mismatch`, `missing_at_provider` (paid on our side, no settlement lists it after 72 h), `settlement_total_mismatch`. One open break per type and reference (a rerun refreshes, never stacks); a later matching report auto-clears a break with a stated reason; a person closes the rest as explained or resolved with a note, audited. **No function in this package posts or corrects anything from a break.**
- Admin view: `/admin/ops/providers` (health, break queue with ageing buckets 24h / 72h / 168h / over, inbox with replay), a navigation entry and an admin-search entry.

## 4. Payouts (migration `s31x`)
- `apply_payout_transfer_event` (rewritten from its live definition): success posts Dr 5200 Clinician fees / Cr 1000 Bank (Paystack); a later reversal after that success posts the exact opposite as a new entry; both keyed by `(payout, attempt, kind)` in `payout_gl_postings`, so a replayed webhook and a second attempt cannot double post. A posting failure (for example a closed period) never blocks the state change: it is recorded `failed`, retried by `retry_failed_payout_gl_postings()`, and a failed success posting that is overtaken by a bank return is marked `skipped` so it is never retried into the books. Flag `payout_gl_posting` (off). Account 5200 and the sources `payout` / `payout_reversal` are added to the chart and the source check.
- Reversal also writes an audit row `payout.reversed_after_success`, a payout event that says it followed a success, and a clinician notice. `my_payout_overview` now returns `reversed_at` and `paid_then_returned`; the clinician statement says in plain words that a paid payout was returned and nothing is needed from them.
- Maker-checker (flag `payout_batch_maker_checker`, off): `propose_payout_batch` (admin or CMO), `release_payout_batch` (a different approver; nobody releases a batch that pays them), `reject_payout_batch`. `payout_prepare_send` (rewritten from its live definition) requires, with the flag on, that the payout sits in a released batch for its CURRENT transfer attempt (a retry after a reversal needs a new batch) and re-checks the per-payout cap. Limits (`payouts.controls`, PROPOSED): per payout, per clinician over a rolling 7 days (sent, succeeded and batched-and-approved), per batch total and count; checked at proposal, at release (everything is read again) and at send; a per-clinician advisory lock stops two simultaneous proposals each fitting under a limit they exceed together. With only one approver in the system nothing can be released: deliberate.
- **OQ-97 compensating controls.** The founder decided Paystack transfer OTP stays off. These controls are the replacement for the second factor OTP would have given: four eyes on every send, hard caps per payout, per clinician and per batch, an append-only record of who made and who released, and a ledger that moves with the money. `payouts_enabled` stays off; no guard was touched.

## 5. Circuit breaker (migration `s14x`)
`provider_health` / `provider_health_v` (admin only, `security_invoker`) and `provider_call_allowed` / `provider_record_result`. Closed, open after `failureThreshold` consecutive outages, one probe per `openSeconds` (half open), a good probe closes. `guardedCall`, `withPaymentBreaker` (guards checkout initialisation only; verify, refund and transfer are never skipped) and `withEmailBreaker`. Fails open when the health store is unreachable. Wired into `order-checkout` behind `provider_circuit_breaker` (off). The email wrapper exists but `send-pending-notifications` still sends through its own Resend code, not the adapter, so it has no caller yet. No second provider.

## 6. Evidence tools (R7)
- `apps/web/scripts/audio-fallback-table.ts` (`pnpm audio-fallback-table [profiles.json]`) and `packages/integrations/src/evidence/audio-fallback-table.ts`: drive the real ladder with a synthetic network, print when audio only, video offer and phone happen under the proposed values and four candidate settings. Profiles are illustrative until real handset readings are supplied.
- `scripts/asr-eval/` (`node scripts/asr-eval/run.mjs manifest.json`): overall WER, drug-name and number error rates, per speaker, per accent tag, dropped negations, every mismatch with context, invented drugs and numbers; spoken numbers normalised ("one twenty over eighty" is 120 over 80); warns below 20 clips; no pass mark. No audio, no vendor, no network. Tests use synthetic data only.
- Q19: the scribe draft screen did NOT mark drug names or numbers. It now shows, under each section, a read-only copy with every drug name and number marked, for the signing clinician to check one by one; the confirm-each-section gate is unchanged and the highlight never changes the text. Drug list: `apps/web/src/lib/scribe/drug-names.ts`, mirrored by `scripts/asr-eval/drug-names.json` with a drift test.
- Q18: enforced in the adapter (a recorded consent id is required; the interface says so), in `scribe-draft` (granted, not revoked, same encounter), in `attach_scribe_draft_to_note` (S23c), by the patient's own in-app answer (S21g), and now by two triggers (migration `s23x`): a transcript or a note can carry only a granted, unrevoked consent of the same organisation, patient and note. Before this a staff user could insert a `scribe_transcripts` row pointing at a declined consent, and a plain UPDATE of `scribe_consent_id` bypassed `attach_scribe_draft_to_note`. 0 rows existed in both tables, so nothing was converted.

## 7. Safety rules kept
INV-01 no model call; INV-07 no condition or reading in any text (payout notices say "a payout", the clinician statement names no patient); INV-08 SMS untouched; INV-09 no stored balance; INV-11 the scribe draft is never written without a signature; money integer kobo; `is_test` rows never reconciled or paid; Africa/Lagos dates for ledger entries; English only; no em dashes.
