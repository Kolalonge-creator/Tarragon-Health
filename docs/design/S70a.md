# S70a design note: Module 18 core (18.1, 18.2, 18.9, 18.3 and the 18.6 / 18.5 alert paths)

Research: `docs/research/S70a.md`. Plan: `docs/design/S66-S70-build-plan.md` 4.5. Binding: CMO pack A9 to A12, as changed by the decisions recorded on branch `docs/s70-s75-decisions` (S70-1 to S70-6, D-22, OQ-309 to OQ-327). Nothing here is signed or applied.

## 1. Differences from the CMO pack, resolved for the recorded decisions
| Item | Pack | Built (recorded decision wins) |
|---|---|---|
| De-dup window | 10 min for all | BP 10, glucose 5, others 10 (S70-1, OQ-309) |
| CGM | RED under 3.0 for 15 min, amber under 3.9, high over 13.9 for 2 h | A clinician TASK, never an instant page; severe-low safety copy at once (S70-2) |
| Irregular rhythm | Same-day task | ROUTINE task within one working day (S70-3); route is the report upload plus a HealthKit ECG classification read; no Kardia or vendor API |

## 2. Reuse (mapping spec names to live tables)
`device_connections` is `wearable_connections`; `observations.source` is `vitals_readings.source` plus `device_id`. Reused: `patient_devices`, `device_catalog`, `platform_modules`, S10 events, S16 `task_types` and `create_clinical_task`, the live classifiers (`classify_bp_level` etc.), the symptom red path, `can_act_for`, the cloud adapters. Existing live behaviour with every switch off is unchanged (tests below).

## 3. Data model (migrations `20261007123854_s70a_vital_source_photo_confirmed.sql`, `20261007123856_s70a_device_core.sql`)
- Enum value `vital_source.photo_confirmed` in its own migration. No `wearable_provider` value (Withings is S70b).
- `device_config`: versioned PROPOSED values (plausibility, dedupe, cgm_events, ecg_alert), mirrored in `packages/shared` as `devices.*` with a drift test. Status stays `proposed`, owner CMO.
- `vitals_readings_held`: an impossible value, held as "please confirm". Never in the record, never triaged; kept after resolution.
- `vitals_reading_links`: the other half of a duplicate. Nothing is ever deleted.
- `device_rhythm_results`: the device's own label verbatim, category, task link.
- `device_catalog` gains `validated_source_url`, `validation_basis`, `nafdac_number`, `authorised_distributor`, review columns. A CHECK demands the evidence before `clinically_reviewed`; a trigger plus `review_device_catalog_entry()` lets only the CMO set it; an owned device can never be active (band stays unbuilt).
- RLS on all four new tables; select mirrors `vitals_readings` exactly (patient, or a caregiver with the vitals category grant); no write grant to anyone; `revoke ... from public` on every function; anon has nothing. The proof found and fixed one mistake here (a first draft let any manage-level supporter read; now identical to `vitals_readings`).

## 4. How each function works
- **18.9 plausibility.** `BEFORE INSERT` trigger `vitals_readings_a_hold_impossible` applies the table to every insert path. Impossible: SBP under 40 or over 300, DBP under 20 or over 200, SBP not above DBP, pulse under 20 or over 250, SpO2 under 50 or over 100, temperature under 30 or over 44, adult weight under 20 or over 400 (unknown age fails open), glucose outside 1.1 to 55. Everything else is saved and triaged as before. Typed-entry limits (OQ-66, 60-260 / 30-160) are untouched. Wrist SpO2: the SpO2 trigger keeps its body; only its WHEN condition gains `private.spo2_may_triage(source)`, so a `wearable` oxygen reading is saved and shown with a "recheck with a fingertip oximeter" note but opens nothing alone.
- **18.9 de-duplication.** `vitals_readings_z_cross_source_dedupe` (sorts after the manual-time stamp). Same patient and vital, DIFFERENT source, inside tolerance and window, same triage band (live classifiers, patient BP target, glucose edges in config), not pregnant BP. Better source arriving later replaces the canonical row IN PLACE (one row, no second triage, no double count) and the old payload goes to the link table; a worse source is linked and not stored. Precedence: BLE device, vendor cloud, phone mirror, photo, manual. If the in-place update fails for any reason both rows are kept (a double count is recoverable, a lost reading is not). The one change to `enforce_vitals_reading_source_lock` is a transaction-local bypass set only by this security-definer trigger. A duplicate red reading raises no second notice (proved).
- **18.5 CGM.** AFTER INSERT trigger for `source = cgm`: run-length rules from config (under 3.0 for 15 min, under 3.9 for 60, over 13.9 for 120, max gap 20 min) create `cgm_glucose_review` via `create_clinical_task`, one per kind per cooldown, a neutral in-app notice and a `device.alert` event. The phone decides the severe-low message itself from the bundled config (offline, INV-06). Failure to create a task is written to the audit log, never swallowed and never blocks the reading.
- **18.6.** `record_device_rhythm_result()`: label stored verbatim; irregular, inconclusive or unrecognised (and anything negated such as "not normal") makes one `device_rhythm_review` task due in 1440 minutes (proposed stand-in for one working day), one fixed patient sentence, one event. Symptoms answered yes now insert into the existing `symptoms` table so the existing red trigger pages.
- **18.3.** `POST /api/mobile/photo-readings` (dormant until its switch is on): numbers only, `confirmed: true` required, idempotent on `client_reading_id`, same post-insert assessments as a typed reading. Phone: camera, editable boxes with a tick per number, unit and context pickers, offline queue (numbers only). **No on-device recogniser ships in this build**: it needs a new native module (for example an ML Kit text-recognition package, exact package unconfirmed) and therefore a fresh EAS build and a `runtimeVersion` bump (currently `0.1.0-native5`). I did NOT bump it. Until then the screen shows the photo and empty boxes. `registerTextRecogniser()` is the seam.
- **18.2 / 18.1.** `recommended_devices()`, `pair_device_for()`, `device_target_for_reading()`, `devices_i_manage()`. Hardware tests are NOT claimed: BLE, HealthKit and the ECG read have never run on a device.
- **Events.** `device.synced` (once per source per 10 minutes) and `device.alert` (ids only, never a condition) in the S10 catalogue. Emitted only once any Module 18 switch is on.
- **DeviceSource.** Interface in `packages/shared`; the five cloud adapters are wrapped in `apps/web/src/lib/wearables/device-sources.ts` and `pullConnection` now calls through it with the same quiet returns and the same exception (tests).

## 5. Go-live
Seven `platform_modules` rows, all OFF: `device_plausibility_hold`, `device_cross_source_dedupe`, `device_cgm_sustained_events`, `device_ecg_rhythm_alerts`, `device_photo_capture`, `device_recommended_list`, `device_wrist_spo2_informational`. Not `go_live_guards`: adding a guard needs a branch inside `private.go_live_conditions()`, a function parallel sessions edit (OQ-371). The existing Connect card is NOT gated (it is live; gating it would switch off a working feature, OQ-372).

## 6. Safety rules honoured
INV-01 no model in triage or photo path; INV-05 nothing delays a red path (the live glucose backstop and symptom path are untouched); INV-07 notices name nothing (a test scans the template text); INV-10 new tables are no more readable than `vitals_readings`; INV-13 `is_test` stamped; INV-14 all off; INV-16 each decision stores its config version. Devices are never required. No threshold is signed.

## 7. Proof

Run as the migration spliced into one rolled-back transaction on the live project; nothing persisted (verified). `photo_confirmed` cannot be used in the transaction that adds it, so that check accepts 55P04 here and runs for real on a CI replay.
