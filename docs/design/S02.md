## 2. Access model built (INV-10, INV-12, OQ-03, OQ-04)

- `private.audit_patient_read(patient, object_type, object_id, reason, action)`: the one place an audited read is recorded. Reason of 10+ characters required, raises if the audit row cannot be written. Not executable by anon or authenticated (the private schema hands EXECUTE to authenticated by default, so the revoke names it).
- `private.can_staff_read_patient_identity(patient)`: an ACTIVE support-view session for that patient (`private.can_support_view`, the mechanism that tells the patient a session started) or an active break-glass grant. A bare `support.view_as` holder can search (minimal fields) but cannot open a record without a session. **One function so S16-S19 add the tied-patient rule (active task, lead assignment, on-call page) in one place.**
- Public audited RPCs (authenticated only, gate inside): `search_patients_audited(query, reason)` (patients only, minimal fields, phone masked, query text and any hash of it never stored, only its length and the result count), `open_patient_identity_audited(patient, reason)`, `read_patient_consents_audited(patient, reason)`. A refused staff caller gets an empty result and a `denied` audit row carrying the patient (`private.audit_denied_read`); a patient caller gets a 42501 error and writes nothing.
- `patient_consents` direct SELECT is now the patient only. Every other reader was checked live and is SECURITY DEFINER. No app code read the table as staff.
- Break-glass already exists and was reused, not rebuilt: `request_emergency_record_access` writes `emergency_record_access_grants` plus an `audit_log` row, `review_emergency_record_access` gives the CMO review, `private.has_emergency_access` excludes `reproductive_health`. Regression-guarded in the S02 proof. CMO alerting wiring stays with S19/S20.
- Protected categories: nothing in S02 returns reproductive, mental-health or clinical rows (identity and consent only, asserted structurally in the proof).

## 3. INV-13 (test accounts)

`is_test` on `profiles` and `clinical_staff`; only an admin or a service context can set it (`private.guard_is_test_flag`; the existing `guard_profiles_self_update` is a deny-list, so a new column would otherwise have been self-editable). Backfilled from `@tarragon.test` (2 accounts live). **Convention for every metric, payout and analytics view: join `public.profiles` and filter `not p.is_test`.** The proof carries a ratchet that fails on any NEW public view named `%payout%` or `%metric%`, or any `analytics` view, that does not mention `is_test`.

## 4. Follow-ups (nothing here is done)

2. Existing metric surfaces that ignore `is_test`: `hypertension_quality_metrics`, `obesity_quality_metrics`, `diabetes_quality_metrics` (allow-listed in the ratchet) and the 56 `analytics_*` RPCs. Practical exposure is low today (2 test accounts) but INV-13 is not met until they filter.
3. Clinical tables still readable by any org staff and needing the audited-read treatment (OQ-02/OQ-03, phased, `/code-review ultra` each): reproductive (`menstrual_*`, pregnancy, contraception) first, then mental and sexual health and clinical notes, then the rest of the roughly 110 `is_org_staff` tables.
4. A staff refusal returns an empty result (so it can look like 'no data' to a UI); raising would roll back its own audit row. Needs an explicit status column or a non-rolling-back audit channel. `audit_log_select` still lets any org staff read every audit row in their org (pre-existing); narrowing it is a separate change.
5b. `proxy_setups`: one pending setup per creator and target phone; a per-target and per-creator rate limit belongs to S04 where the SMS is sent.
5c. `request_ip` prefers `cf-connecting-ip`, then `x-real-ip`, then the rightmost forwarded hop; confirm which header the Supabase edge really sets before relying on `audit_log.ip`.
5. `authenticated` can still INSERT `audit_log` directly (`actor_id = auth.uid()`); rows cannot be altered but a user can add rows about themselves. Left as is (existing behaviour, other code depends on it).
6. `search_support_view_subjects` (view-as feature) is not audited. It predates S02. Converting it to write an audit row needs a reason parameter, so it is a small change to the view-as UI.
7. `proxy_setups` confirmation, decline and expiry are S04's SECURITY DEFINER functions; the 72 hour window is supplied by S04 from versioned config (no column default on purpose).
