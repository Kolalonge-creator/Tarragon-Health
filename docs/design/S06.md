# S06 design note: offline store and outbox sync

Decisions S06-1 to S06-4 (`docs/DECISIONS.md`) are inputs. Invariants INV-02, INV-05, INV-06 and INV-10 shape the rules below.

## 1. Reconciliation (what exists, what changes)

| Existing | Used as | Change |

## 2. Data model

Server (migration `*_s06_offline_client_recorded_time.sql`): `client_recorded_at`, `received_at`, `time_basis` on `vitals_readings`, `symptoms`, `medication_logs`; table `offline_sync_config` (versioned, one active row). `taken_at` / `reported_at` / `logged_at` stay the one defined time every reader uses. They hold the device time only when it is not more than `future_skew_minutes` ahead of receipt and not older than `backdate_window_hours`; else server time. `received_at` is always server time. Non-manual vitals (device, wearable, CGM, FHIR) are untouched.

Device (`tarragon-offline.db`):
- `outbox(client_id pk, kind, owner_user_id, subject_id, beneficiary_profile_id, payload json, client_recorded_at, created_at, attempts, next_attempt_at, state pending|rejected, last_error, last_status, danger)`.
- `local_vitals`, `local_symptoms`, `local_doses`, `local_medications`: read mirrors of the patient's own rows, upserted by id. `sync_state(key, value)` holds one pull cursor per table.
- `drafts(key, value, updated_at)`: form drafts saved on every change.

## 3. Rules

- **Write**: a log is durable in `outbox` before any network call; its UUID is the idempotency key (`client_reading_id` for vitals, `client_id` for symptoms and doses). Time is the device clock at logging.
- **Replay safety**: vitals replay is a server no-op (23505); symptoms and doses treat 23505 as done. A blind retry never double-writes. Every database trigger that raises an alert runs on the single successful insert, so a retry cannot fire a second emergency.
- **Order and isolation**: oldest first, one row at a time. A network failure stops the run (the radio is down). A server refusal marks that row and the run continues, so one bad row never blocks the queue.
- **Failure classes**: `network` (stop, no attempt counted), `auth` (stop, row kept, no attempt counted), `retry` (5xx and unknown: exponential backoff 30 s to 30 min), `rejected` (4xx validation, 42501 row security, 22/23 constraint: terminal, never retried automatically).
- **Rejected rows are never dropped silently.** They stay in `outbox` as `rejected`, show in the app with a support code (first 8 characters of the id) and the reason, and the patient can Retry or explicitly Remove from this phone (a confirmed action, logged to diagnostics).
- **Who logged it**: every row stores `owner_user_id` (the signed-in account when logged) and `beneficiary_profile_id` for a supporter. A flush only sends rows whose owner is the current session. On sign-out nothing is deleted and nothing is sent. On a user switch the previous account's rows wait, are counted as held, and go out when that account signs in again. Token expiry holds rows (class `auth`). The database still stamps `logged_by_profile_id` from the live session and still refuses a supporter below manage level.
- **No clinical change offline (INV-02, S06-2)**: medications are cached read-only. Only readings, symptoms and dose logs queue.
- **Stuck notice (S06-3)**: an unsynced row older than `stuck_notice_hours` (12), or `stuck_notice_danger_hours` (1) if the device classified it as urgent or emergency, makes the app say plainly it has not reached the care team. Numbers come from `offline_sync_config`, cached on the device with bundled defaults.
- **Pull (S06-4)**: per table, read `created_at >= cursor - overlap`, ordered by `created_at, id`, in pages; upsert by id; cursor moves to the newest `created_at` seen. Live tables, not the S05 aliasing views (the views are `security_invoker` shells with renamed columns; the tables carry `created_at` and the idempotency keys directly). Medications have no append-only guarantee, so the active list is replaced whole.

## 4. Emergency delay (INV-06 context)

An offline dangerous reading raises its alert at sync time, not logging time. The device shows the existing on-device emergency guidance immediately (S06 does not change that); the care team learns when the row syncs: up to the next connection, and the patient is told after 1 hour that it has not reached them. On-device red rules for more vital types are S11 and S12.

## 5. Events

`observation.recorded` and `dose.recorded` fire from the database insert as today. The outbox adds none.

## 6. Screens

Vitals, symptom and medication screens show a per-row state (Saved on this phone, Sent, Not sent yet, Could not be saved) and a single banner for held, stuck and rejected rows with Retry. Strings go through `packages/i18n` (en, pcm), no em dashes.

## 7. Low data and power cut (spec section 11)

- Drafts saved on every change (`drafts`), cleared on successful enqueue.
- No image or audio auto-download: S06 downloads none. The pull reads text rows only, columns trimmed.
- Pull pages capped; a pull is skipped on a metered or offline state; daily data target (under 1 MB) is checked as payload bytes in tests, not measured on a device.

## 8. Performance budget (2 GB Android class)

Budget is code in `offline-budget.ts` and tests on the Jest SQLite stand-in. **Not measured on a device**: cold start (under 3 s), installed size (under 40 MB), real memory. Measured on the stand-in only: enqueue latency, backlog flush bookkeeping, database file growth, pull upsert time, bytes per day. No stand-in number is reported as met on a 2 GB phone.
