## 3. The gate (safety design)

`public.my_nutrition_guidance()` is the only way a patient receives a plan or a swap. It answers `{state:'unavailable'}` for "not signed yet" and for "not for you", identically, exactly as `my_nutrition_target_gate()` does, so calling it (for example on someone else's unlocked phone) reveals nothing. The apps render `unavailable`, a failed call, and anything they do not understand as NOTHING: no empty card, no hint.

* The swaps, the weight plan and the condition plans (hypertension, diabetes, kidney) are withheld exactly when `private.nutrition_targets_withheld()` is true: pregnancy, the postnatal year, a clinician hold, a positive eating-disorder screen, under 18. The S49a gate is reused, not copied.
* A condition plan appears only for a patient with an ACTIVE `care_plans` row of that condition (kidney is `ckd`), the same source the existing meal-plan code uses. The weight plan appears for every adult who is not withheld.
* The pregnancy plan: `private.nutrition_pregnancy_known(auth.uid())` reads the three places pregnancy is held (profile flag, `patient_pregnancy`, reproductive life stage `pregnant`), on the signed-in person's OWN record only. The public function takes no patient argument and the private one is not executable by a client, so a caregiver or supporter is answered about themselves, never about the person they support. Written fresh; no older sibling's policy was copied. A pregnant patient is shown ONLY the pregnancy plan (no swaps, no other plan), and one under a clinician hold or with a positive eating-disorder screen is shown nothing. A pregnant patient who is not pregnant in any of those records gets nothing, which is also what an unknown state gives.
* `public.nutrition_guidance_is_signed()` is a platform-wide fact (is any version signed), carrying nothing about the caller. It exists so the web can keep using the old built-in swap hint until a table is signed and stop using it the moment one is, so a person the signed table withholds never falls back to the old hint. A failed call to either function is treated as "signed and unavailable" (the safe direction, logged), never as the old hint.
* Signing is Chief Medical Officer only (`sign_nutrition_guidance_config`). The config validator is a database CHECK mirrored by `parseEatingGuidance` in code; a half-valid answer makes the whole answer unavailable rather than showing half a plan.

## 4. Sign-off hub

One new governed table, so one panel: `nutrition_guidance_config` ("Eating plans and food swaps", slug `nutrition-guidance-config`) is registered in `GOVERNED_CONFIG_TABLES`, `signoff-queue.ts`, `refuse-superseded-draft.ts`, `CONFIG_PANELS` in `clinical-signoff/page.tsx`, the admin search and `proposed-config/registry.ts` (`nutrition.eating_plans_numbers`). The count in `governed_config_supersede_guard.sql` goes from 19 to 20. Nothing was signed.

## 5. Phone

Plans are fetched from `/api/mobile/nutrition/eating-plans` and kept in the encrypted store, one copy per account, under these rules (`eating-plans-model.ts`): a fresh `unavailable` ERASES the copy; a copy older than 7 days is not shown; a copy is shown only when the request itself failed. The pregnancy plan is shown but never saved. A server failure is a 503 (never a fake "unavailable"), so a saved copy is kept through it. The card is drawn only on the person's own account (never on a supported person's screen). The 7 days is a judgement call (OQ-S50A-3). The older built-in swap hint still reaches withheld people until a table is signed (OQ-S50A-6). Requesting nutrition support and booking a dietitian visit are on the web; the phone shows the status only.

## 6. What is deliberately not done

* No naira-budget planner or shopping list (S50-1). No new AI call. No calorie, protein, potassium or phosphorus figure anywhere.
* The referral does not move to `scheduled` by itself when a visit is booked. Booking a visit and the referral row are still two things; staff move the referral. See OQ-S50A-2.
* No dietitian review of any swap. No go-live guard was added or touched.

## 7. Order of release

Apply the migration first, then deploy the code. The migration is purely additive. The code works against the old schema until the migration is applied only as far as the new RPCs: the web loader treats a failed `nutrition_guidance_is_signed` call as "signed and unavailable", so before the migration is applied the web shows no swap hint at all (rather than the old hint). Apply before merging (CI does not apply migrations).
