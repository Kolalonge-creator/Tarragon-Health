# S85 Design: end-to-end journeys and the event map (D.7)

Spec D.7.2 (event map) and D.7.3 (four journeys), invariants INV-01, INV-03, INV-05, INV-06, INV-07, INV-10, INV-12, INV-13. Depends on S40 (not passed). Plan: `docs/plans/S85-S87-build-plan.md` section 3.

## What S85 is, and what it is not
S85 cannot be completed as written because much of what the journeys touch is not built: Health Points (S58), the symptom checker (S59, S60), the consultation directory (S64), the institution console (S79), and the PHQ-9, wearable and pregnancy events. So this session builds the **harness and the honesty mechanism first**, runs every step that can run today, and declares every other step `pending(owner_session)`. **No journey is reported "passing" while any step is pending or skipped, and nothing here says a stage or gate is complete.** A pending step is a promise: the owner session turns it on by deleting one line.

## Parts
1. **Step model** (`packages/shared/src/journeys/steps.ts`, pure). States `passed | failed | pending(owner) | skipped(reason)`. A journey declares every step first; an unresolved step is a failure; verdict is `failed`, `incomplete` or `passing`, and `passing` needs every step passed. A pending step must name an owner (`S58`, `S59, S60`, `CMO`, `FOUNDER`). Reports are JSON plus text, counting pending steps per owner.
2. **Journey definitions** (`journeys.ts`): the four journeys as typed step lists with the known-pending steps and owners as data. Jest checks every owner exists in `docs/v5-sessions/00-INDEX.md`.
3. **Event-map conformance**
   - `event-map.ts` is one row per D.7.2 event plus the two spine rows (triage to queue, triage to page). A row is conformant when the event type is seeded, an emitter calls `private.emit_domain_event('<type>'`, a migration registers a subscriber whose `handler_key` is registered in `process-events/handlers.ts`, and the handler's port calls a named RPC that a migration defines.
   - Rows that fail today carry an **expected-gap entry** naming exactly which components are missing and the owner session. The registry may only shrink: a gap that starts passing, or gets worse, fails the test until the entry is updated.
   - Static check: `event-map.test.ts` reads the real migrations and `handlers.ts`, with sabotage cases (remove a handler registration, remove an emitter, close a gap, worsen a gap).
   - Database check: `packages/db/tests/s85_event_map_conformance.sql` (in `ci.manifest`) asks the migrated database what is seeded and registered, emits one event per type in a rolled-back transaction and counts the deliveries. A sabotage step proves it can fail. The Jest test compares the SQL file's gap lists to the registry so the two cannot drift.
4. **Harness** (`apps/web/e2e-browser/journeys/harness`)
   - `env.ts` local-only guards for the API URL and the database URL. `sql.ts` seeds and observes through `psql` (the proof runner's tool). That channel is for seeding and for looking at rows only.
   - `sessions.ts` creates real users with real passwords and signs in with the anon key. **Every access assertion goes through a real signed-in session** (patient, clinician, institution admin, supporter), never through the service role.
   - `drain.ts` runs the bus synchronously with the same dispatcher and handler registry the edge function uses, so a journey need not wait for the 15 second cron. A parity test compares its RPC calls with `process-events/index.ts`. A fetch spy records every host contacted (INV-01).
   - `capture.ts` is the notification capture: it reads `public.notifications` (the outbox). The send function is never run, nothing is sent. An INV-07 neutrality check runs over what was written for a real event.
   - `clock.ts` a deterministic clock for harness waiting. Server time is not faked: where a rule depends on elapsed minutes the journey moves the row's own timestamp through the same guarded flag the DB proofs use, and says so. The browser clock is left real because a faked page clock makes session tokens look expired.
   - `oncall.ts` an on-call team fixture (CMO, primary, backup, rota), the same shape as the S19 proof.
   - `report.ts` writes `test-results/journeys/<id>.json` and `.txt`.
5. **Journey 2** (full depth, Playwright, real browser). Patient logs a very high reading through the real form; an emergency symptom is recorded through the patient's own session; the web guidance dialog is asserted; the network is switched off and the form must refuse and not claim a save; the on-device engine (bundled rules, no fetch) must grade at least as severe as the server; the bus is drained; the stored grade must equal what the engine gives on the same facts with the rule set read from the database; no model call; queue item, page, Care Circle alert, neutrality, acknowledgement, audit rows and the follow-up tasks named by the graded actions. **The grade is never hard-coded.**
6. **Journey 1** spine test: phone sign-up with the local test OTP, password, an order through the real RPC, the INV-03 hold of an abnormal result and its release by a real clinician session, daily readings graded through the bus, a Care Circle join. Health Points, the care-pack offer, the risk questionnaire, the screening calendar, the silence nudge and the explanation are pending with owners. Checkout through Paystack is `skipped` with the reason unless keys and a served function exist.
7. **Journey 4** privacy property test: a 300 person cohort, joined through the real `join_cohort` RPC; real institution, clinician, admin and patient sessions; aggregates only, small cell suppression, no reproductive or mental health data though rows exist, plus controls so an empty result cannot be an empty fixture. Redemption in the institution console and sponsored entitlements are pending S79.
8. **Journey 3** typed skeleton: every step pending with its owner (S59, S60, S64, S54, S53, S51), run as a Jest test because it needs no stack.
9. **Maestro and CI**: see "Running" below and the README in `apps/web/e2e-browser/journeys`.

## The rule set question (never sign, never hard-code)
A fresh stack holds `bp_care_triage` versions as drafts only (approval is a CMO signature through `approve_triage_rule_set`). Until a rule set is approved the server grades with the draft and records the result as **shadow** (OQ-88): nothing new pages or creates a task. A parallel branch drafts a 180/120 trigger version that is neither approved nor merged. So the journey reads whatever is in the database:
- it records which version and status the grade used (`rule-set-read-from-database`);
- step `d1-rule-approved` passes only if an approved row already exists that a real (non test) Chief Medical Officer approved; otherwise it is `pending(CMO)`, always, even in fixture mode;
- the queue, page and Care Circle steps need an approved set. With a draft they are `pending(CMO)` and the journey asserts the shadow behaviour instead (shadow flag set, nothing new paged). With `S85_FIXTURE_APPROVE_RULESET=1` a **test** CMO approves the highest draft inside the disposable local database (the same call a real approval makes, never a real signature), so the downstream pipeline is exercised. The report says "fixture approved" and the journey stays incomplete. The fixture helper refuses any non-local database.
- Expected grade = the engine run on the facts the server used and the rule set the server read.

## Safety rules for this session
No language model is called. Test data is always `is_test`. No secrets are committed or printed. English only, no em dashes, "your care team". The service role is used to seed and observe, never to prove access.
