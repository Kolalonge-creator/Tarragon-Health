# S86: adding languages framework (dormant), design note

Status: built dormant. Decision D-14 (2026-10-06) stands: the product is English only. This session ships no language, widens no database constraint, adds no migration and no table. Spec D.8 ("add yo, ha, ig") is superseded by D-14 (see `docs/DECISIONS.md`, S86-1).

## What already exists and is reused
- `packages/i18n/src/clinical-wording.json`: the signed pattern (current, proposed, signed by, on, version). Reused as the shape of a sign-off.
- `audio/manifest.json` and `scripts/audio/*`: per clip, per language file with sha256, approvals (brand, clinical, legal) tied to the recording's sha256, and a `script_hash` that drops sign-offs when the English script changes. Reused as the audio pairing rule.
- `packages/shared/src/proposed-config`: versioned PROPOSED config, owner CMO. Reused for the registry (`i18n.language_registry` v1).
- `i18n.test.ts` key parity over `LOCALES`: untouched and still the production parity test.
- No language picker exists in the web or mobile app today, so no UI is touched.

## Model (config, not schema)
`i18n.language_registry`: `source_language`, `features` (key prefixes, audio manifest groups, clinical flag) and `languages`. Per language: `status` (`draft`, `native_reviewed`, `clinician_signed`), `enabled_for` (feature keys) and two sign-off maps (`native_review`, `clinician_signoff`) keyed by feature. A sign-off is `{by, on, version, set_hash}`; `set_hash` is the SHA-256 of the English and the translated text of that feature's string set, so editing any word, or the English source, makes the sign-off stale (the same idea as `script_hash`). Default and only entry: `en`, enabled for every feature.

Features: `emergency_triage`, `course`, `results_consult` and `health_and_care` (clinical, need a CMO signature; `health_and_care` is the catch-all, so any key nobody names, including new ones, is treated as clinical) and `general_ui` (explicit non-clinical prefixes, native review only). Every English key belongs to exactly one feature (longest prefix) and every audio group to exactly one feature; both are tested.

## Pure functions (`packages/i18n/src/language-readiness.ts`, not exported from `index.ts`)
`keyParity`, `stringSetHash`, `clipPairing`, `featureCoverage` / `coverageReport` / `formatCoverageReport`, `checkLanguageGate`, `pickerLanguages` / `shouldShowLanguagePicker`, `resolveMessage` (fallback), `audioScriptText`, `parseLanguageRegistry`.

## Gate (a language is listed as enabled for a feature only if all hold)
1. Every key of the feature present, non-blank, same placeholders as English.
2. Native review sign-off matching the current text; for a clinical feature also a CMO sign-off matching it; language status high enough.
3. Every audio clip of the feature recorded and signed against its own sha256 (and, for a non-source language, made from the current English script).
4. English stays enabled for every feature so fallback always exists. The source language is exempt from review and audio (a missing clip shows its text, spec 8.8).

## Report
`pnpm --filter @tarragon/i18n language-report` prints, per language and feature: keys present, reviewed, signed, audio paired, enabled. The same suite asserts the production gate is clean, so CI fails on a registry that enables something incomplete.

## Generalised English-only assumptions (production output unchanged)
- `AudioScript` keeps `en` required and adds an optional `other` map for further languages (hand edit plus the generator template; the generated data is byte identical).
- `import-production-list.py --languages en,xx`: creates empty, unsigned file entries per language; the default is the language list already in the manifest (`en`), so a plain re-run never drops a language and produces the same manifest. (The source Word document is not in the repo, so this edit was compile checked only, not re-run.)
- `ingest-recordings.mjs --languages en` (default): ignores and never bundles a file for a language not named; a non-English recording is playable only when signed against its checksum and its source script hash.

## Picker rule
`shouldShowLanguagePicker`: lists only languages enabled for every feature; with one it renders nothing. Not wired (no picker exists).

## Safety rules
No language model is called. Nothing is signed or seeded by a build; only the CMO publishes a new registry version. The stub language `xx` exists only in test files and is asserted absent from `LOCALES`, the catalogues, the manifest and production config.

## Known limit
The runtime manifest parser in `packages/audio` accepts English only, on purpose. Adding a language means widening its `Lang` in the same pull request as the registry change; until then a manifest with another language is rejected at load, which is the safe failure.

## Future review standard (for whoever adds a language)
Forward translation, independent back translation, reconciliation of differences, native clinical review of the string set, CMO signature per string set, then per feature enablement by a new signed registry version. Audio is recorded only after the text is signed. An alternative that needs no translated clinical text: language-matched consultation using the clinician `languages` field (S64).
