# S85 D2: fertile window hidden by default, opt-in "Planning a pregnancy" mode

Status: built on branch `s85d2/fertile-window-opt-in`, stacked on S87 (Part C scan). CMO wording is UNSIGNED.
Decision source: OQ-12 (founder, 2026-09-30) and the S85-S87 sign-off pack, D2.

## What the founder decided (binding)

- The fertile window is hidden by default. It shows only when the person turns on a mode called "Planning a pregnancy".
- Every screen that shows it carries exactly: `Not contraception. This cannot prevent pregnancy.`
  with the link text `Learn about contraception and talk to your care team.`
- Banned anywhere: "safe days", "avoid pregnancy", "natural contraception" (the Part C scan already enforces this).
- Temperature-based ovulation confirmation sits behind the same mode and label.
- Period prediction stays visible by default.

## What counts as "the fertile window" in the code

| Surface | Web | Mobile |
| --- | --- | --- |
| Ring arcs "fertile" and "ovulation", legend entries | `cycle-ring.tsx` | not drawn |
| Calendar shaded band and "estimated ovulation" day | `cycle-calendar.tsx` | not built |
| "Estimated ovulation" and "Fertile window a to b" stat | `cycle-tracker.tsx` | `cycle-screen.tsx` |
| Current phase "Fertile window" / "Ovulation" and their descriptions | `cycle-tracker.tsx` | `cycle-screen.tsx` |
| Pattern text "Usually in your fertile window" | `cycle-insights-card.tsx` | not built |
| Temperature rise "suggests ovulation" | `cycle-insights-card.tsx`, `cycle-day-log.tsx` hint, `cycle-thermal-shift.ts` | none |
| Reading suggestions whose reason says "fertile window" | `cycle-reading.ts` | not built |

## Where the per-user mode lives

An additive column on the existing `public.reproductive_health_profiles` table:
`planning_pregnancy_mode boolean not null default false`.

- The table already carries the category-scoped RLS model (`reproductive_health` category grant for any caregiver, `manage` permission
  for writes, adolescent guardian gate, patient always). A column inherits row policy, so nothing is copied from a sibling table and no
  policy is rewritten. The proof script (`packages/db/tests/s85d2_planning_pregnancy_mode.sql`) shows a simulated caregiver is refused,
  and sabotages the policy once to show the proof fails.
- Default false means every existing row, and every patient with no row yet, is "off". No data conversion (row count is irrelevant to a
  default-false column).
- No second table, no new function, no new grant: `authenticated` already has table-level privileges on this table.
- Nothing else reads the column. Cycle data stays out of risk scoring, as before.
- Migration `20261007171346_s85d2_planning_pregnancy_mode.sql`. It is committed but NOT applied to production by this change.
  Until it is applied, the app reads the column defensively: a missing column is treated as "off" (the web page and the phone select
  tolerate the error and fall back to false). Off is the safe state.

## Behaviour when the mode is off

A single pure function per app, `hideFertileWindow(prediction)`, returns the prediction with `predictedOvulationDate`,
`fertileWindowStart` and `fertileWindowEnd` set to null, and shows the person a neutral phase. Everything downstream (ring, calendar,
stats, phase text, insights, readings) takes the filtered prediction, so no surface can leak the window by reading the raw one.

- Ring: period arc plus one neutral arc "Between periods". No fertile or ovulation arc. The luteal split is not drawn either, because
  the point where it starts reveals the end of the window.
- Phase line: "Period" when bleeding, otherwise "Between periods" with a neutral line. (Open question for the CMO: whether the
  luteal phase label, which helps with premenstrual symptoms, may stay visible. It is hidden for now because its start date is the
  window's end.)
- "What to expect": next period only. No ovulation tile.
- Pattern insights: phase wording is neutral ("Usually between periods.").
- Temperature rise sentence and detection are not shown. The temperature and ovulation-test inputs on the daily log stay (logging is
  not displaying), without the "suggests ovulation" hint.
- Readings: the fertility basics article is not suggested on the strength of a window the person cannot see.
- A short card near the top explains the switch, with the switch itself.

## Behaviour when the mode is on

The window shows as before, with the label directly under each place the window or the temperature confirmation appears. The label is
rendered by one component on the web (`FertileWindowNotice`) and one on the phone, from one source of words.

## The words, and the unsigned state

- Source: `packages/i18n/src/clinical-wording.json`, new top-level block `fertileWindow`, with `current`, `proposed` and
  `signed: null`. `activeFertileWindowWording()` returns `proposed` only once `signed` is a real record; otherwise `current`.
- `current` and `proposed` are the same founder-mandated text. A missing label is the unsafe state, so the label must render
  correctly either way. The CMO signs through the existing route; this change never sets `signed`.
- i18n catalogue (`en.ts`) carries the same strings as keys, kept equal by a test.
- No em dashes. "your care team", never "your doctor".

## Safety rules the tests enforce

1. The mode is off by default, for no row, a null column and `false`.
2. With the mode off, a prediction has no ovulation date and no window, and no phase says fertile or ovulation.
3. Every surface that shows the window renders the exact label and link text (web: component tests; phone: the label module plus a
   source check, because the phone has no component test harness).
4. Removing the label from a surface fails the test (a sabotage test renders without it and expects the failure).
5. The Part C scan no longer allows any `fertile-window-label` file, and its rule accepts the label only when the file imports the
   shared label, so a file cannot silently drop it.
6. Banned wording is absent from the new strings.
7. Temperature confirmation text appears only with the mode on.

## Not done here

- No CMO signature, no activation of the proposed state.
- Not applied to the live database.
- Not run on a device or simulator (the phone has logic tests only).
- The `fertile` and `ovulation` values in the `CyclePhase` type and the engine remain (the engine still computes them). They are
  filtered at the edge. Removing the computation would change the engine for the mode-on case.
