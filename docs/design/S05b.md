## 1. Genotype and blood group: self_reported or lab_verified

Where they live: one table, `public.patient_blood_profile` (0 rows live). It already carried `provenance` (`lab_document` needs a report that belongs to this patient; `patient_attested` needs an attestation stamp), and `private.enforce_blood_profile_provenance` forces any non-staff caller to `patient_attested`. A later source-precedence rule (lab beats attestation) means a patient cannot overwrite a lab-backed value either; her attempt is recorded in `superseded_source_values`.

What was added: `patient_blood_profile.verification`, a **generated** column (`lab_verified` exactly when `provenance = 'lab_document'`, else `self_reported`). It cannot be written by anyone (428C9), so there is no second field to drift and no extra guard to get wrong; the guard is the existing trigger.

Shown as "Self-reported" and "Verified by a lab" (`BLOOD_VERIFICATION_LABEL` in `@tarragon/shared`): the clinician chart form, the emergency card (web and print), the patient's emergency-card page. The mobile emergency card does not show provenance today and was not changed.

## 2. One supersede-with-status rule

Rule: a clinical value that was relied on is never edited and never hard-deleted. A correction creates a new row that supersedes the old one; the old row is kept and marked with a status (`corrected`, `amended`, `entered_in_error`, or `cancelled` when a clinician already acted on it); actor and reason are stored.

### What was built (migration `20261013184219_s05b_supersede_not_edit_corrections.sql`)

* Enum `correction_status` (`corrected`, `amended`, `entered_in_error`, `cancelled`).
* Columns on the four tables: `supersedes_id`, `superseded_by_id` (no foreign key: a deferred one leaves pending trigger events that block later ALTER TABLE in the same transaction; only the function writes it), `correction_status`, `correction_reason`, `corrected_by`, `corrected_at`, plus a CHECK that a marked row has a status, a time and a reason of at least 5 characters.
* One guard trigger function, `private.enforce_clinical_value_supersession`, attached to all four. `SECURITY INVOKER` on purpose: it sees the role running the statement, so a client (including the service role) is refused, and only the correction function (a definer function owned by postgres) may write the chain columns. Value columns are frozen per table (the list is the trigger argument; device and connection ids are not, because their foreign keys null themselves when the device is removed). DELETE is refused unless a privileged function set the transaction-local flag `app.allow_clinical_value_delete`; only the patient's own "delete my wearable data" does (patched in the same migration, asserted, row count preserved). A cascade from a deleted profile is refused as well (the test-account purge disables triggers on the tables it touches).
* `public.correct_clinical_value(table, id, status, reason, replacement)`. **Not yet granted to `authenticated`** (service role only, so a server action acting for a verified user can call it): no read path hides superseded or `entered_in_error` rows yet, so exposing it to every signed-in user would double count a corrected value and keep showing a voided one. S05b-c adds the read filters and the grant in its own migration. Who may call it (checked inside, from `auth.uid()`): a clinician tied to the patient (`private.clinician_has_patient_access`) at a tier other than care coordinator, and the patient on entries she made herself (a manual reading, an allergy or condition with source `patient` that no clinician verified), never on a lab value, never to `cancelled`, never on a reading a clinician already reviewed. `entered_in_error` and `cancelled` take no replacement; `corrected` and `amended` require one, limited to a per-table allow list of value columns. A reading a clinician already validated cannot be `entered_in_error`; it is `cancelled`. The original is marked first, the replacement inserted second, in one transaction. A manual replacement keeps the original time through `client_recorded_at` while it is inside the offline backdating window (72 hours); older than that, the platform rule that manual readings cannot be backdated wins and the replacement is stamped with the correction time (the `supersedes_id` link keeps the original time visible).
* The replacement does not carry a coded or derived column the new values can invalidate (`allergen_concept_id`, `condition_concept_id`, `analyte_concept_id`, `abnormal_flag`: dropped, so uncoded or unflagged rather than wrong). A clinician's correction of an allergy or condition is stored with source `clinician`, and a staff-logged reading keeps the staff member's id, so the patient guard cannot supersede it.
* Known limits: the existing triggers fire on the replacement as on any new row, so a corrected dangerous reading raises its own alert; alerts raised for the original are not cancelled or linked (follow-up with the read filters). The `ON DELETE SET NULL` on `corrected_by` is the one chain change the guard lets through from outside the function (a profile removed later), checked in the proof.
* Before the `authenticated` grant (S05b-c): freeze or guard `validated_by`, `validated_at` and `logged_by_profile_id` against a patient clearing them (she has an update policy on her own readings; the patient guards in the function rely on those columns); the patient guard must also refuse a reading that raised an alert, escalation or triage event (it checks only `validated_by`, the staff id and the source today); the corrected replacement re-fires the red-flag, timeline and adherence triggers like any new reading; any new definer function that deletes these rows must set the flag explicitly and be reviewed; the scan test matches the literal `.from("table").update(` chain only, so a helper that takes the table name as a parameter is caught by the database trigger, not the scan.
* Not built (no UI calls the function yet): reads do not yet hide superseded or `entered_in_error` rows (S05b-c).

## 3. Range source on lab values

Tables holding a displayed range: `lab_analyte_readings` (`reference_range_*`), `lab_result_items` (`ref_low`/`ref_high`, written by `private.submit_lab_result` from the CMO-signed panel version), both 0 rows live. Migration `20261013184358_s05b_lab_range_source.sql`:

* `range_source` (`lab_report`, `guideline`, `cmo_signed_config`, `unspecified`, default `unspecified`) and `range_source_ref` on both tables.
* `lab_analyte_readings`: a stored range **must** declare its source (CHECK), `guideline` and `cmo_signed_config` need a named reference, `lab_report` needs a range. Nothing guesses: a writer that has a lab-supplied range says `lab_report`.
* `lab_result_items`: a trigger stamps `cmo_signed_config` with "lab panel X version N" when the panels are signed (exactly the predicate the release rules use, `private.lab_panels_signed()`), else `unspecified` with a reference saying it was a proposed, unsigned panel range (nobody sees it as a number except the reviewing clinician, who sees it labelled "Range not signed"). Sign-offs have no structured list of the panel versions they cover, so the label can only be as precise as the release gate; a structured coverage field is the better fix.
* `my_lab_results()`, `lab_result_for_review()` and `record_share_by_token()` are patched in place from their live definitions and return the source.
* Screens: patient released results, clinician result review, the shared-record page, the CMO lab-panel page (names the signed version or says the ranges are proposed), and the lab-partner entry box (says its reference is the Tarragon panel for entry only). The rule in code: `describeRangeWithSource` shows the numbers only for a known source and prints "Range not specified" otherwise; `rangeMayBeShownAsClinical('optimal')` is false. A qualitative analyte (no numeric range) prints nothing in the range cell.
* Not covered: `screening_results.interpretation` carries a `reference_range` string (from `fallback-interpretation.ts`, with the guideline in code comments) but no screen renders it today.

A staff correction of a device or wearable reading keeps the original `source` and device ids (the provenance of the instrument) and records the staff member in `logged_by_profile_id`; the lab-partner entry screen states that the patient sees the Tarragon panel range, not the range printed on the lab's own report (which is not stored).

Accepted limits of the range stamp (review findings, to revisit with a structured sign-off coverage field): the stored label is written once when the item is inserted (the table is append only); the two lab-result read paths resolve it at read time (a result entered before the signature reads as signed once the panels are signed; before that the reviewer sees the typed marker `proposed_unsigned`, never a stored value); the frozen-column lists are an explicit blacklist (a column added later must be added to the trigger argument; the self-check proves every listed column exists); a corrected lab value is stored without `abnormal_flag` until a clinician flags it again.

## 4. The scan test

`apps/web/src/lib/clinical/correction-rule-scan.test.ts` fails if application code (`apps/web`, `apps/mobile`, `apps/console`, `supabase/functions`, shared packages) calls `.update`, `.delete` or `.upsert` after `.from("<table>")` for the four tables or `lab_result_items`, and for the watched tables (`screening_results`, `lab_result_documents`, `clinical_encounter_notes`, `medications`) unless the call is on a short allow list of workflow updates. Two existing paths replace a result document's file in place (`api/mobile/lab-result-replace`, `lib/lab-results/actions.ts`); they are listed as known debt, the count may only go down, and the right fix (a new document with `supersedes_document_id`) is S05b-c.

## 5. Proof

`packages/db/tests/s05b_record_integrity.sql` (registered in `ci.manifest`): blood verification (lab-backed gate opens, patient cannot reach lab_verified, column unwritable, someone else's report refused); the guard (service role cannot edit, delete or forge a chain; control that a note still updates; cascade still deletes; wearable erasure still works and the flag does not leak); the function (original kept, replacement linked, actor and reason stored and mirrored in `record_corrections`, second correction refused, untied clinician, other patient, patient `cancelled`, reviewed reading, allergies and lab values); range source (unlabelled range refused, named source needs a reference, lab_report needs a range, items stamped unsigned and signed, read paths carry the field); three sabotages (provenance trigger, supersession trigger, range constraint), each must flip.

## 6. S05b-c: read filters, guards, and the held-back grant (migration `20261013225700_s05b_c_read_filters_and_patient_guards.sql`)

Built, NOT applied, NOT yet proven on a real database (no Docker in the build session: the migration was run only against a stub schema to check syntax, the rewrite and the anchor patch; the SQL proof `packages/db/tests/s05b_c_read_filters_and_guards.sql` compiles but has not been executed against the full schema; Jest was not run, dependencies were not installed). The merge of a migration PR applies it automatically, so the replay job is the first real run.

* **RLS**: a RESTRICTIVE select policy `<table>_hide_superseded` (`correction_status is null`) on the four tables. Every user-session read (patient, clinician, console, `security_invoker` views) stops seeing a marked row; the replacement shows.
* **Definer readers (they ignore RLS)**: the live inventory found 77 definer functions that mention the tables. The migration rewrites every definer function in `public`/`private` that reads a table with `from|join public.<table>` onto `private.<table>_current` (owner-rights views, `correction_status is null`, revoked from every client role), except the writers that must see every row (`correct_clinical_value`, `delete_wearable_connection_data`, `execute_wearable_data_deletion`, `clear_vitals_validation_flag`, `record_triage_result`, `record_poc_measurements`, `confirm_lab_report_extraction`, `enforce_fhir_import_resource_attribution`, `capture_record_correction`). This covers risk scores, red-flag and adherence aggregates, the timeline and monitoring readers, prescription safety, the emergency card, record sharing, analytics. The two owner-rights views (`private.v_bp_cohort_90d`, `public.diabetes_quality_metrics`) are patched. Invoker functions are left alone (RLS already applies). The migration refuses to run if fewer than 30 functions are rewritten and ends in an assertion that no definer function reads a base table directly. The proof repeats that scan, so a definer function added later that reads the table directly fails CI until it reads the `_current` view (or is added to the listed writers).
* **Application code with the service role**: every lib reader that crons and background jobs can call with a service client now adds `.is("correction_status", null)` (heart rate, glucose, risk reassessment, BP control, health score, clinical rules window, CV risk, BMI, emergency dataset, patient clinical context, corporate activation funnel). A Jest scan (`correction-read-filter.test.ts`) walks all of `apps/web/src/lib`: a new reader of the four tables must filter or be listed as user-session only. Readers under `apps/web/src/app` and `apps/mobile` use the signed-in user's client (RLS).
* **Known limits of the rewrite** (review findings, accepted): the definer rewrite and its self-check share one regex, so an unqualified name under `set search_path = public`, dynamic SQL, and definer functions outside `public`/`private` are not seen (none exist live today; the live inventory was taken 2026-10-13); an invoker function run with the service role still sees marked rows (the five readers above cover the application side). A clinician-corrected reading that raised an alert is hidden from RLS-bound embeds on that alert; the alert is neither re-raised nor relinked (section 6 list below). The 9 listed writers are named in three places (loop, self-check, proof).
* **History**: `public.clinical_value_history(table, id)` (granted to authenticated) returns the whole chain through `supersedes_id`/`superseded_by_id` for the tied clinician (not a care coordinator) or the patient on her own record; anyone else gets the same refusal as a missing row. The patient copy omits staff identifier and flag columns. It does not write an access-audit row (the audited chart readers are the main route; add one if the history is shown to staff on a screen).
* **Review-column guard**: trigger `b_guard_vitals_review_columns` refuses a change to `validated_by`, `validated_at`, `logged_by_profile_id` unless the role running the statement is postgres/supabase_admin (the definer review paths). On insert a client session cannot pre-set `validated_by`, `validated_at` or `triage_event_id`; `logged_by_profile_id` stays settable on insert (device and acting-supporter paths).
* **Patient guard**: `correct_clinical_value` now refuses a patient correcting a reading that has a `clinician_alerts` row, an `emergency_events` row, a `triage_event_id` or a pending triage recheck (patched in place from the live definition). The clinician path is unchanged.

### The grant (item 1c) was NOT made
Reasons: the filters and guards are unexecuted; and the following remain, to be checked before the grant. (1) Run the proof and the whole replay on a real database. (2) The nine listed writers still read all rows (intended). (3) `care_plans.patient_condition_id` points at the original condition after a correction (not repointed). (4) Alerts raised for the original reading are not cancelled or linked. (5) Full-record exports built from user sessions will now omit marked rows; decide whether the data-subject export should include the history (use `clinical_value_history`). (6) `select *` views freeze the column list at creation: a column added later to a table must be added to its `_current` view. Then the grant, in its own migration after (1) passes:

```sql
revoke all on function public.correct_clinical_value(text, uuid, public.correction_status, text, jsonb) from public, anon;
grant execute on function public.correct_clinical_value(text, uuid, public.correction_status, text, jsonb) to authenticated;
-- assert: has_function_privilege('anon', ..., 'EXECUTE') is false
```
The S05b-a migration's self-check (authenticated must not execute) and this proof's section H both have to be flipped in that same change.

### Result documents (item 2) were NOT changed
The two in-place replace paths (`api/mobile/lab-result-replace`, `lib/lab-results/actions.ts`) stay as known debt (count unchanged). A real fix needs a new SECURITY DEFINER function, because a patient cannot set `supersedes_document_id` (the pointer is staff-only in `private.enforce_lab_result_document_update`) and an insert fires `handle_lab_result_document`, which opens a second clinician alert while the first alert keeps pointing at the old document (the reason the 2026-09-12 migration chose an in-place update). The function would have to insert the new row, stamp both pointers, and re-link or close the old alert in one transaction. That touches alert semantics, so it was not attempted blind. The replace is limited to the patient's own unreviewed upload (`reviewed_at is null`), i.e. before any clinician relied on the file.
