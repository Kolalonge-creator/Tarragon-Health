Written 2026-10-13 on a branch cut from `origin/main-dev` (4f1f6c968). Checked read-only against the live project `koiplnmbgnqnbywhpjlf` (latest live migration 20261013171417, nothing unrecognised). ## 1. Genotype and blood group: self_reported or lab_verified

Where they live: one table, `public.patient_blood_profile` (0 rows live). It already carried `provenance` (`lab_document` needs a report that belongs to this patient; `patient_attested` needs an attestation stamp), and `private.enforce_blood_profile_provenance` forces any non-staff caller to `patient_attested`. A later source-precedence rule (lab beats attestation) means a patient cannot overwrite a lab-backed value either; her attempt is recorded in `superseded_source_values`.

What was added: `patient_blood_profile.verification`, a **generated** column (`lab_verified` exactly when `provenance = 'lab_document'`, else `self_reported`). It cannot be written by anyone (428C9), so there is no second field to drift and no extra guard to get wrong; the guard is the existing trigger.

Shown as "Self-reported" and "Verified by a lab" (`BLOOD_VERIFICATION_LABEL` in `@tarragon/shared`): the clinician chart form, the emergency card (web and print), the patient's emergency-card page. The mobile emergency card does not show provenance today and was not changed.

## 2. One supersede-with-status rule

Rule: a clinical value that was relied on is never edited and never hard-deleted. A correction creates a new row that supersedes the old one; the old row is kept and marked with a status (`corrected`, `amended`, `entered_in_error`, or `cancelled` when a clinician already acted on it); actor and reason are stored.

### What was built (migration `20261013184219_s05b_supersede_not_edit_corrections.sql`)

* Enum `correction_status` (`corrected`, `amended`, `entered_in_error`, `cancelled`).
* Columns on the four tables: `supersedes_id`, `superseded_by_id` (no foreign key: a deferred one leaves pending trigger events that block later ALTER TABLE in the same transaction; only the function writes it), `correction_status`, `correction_reason`, `corrected_by`, `corrected_at`, plus a CHECK that a marked row has a status, a time and a reason of at least 5 characters.
* One guard trigger function, `private.enforce_clinical_value_supersession`, attached to all four. `SECURITY INVOKER` on purpose: it sees the role running the statement, so a client (including the service role) is refused, and only the correction function (a definer function owned by postgres) may write the chain columns. Value columns are frozen per table (the list is the trigger argument; device and connection ids are not, because their foreign keys null themselves when the device is removed). DELETE is refused unless a privileged function set the transaction-local flag `app.allow_clinical_value_delete`; only the patient's own "delete my wearable data" does (patched in the same migration, asserted, row count preserved). A cascade from a deleted profile is refused as well (the test-account purge disables triggers on the tables it touches).
* `public.correct_clinical_value(table, id, status, reason, replacement)`. **Not yet granted to `authenticated`** (service role only, so a server action acting for a verified user can call it): no read path hides superseded or `entered_in_error` rows yet, so exposing it to every signed-in user would double count a corrected value and keep showing a voided one. S05b-c adds the read filters and the grant in its own migration. Who may call it (checked inside, from `auth.uid()`): a clinician tied to the patient (`private.clinician_has_patient_access`) at a tier other than care coordinator, and the patient on entries she made herself (a manual reading, an allergy or condition with source `patient` that no clinician verified), never on a lab value, never to `cancelled`, never on a reading a clinician already reviewed. `entered_in_error` and `cancelled` take no replacement; `corrected` and `amended` require one, limited to a per-table allow list of value columns. A reading a clinician already validated cannot be `entered_in_error`; it is `cancelled`. The original is marked first, the replacement inserted second, in one transaction. A manual replacement keeps the original time through `client_recorded_at` while it is inside the offline backdating window (72 hours); older than that, the platform rule that manual readings cannot be backdated wins and the replacement is stamped with the correction time (the `supersedes_id` link keeps the original time visible).
* The replacement does not carry a coded or derived column the new values can invalidate (`allergen_concept_id`, `condition_concept_id`, `analyte_concept_id`, `abnormal_flag`: dropped, so uncoded or unflagged rather than wrong). A clinician's correction of an allergy or condition is stored with source `clinician`, and a staff-logged reading keeps the staff member's id, so the patient guard cannot supersede it.
* Known limits: the existing triggers fire on the replacement as on any new row, so a corrected dangerous reading raises its own alert; alerts raised for the original are not cancelled or linked (follow-up with the read filters). The `ON DELETE SET NULL` on `corrected_by` is the one chain change the guard lets through from outside the function (a profile removed later), checked in the proof.
* Before the `authenticated` grant (S05b-c): freeze or guard `validated_by`, `validated_at` and `logged_by_profile_id` against a patient clearing them (she has an update policy on her own readings; the patient guards in the function rely on those columns); the patient guard must also refuse a reading that raised an alert, escalation or triage event (it checks only `validated_by`, the staff id and the source today); the corrected replacement re-fires the red-flag, timeline and adherence triggers like any new reading; any new definer function that deletes these rows must set the flag explicitly and be reviewed; the scan test matches the literal `.from("table").update(` chain only, so a helper that takes the table name as a parameter is caught by the database trigger, not the scan.
* Not built (no UI calls the function yet): reads do not yet hide superseded or `entered_in_error` rows (S05b-c).

## 3. Range source on lab values

Tables holding a displayed range: `lab_analyte_readings` (`reference_range_*`), `lab_result_items` (`ref_low`/`ref_high`, written by `private.submit_lab_result` from the CMO-signed panel version), both 0 rows live. Migration `20261013184358_s05b_lab_range_source.sql`:

* `range_source` (`lab_report`, `guideline`, `cmo_signed_config`, `unspecified`, default `unspecified`) and `range_source_ref` on both tables.
* `lab_analyte_readings`: a stored range **must** declare its source (CHECK), `guideline` and `cmo_signed_config` need a named reference, `lab_report` needs a range. Nothing guesses: a writer that has a lab-supplied range says `lab_report`.
* `lab_result_items`: a trigger stamps `cmo_signed_config` with "lab panel X version N" when the panels are signed (exactly the predicate the release rules use, `private.lab_panels_signed()`), else `unspecified` with a reference saying it was a proposed, unsigned panel range (nobody sees it as a number except the reviewing clinician, who sees it labelled "Range not signed"). Sign-offs have no structured list of the panel versions they cover, so the label can only be as precise as the release gate; a structured coverage field is the better fix.
* `my_lab_results()`, `lab_result_for_review()` and `record_share_by_token()` are patched in place from their live definitions and return the source.
* Screens: patient released results, clinician result review, the shared-record page, the CMO lab-panel page (names the signed version or says the ranges are proposed), and the lab-partner entry box (says its reference is the Tarragon panel for entry only). The rule in code: `describeRangeWithSource` shows the numbers only for a known source and prints "Range not specified" otherwise; `rangeMayBeShownAsClinical('optimal')` is false. A qualitative analyte (no numeric range) prints nothing in the range cell.
* Not covered: `screening_results.interpretation` carries a `reference_range` string (from `fallback-interpretation.ts`, with the guideline in code comments) but no screen renders it today.

A staff correction of a device or wearable reading keeps the original `source` and device ids (the provenance of the instrument) and records the staff member in `logged_by_profile_id`; the lab-partner entry screen states that the patient sees the Tarragon panel range, not the range printed on the lab's own report (which is not stored).

Accepted limits of the range stamp (review findings, to revisit with a structured sign-off coverage field): the stored label is written once when the item is inserted (the table is append only); the two lab-result read paths resolve it at read time (a result entered before the signature reads as signed once the panels are signed; before that the reviewer sees the typed marker `proposed_unsigned`, never a stored value); the frozen-column lists are an explicit blacklist (a column added later must be added to the trigger argument; the self-check proves every listed column exists); a corrected lab value is stored without `abnormal_flag` until a clinician flags it again.

## 6. S05b-c: read filters, guards, and the held-back grant (migration `20261013235037_s05b_c_read_filters_and_patient_guards.sql`)

Built, NOT applied, NOT yet proven on a real database (no Docker in the build session: the migration was run only against a stub schema to check syntax, the rewrite and the anchor patch; the SQL proof `packages/db/tests/s05b_c_read_filters_and_guards.sql` compiles but has not been executed against the full schema; Jest was not run, dependencies were not installed). The merge of a migration PR applies it automatically, so the replay job is the first real run.

* **RLS**: a RESTRICTIVE select policy `<table>_hide_superseded` (`correction_status is null`) on the four tables. Every user-session read (patient, clinician, console, `security_invoker` views) stops seeing a marked row; the replacement shows.
* **Definer readers (they ignore RLS)**: the live inventory found 77 definer functions that mention the tables. The migration rewrites every definer function in `public`/`private` that reads a table with `from|join public.<table>` onto `private.<table>_current` (owner-rights views, `correction_status is null`, revoked from every client role), except the writers that must see every row (`correct_clinical_value`, `delete_wearable_connection_data`, `execute_wearable_data_deletion`, `clear_vitals_validation_flag`, `record_triage_result`, `record_poc_measurements`, `confirm_lab_report_extraction`, `enforce_fhir_import_resource_attribution`, `capture_record_correction`). This covers risk scores, red-flag and adherence aggregates, the timeline and monitoring readers, prescription safety, the emergency card, record sharing, analytics. The two owner-rights views (`private.v_bp_cohort_90d`, `public.diabetes_quality_metrics`) are patched. Invoker functions are left alone (RLS already applies). The migration refuses to run if fewer than 30 functions are rewritten and ends in an assertion that no definer function reads a base table directly. The proof repeats that scan, so a definer function added later that reads the table directly fails CI until it reads the `_current` view (or is added to the listed writers).
* **Application code with the service role**: every lib reader that crons and background jobs can call with a service client now adds `.is("correction_status", null)` (heart rate, glucose, risk reassessment, BP control, health score, clinical rules window, CV risk, BMI, emergency dataset, patient clinical context, corporate activation funnel). A Jest scan (`correction-read-filter.test.ts`) walks all of `apps/web/src/lib`: a new reader of the four tables must filter or be listed as user-session only. Readers under `apps/web/src/app` and `apps/mobile` use the signed-in user's client (RLS).
* **Known limits of the rewrite** (review findings, accepted): the definer rewrite and its self-check share one regex, so an unqualified name under `set search_path = public`, dynamic SQL, and definer functions outside `public`/`private` are not seen (none exist live today; the live inventory was taken 2026-10-13); an invoker function run with the service role still sees marked rows (the five readers above cover the application side). A clinician-corrected reading that raised an alert is hidden from RLS-bound embeds on that alert; the alert is neither re-raised nor relinked (section 6 list below). The 14 exempt functions (9 writers, 5 alert-linking readers) are named in three places (loop, self-check, proof).
* **History**: `public.clinical_value_history(table, id)` (granted to authenticated) returns the whole chain through `supersedes_id`/`superseded_by_id` for the tied clinician (not a care coordinator) or the patient on her own record; anyone else gets the same refusal as a missing row. The patient copy omits staff identifier and flag columns. It does not write an access-audit row (the audited chart readers are the main route; add one if the history is shown to staff on a screen).
* **Review-column guard**: trigger `b_guard_vitals_review_columns` refuses a change to `validated_by`, `validated_at`, `logged_by_profile_id` unless the role running the statement is postgres/supabase_admin (the definer review paths). On insert a client session cannot pre-set `validated_by`, `validated_at` or `triage_event_id`; `logged_by_profile_id` stays settable on insert (device and acting-supporter paths).
* **Patient guard**: `correct_clinical_value` now refuses a patient correcting a reading that has a `clinician_alerts` row, an `emergency_events` row, a `triage_event_id` or a pending triage recheck (patched in place from the live definition). The clinician path is unchanged.

Open risks recorded by review (not fixed here): ~~a patient voiding her own unverified allergy removes it from prescription safety and the emergency card at once~~ (decided and built in S05b-d, section 7: her request waits for a clinician); a patient can still correct a reading in the short window before the asynchronous triage links it (consider a minimum age or a synchronous link before the grant); the history function uses the same tie test as the correction function, not the S39 audited gate, and writes no access row; the rewrite finds readers by text, so a definer function outside the patterns (comma join, unqualified name, `BEGIN ATOMIC`) is neither rewritten nor detected; the migration is not re-runnable on its own (use repair-mark, not re-apply).

## 7. S05b-d: the allergy rule and the grant (migration `20261014162552_s05b_d_patient_allergy_correction_requests_and_grant.sql`)

**Founder decision (2026-10-14, `docs/DECISIONS.md`)**: a patient's own allergy correction or void is only a request. The original stays active in prescription safety, the emergency card and every reader until a tied clinician (not a care coordinator) confirms. A clinician-tied user's correction is immediate, as before. Nothing else changes: other tables keep their rules (a patient still corrects her own manual reading at once; the vitals guards are untouched).

* **Mechanism**: `public.patient_allergy_correction_requests` (one pending request per allergy, partial unique index) and the append-only `public.patient_allergy_correction_events` (requested, confirmed, rejected, void, with actor and time). Clients can only read: the patient her own, a tied non-coordinator clinician her patients' (`private.is_correcting_clinician`, the same test the correction function uses). Every write is by a function; a guard trigger refuses any other writer and any edit of a decided request. In `correct_clinical_value` the patient branch on `patient_allergies` (patched in place from the live definition, one anchor, inserted after the "already superseded" check so every earlier patient guard still runs) calls `private.request_patient_allergy_correction`, which validates the replacement now (allowed columns, real values) and returns `status: pending`.
* **Confirm** (`public.confirm_patient_allergy_correction`): the clinician's session calls `correct_clinical_value` itself, so the original is marked and the replacement inserted by the one supersede path, atomically, stored as a clinician entry. A trigger on the allergy (`z_void_pending_allergy_requests`) closes any still-pending request as `void` (audit row by `system`) when the allergy is superseded another way, so a request is never left pending for good; a flag keeps it from closing the request being confirmed. A request that would rename the allergy to a name another current allergy already has is refused when it is made. **Reject** (`public.reject_patient_allergy_correction`): the original is not touched; one in-app notice (`record_change_not_confirmed`, `non_clinical`) goes to the patient with no allergen, no value and no clinician note in it; `describe-in-app.ts` renders it, no SMS or email text exists (INV-07, INV-08). A missing id and a refused caller get the same answer.
* **Grant checklist, item by item**: (1) both S05b proofs and the S05b-d proof pass on a local full replay (`supabase db reset`), then again after the grant; (2) the nine writers that read every row are intended; (3) `care_plans.patient_condition_id`: nothing reads it (checked in every database function and all app code), the foreign key stays valid; not repointed because `care_plans` carries signed-change and versioning triggers and nothing needs it; (4) alerts for an original reading: no function joins an alert to its reading (all only test that the id is set), the alert stays open for the clinician who corrected the reading to resolve, and a patient cannot correct a reading that has an alert, emergency event or triage event; (5) the data export now carries the patient's superseded values (`public.my_corrected_record_entries`, caller's own rows only, staff identifiers removed; `correctedEntries` in `get-full-patient-record.ts`); (6) the migration ends in an assertion that each `_current` view has exactly its table's columns today; the standing check for a column added later is the registered proof (section F), which fails CI until the view is rebuilt (a migration's own check runs once, at its place in the replay).
* **What a client can read**: column grants only. The patient and the tied clinician read the safe columns of the request and audit tables (not `decided_by`, `decision_note`, the audit `actor_id` or `note`), so a clinician's note and identity never reach the API (INV-07). `decided_by` has no foreign key (its SET NULL update would hit the decided-request guard when a profile is removed). `correct_clinical_value` now calls `private.is_correcting_clinician` instead of its own copy of the test. The notice template is registered in `notification_templates` and `notification_template_locales`; the request table is registered in `minor_dependant_table_policy` (guarded) and in `data_registry` with `in_export = false` (the registry export dumps whole rows and would carry the clinician's note and identity), and her own requests, safe columns only, appear with her superseded values in the patient's own export (`my_corrected_record_entries`, which drops staff identifiers by a column-name pattern, `private.is_staff_identifier_column`, so a staff id column added later is excluded without a list; the proof asserts it). The export route degrades with `correctedEntriesAvailable: false` while the function does not exist yet. A name collision that appears after a request was made is refused at confirmation with a clear message.
* **The grant**: `revoke ... from public, anon; grant execute ... to authenticated` is the last statement before the self-check, which asserts authenticated can, anon cannot.
* **Screens and notices (built in S05b-e, section 8)**: the clinician queue, the patient status line and withdraw action, the arrival notice to the tied clinician and the confirmation notice to the patient all exist now. This bullet read "not built" when S05b-d shipped. The patient can take a pending request back (`public.withdraw_patient_allergy_correction`, status `withdrawn`). The same exposure exists for a CONDITION a patient entered herself: `patient_conditions` is not covered by the allergy rule (the founder decision named allergies only), so a patient voiding such a condition still takes effect at once: decide whether the rule should extend to conditions.
* **Still accepted from the S05b-c review**: a patient can correct a reading in the short window before the asynchronous triage links its event (the synchronous red-flag triggers and the alert guard cover the dangerous cases); the history function uses the tie test, not the audited gate, and writes no access row; the definer rewrite finds readers by text.

## 8. S05b-e: the review screen, the notices and the resubmit limit (migration `20261014213843_s05b_e_allergy_request_notices_and_resubmit_limit.sql`)

**What was built**
* **Clinician queue** at `/clinician/record-changes` in `apps/web` (not `apps/console`: `CONSOLE_AREAS` holds only `/ngo`, and `/clinician` has not been extracted). It reads `patient_allergy_correction_requests` as the signed-in clinician, so row level security (`private.is_correcting_clinician`) decides which requests appear; no service role anywhere. The allergy as currently recorded is NOT readable by staff directly (S05c closed every staff SELECT on `patient_allergies`; an embedded read returned null for every row), so it comes from the audited chart reader `read_patient_chart_audited(patient, ['allergies'], reason)`, once per distinct patient, which checks the tie and the patient's access categories and writes the access to the audit trail (INV-10). If that read is refused or fails the screen says "could not be loaded" and warns the doctor to check the record, rather than saying the entry is gone. Each row shows the patient, the allergy as recorded, what she asks (remove, or the replacement) and when. "Open request" shows the current record and the request side by side, with her reason. Confirm calls `confirm_patient_allergy_correction`; "Leave the record as it was" calls `reject_patient_allergy_correction` with an optional note that is internal (the patient never sees it). Both are server actions (`actions.ts`) with Zod validation; the database's own refusal is shown to the clinician, never swallowed. A care coordinator is refused in the action before the database is called (`isClinicalTier`), the page shows them no queue, and `proxy.ts` keeps `/clinician/record-changes` off the coordinator allow-list. Nothing on the screen claims a reviewer: there is no "reviewed by" text, so there is nothing to gate.
* **Sidebar count and search**: a "Record changes" item in the clinician menu with `recordChangeRequestsWaiting` (RLS limits the count to requests that clinician may decide; a coordinator always sees 0), registered in the launch worklist (follow-up bucket, href, label), plus keywords in `lib/admin-search.ts` so the Chief Medical Officer search (built from the nav sections) finds it by "record changes", "allergy request", "entered by mistake" or "void".
* **Patient side**: on her allergy list an allergy with a waiting request shows "Change requested, waiting for your care team" and a "Withdraw request" button (`withdraw_patient_allergy_correction`; a failure is shown). Only she can see her request (a caregiver's read returns none, so the line does not show for a caregiver).
* **Notices** (all in-app only, `content_class = non_clinical`, no allergen and no clinical word, INV-07 and INV-08): a new request sends one `record_change_request_waiting` notice to each tied clinician who is not a care coordinator (`private.allergy_request_recipients`: active non-coordinator staff on the patient's care team, with an open escalation assigned to them, or responsible or backup on an open alert); a confirmation sends the patient one `record_change_confirmed` notice (trigger on the status change; the rejection notice already existed). Both notices are written inside a guarded block: if a notice cannot be written the database logs a warning and the request, or the clinician's confirmation, still stands (a notice must never undo either). The notice wording says "their record", not a gendered pronoun.
* **Resubmit limit**: a before-insert trigger on the request table refuses a 4th request for the same allergy inside a rolling 7 days, whatever the outcome of the earlier ones except `void` (so withdraw and ask again cannot be used to flood the queue, but a request the system closed because the entry was changed another way does not use up her three). The limit is per allergy, not per patient. The refusal text is calm: "You have asked about this entry a few times this week. Please message your care team about it instead, and they will help." A per-allergy advisory lock keeps two quick taps from both slipping under the limit.

**Known limits**
* `private.clinician_has_patient_access` reads `auth.uid()` and cannot be asked about another person, so the arrival notice uses the care team, escalation and alert ties only. A clinician tied only through a booked visit, a clinical task, a page or a referral still sees the request in the queue and in the sidebar count, but is not sent a notice. If a patient has no one in those three ties, no one is notified and the request waits for whoever the real tie admits.
* There is still no patient screen that CREATES a request (the allergy list has no edit or remove control): the request comes from `correct_clinical_value`, called by the app or the API. The status line and withdraw action are ready for when that control is built. A condition a patient entered herself is unchanged (the earlier open question).

### Result documents (item 2) were NOT changed
The two in-place replace paths (`api/mobile/lab-result-replace`, `lib/lab-results/actions.ts`) stay as known debt (count unchanged). A real fix needs a new SECURITY DEFINER function, because a patient cannot set `supersedes_document_id` (the pointer is staff-only in `private.enforce_lab_result_document_update`) and an insert fires `handle_lab_result_document`, which opens a second clinician alert while the first alert keeps pointing at the old document (the reason the 2026-09-12 migration chose an in-place update).
