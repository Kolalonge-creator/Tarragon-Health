## 2. Encrypted store (D1)

- SQLCipher through `expo-sqlite`. Key: 32 random bytes from `expo-crypto`, hex, kept only in `expo-secure-store` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY` (not in an iCloud backup, not restored to another phone). Read back after writing; never logged, never sent, never in AsyncStorage.
- After `PRAGMA key` the code asks `PRAGMA cipher_version`. A plain SQLite build ignores `PRAGMA key` silently, so without this check the app would claim encryption it does not have. No answer means "not encrypted": plain file, patient told (`not_encrypted` notice). Same if the keystore fails.
- File name carries a generation: `tarragon-secure-<n>.db`.
- **Migration** from the plain file (once): drop and recreate each table in the encrypted file, copy in pages of 200 by rowid, then compare per table row count and an order-sensitive checksum (FNV-1a over typed values, blobs included). Only on a full match is `@tarragon/legacy-store/v1` set to `verified`, the old file deleted, the state set to `done`. If the delete fails the state stays `verified` and the next start only retries the delete; it never copies again over a live encrypted store.
- **Escape hatch.** Any mismatch or error: the old plain file is kept and used as the store for this run (so the outbox keeps flushing), a `migration_held` notice with a code is shown, and the next start retries a fresh copy. The outbox is never silently dropped.
- **Key lost** (keystore reset, restored backup): the encrypted file will not open with the new key. It is left untouched, generation n+1 starts, a `key_lost` notice with a support code is shown once. The old rows are unreadable by design; the notice says so and asks the patient to log again and tell their care team. The code identifies the quarantined file locally; nothing is sent to the server for it.
- Legacy `drafts` rows (no account) are copied with the rest and then dropped when the drafts table is set up: nobody can safely be shown them. They hold only typed form text.
- The copy reads each table by rowid (a WITHOUT ROWID table by primary key), in pages of 25, taking the source checksum in the same pass as the copy. A copy that stays held is escalated: after three starts the notice becomes a request to contact support (`migration_stuck`), still as one notice, not a stack.

## 3. Drafts (D2)

`drafts_v2(owner_user_id, key, value, updated_at)`. Every read and write is scoped to the signed-in account; signed out means nothing is saved or shown. Sign-out and forced sign-out no longer delete drafts. Another account on the phone cannot read them.

## 4. Remote wipe and key lease (D3, refined for urgent entries)

**This refines D3 for urgent (danger-flagged) entries. Flagged for the founder:** D3 as written allows a lease that runs out to wipe unsent entries. After review the rule is gentler for urgent rows: a lapsed lease NEVER wipes while any urgent entry is unsent, for any account on the phone (`held`; the last upload attempt still runs on every check). Only an explicit lost-phone report wipes urgent rows, after one last attempt. If the founder wants the original D3 behaviour back it is one condition in `wipeForExpiredLease` (`device-lease.ts`).

- Server (`20261013181713_s06x_offline_trust.sql`): `offline_device_leases` (one row per account and phone; `retired_at`, `wipe_reason`, counts), RPCs `offline_device_checkin`, `request_offline_device_wipe` (the patient for their own phone, or a same-organisation admin), `confirm_offline_device_wipe`. `offline_sync_config.device_lease_days` (30, PROPOSED, mirrored in `offline.trust`).
- **Server clock decides.** Check-in returns what the server held BEFORE renewing (`prev_lease_expires_at`) and `server_now`. The phone treats a lease as lapsed online only when the server's own previous value is before the server's own time; a phone whose clock jumped forward is renewed, not wiped. Offline, the phone's own record only starts a grace period (`lease_grace_hours`, 24, PROPOSED); the wipe waits until that has run, a clock that went backwards never counts, and reaching the server at any point settles it on the server's clock. A 5xx never starts or advances the grace period. An over-cap answer (53400) is handled like an outage: the phone's own lease record still applies, it is never skipped.
- **Phone cap.** An account may have 20 live phones. A check-in first retires the account's phones silent for twice the lease (`retired_at`), and only live ones count, so old rows never fill the cap for good. A retired phone that comes back is let in again when there is room.
- **Confirmation guard.** `confirm_offline_device_wipe` is accepted only for a phone that was reported lost (`revoked_at`), or whose lease the SERVER sees as lapsed, or (`shared_phone`) for a sibling account on a phone that was wiped; the last is recorded as phone-reported and unverified. Counts (unsent, urgent) are capped at 100000. Counts only, never content.
- **Phone** (`device-lease.ts`): checks in after every flush (foreground at most every 10 minutes, and in the background task). On a wipe: one last `flushOutbox()`; count unsent rows PER ACCOUNT (and urgent ones); write each account's own notice and pending confirmation first (`ownerUserId`; an account sees only its own notice); remove the store (every generation), the plain file, the key, and every AsyncStorage entry except notices, the data meter and the lease records; reset the device id of EVERY account known on the phone (listed in `@tarragon/device-accounts/v1`, because the keystore cannot list keys, so it works with nobody signed in); send the confirmation of the signed-in account BEFORE signing out (the server needs the session), keep the others until their own account signs in (90 days at most); sign the phone out. A failed file delete aborts the wipe and leaves the revoked flag in place, so it retries.
- Never silent: notices are written before the files are removed and stay until dismissed.
- **Risks recorded, not solved:** (a) offline, a forward clock jump that is never corrected and lasts more than the grace period still wipes (after the last attempt, and never with an urgent entry unsent). (b) A phone that never reached the server has no lease and is never lease-wiped. (c) A patient-facing "my phones" screen to file the lost-phone report is not built; `reportPhoneLost` and `listMyPhones` exist in `device-lease.ts`, and an admin can call the RPC. (d) Drafts and the outbox need `supabase.auth.getSession()` to know the account; after a long offline spell with an expired token a draft is not saved (the outbox has the same dependency).

### What is encrypted, and what is not

Encrypted at rest (SQLCipher store): the outbox, the read mirror (vitals, symptoms, doses, medications, tasks), drafts, the written-question queue with its photos, and (since the review) the obstetric status (pregnancy and postpartum).

**Still plaintext in AsyncStorage** (removed by the remote wipe, NOT encrypted at rest): `offline-queue.ts` (BLE device readings and health-sample pages), `dose-reminders.ts`, `bp-target.ts`, `triage-device.ts`, `catch-up.ts`, `reminder-prefs.ts`, `health-connect-consent.ts`, and the offline sync configuration. Nothing in the app or the notices should be read as "everything on this phone is encrypted". Moving the first (`offline-queue.ts`) into the store is the next piece of work.

### iOS build

`apps/mobile/ios` is committed prebuild output, so the expo-sqlite plugin does not run for it. The flag is set by hand in `ios/Podfile.properties.json` (`expo.sqlite.useSQLCipher`), and `ios/Podfile.lock` plus the project file were regenerated with `LANG=en_US.UTF-8 pod install` on the same pnpm tree (the lock now carries the NetInfo pod and a changed `ExpoSQLite` checksum; its many path lines differ only because pnpm's store paths changed). A jest test (`sqlcipher-config.test.ts`) fails if the flag is missing from `app.json` or `Podfile.properties.json`, and a build without SQLCipher shows the `not_encrypted` notice at run time (`PRAGMA cipher_version` is checked). **Before the iOS build:** run `pod install` again in `apps/mobile/ios` if `pnpm install` changed anything, and build with EAS (not the dev client).

## 5. Honest sync

- `@react-native-community/netinfo` plus `reachability.ts`: when the radio goes from not connected to connected and entries wait, one HEAD (no body) to our own REST root decides whether to flush. At most once a minute (`offline.trust.probe_min_interval_seconds`), none with an empty outbox, retried each minute while a probe fails. NetInfo is imported lazily so a binary without it syncs as before.
- The foreground flush and the one-minute loop in `App.tsx`, and the background task, stay as the fallback. The watcher only adds a trigger.
- `offline_sync_rejections` (id, organisation, account, patient, kind, reason class, HTTP status, support code, client id, created_at). One row per entry (`unique(account_id, client_id)`), written best effort on the first rejection and retried at the next flush if it could not be sent (`outbox.rejection_reported` column). No health value, no server message, no JSON column. Patient inserts and reads own rows; support reads through `read_offline_sync_rejections`, admin of the same organisation only, every read written to `audit_log`.
- Post-pull count check: for each table, a HEAD count of server rows for the patient between the window start and the cursor, against the local count. Fewer local rows means drift: the cursor is dropped and the whole window re-read once; still short is recorded in sync diagnostics, not looped. The window start is the later of the first-pull horizon and the retention horizon, so the housekeeping purge never counts as drift.
- Data meter (`data-usage.ts`): per-month estimate of bytes the sync code sent and received, shown in the sync banner.

## 6. Not measured

Cold start under 3 s, installed size under 40 MB, memory, logging speed and the one-minute reconnect flush are NOT measured: there is no device. `docs/S06X_DEVICE_CHECKLIST.md` is the run sheet. SQLCipher itself, the keychain flags and NetInfo have never run on a device; the Jest SQLite stand-in models key behaviour only.
