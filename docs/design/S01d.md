## 3. Shared layers and how each is affected

**Auth and session.** `lib/supabase/{server,client,middleware}.ts` create `@supabase/ssr` clients with **no cookie `domain`** option, so the session cookie is host-only. A `console.` host will therefore start with **no session**: every staff member logs in again, once, on the new host, unless we set a parent-domain cookie. `proxy.ts` runs `updateSession()` on every request and holds four security-relevant gates: the MFA step-up (`aal2`) gate, the supporter default-deny gate, the role-area gate (`pathMatchesRole`), and the delegated-permission door for `/admin` and `/finance`. All four must exist unchanged on both hosts, and the console needs its own `proxy.ts`. `login/*`, `auth/*` and `signOut` (`app/auth/actions.ts`) are used by staff and patients; the console needs its own login surface or a redirect to one.

**Hostname routing.** `lib/marketing/host.ts` treats `app.*` as platform and everything else as marketing. Role home paths live in `lib/auth/roles.ts` (`ROLE_HOME_PATH`), shared by `proxy.ts`, the login redirect and the app shell. After the split, a staff role's "home" is a different host, not a path. Cross-host redirects must use an absolute URL built from an env var.

**Layout and shell.** `(dashboard)/layout.tsx` is a single shell for every role: it reads `profiles`, `clinical_staff`, banners (MFA nudge, consent nudge, pending jobs, offline, AI governance signoff), builds nav from `lib/navigation.ts`, and imports `updateUiLanguage` from `patient/ui-language-actions`. `components/shell` has 3 staff-only, 11 patient-only and 3 unreferenced files. The console needs its own layout and nav; nav must be split (`lib/navigation.ts` is patient-only by the graph but also carries staff sections and two navigation tests).

**Server actions.** 72 files in the staff areas declare `"use server"`. Server action IDs are bound to the deployment that built them; moving an area moves its actions with it, and any patient-side caller of a staff action (the two inversions above) breaks at build time, which is the safe failure.

**API routes** (`app/api/**`, 81 handlers): **none is a staff UI route.** They are patient (`patient/*`, `mobile/*`), public (`broadcasts/*`, `track`, `reputation`, `status`, `heartbeat`), partner-facing (`v1/*`, `protocol-api/*`, `integrations/*`, `wearables/*`), internal (`internal/notifications/*`) or scheduled (`cron/*`, 19 jobs in `vercel.json`). The crons are platform jobs (Paystack reconciliation, refunds, fraud sweep, embeddings), not staff features, and several run against Vercel's daily-cron limit. **Recommendation: all `app/api/**` and `vercel.json` stay in `apps/web`.** The console would call the database directly with the user's own session, as the staff pages do today. Confirm per route when each area moves (some staff pages may `fetch` an `/api` route; grep at move time).

**Env vars.** 17 files read `APP_BASE_URL` / `NEXT_PUBLIC_APP_URL` / `NEXT_PUBLIC_SITE_URL`; the console needs its own and `apps/web` needs the console's base URL to build redirects. Staff areas use the same Supabase URL and anon key. Paystack/Zoom/Twilio/Upstash secrets are used by shared server code; a console project should receive only what its own code paths need (least privilege), which is another reason not to co-locate crons.

**Security headers.** `apps/web/next.config.ts` sets an enforcing CSP tuned for the whole app: `script-src 'self' 'unsafe-inline'`, `frame-ancestors 'self'`, `frame-src` allowing the Supabase origin (staff pages embed signed Storage URLs in iframes: `ecg-report-extraction-panel`, `lab-report-extraction-panel`) and YouTube (marketing only), and browser Sentry via `NEXT_PUBLIC_SENTRY_DSN`. The console CSP should drop YouTube, set `frame-ancestors 'none'`, keep the Supabase frame origin, and add `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy`, `Permissions-Policy`. `'unsafe-inline'` cannot go without nonces (documented in the current file). Sentry: `lib/sentry/scrub-pii.ts` and `run-best-effort.ts` are needed by both apps and go into a shared package, not a copy.

**Zoom / video host pages, masked calls, partner portals.**
- `clinician/video-visit/[consultationId]` runs the consultation (Zoom join, `add-medication-form`, notes). It uses `lib/zoom` and `lib/masked-calls` (shared with the patient waiting room). It belongs in the console but pulls a shared Zoom client; move `lib/zoom` to a package with `server-only` intact.
- `lab-partner`, `pharmacist`, `lab-liaison`, `provider-org`, `payer`, `ngo` are external-organisation portals. Their users are not Tarragon staff and may need a different domain trust posture; the spec puts `partner_lab` and `partner_pharmacy` in the console's partner area, so they move, but they are the strongest argument for a strict per-role area gate and are last in order.
- `verify-report` and `emergency/[token]` are anonymous and stay in `apps/web`.

**Links that point at staff URLs** and must keep redirecting for a long time: `supabase/functions/send-pending-notifications` (email and push deep links), `packages/shared/src/ml-client.ts`, and `lib/queries/{governed-config-signoff,signoff-queue,launch-worklist,pending-ai-governance-signoff}.ts` (build `/clinician/...` and `/admin/...` hrefs); `notifications` rows already written to the database hold `app.` paths; the mobile app links staff paths only through its WebView bridge. The old paths in `apps/web` become 308 redirects to the console host (with the query string kept) for every moved prefix. That includes `/clinician/*` reachable by `care_coordinator` and delegated `/admin` and `/finance` members.

**Tests and CI.** `apps/web/e2e/` (`auth`, `clinician`, `patient` specs and an abnormal-screening escalation test), `apps/web/e2e-browser/` (b2c signup, employer eligibility), `proxy.test.ts`, `lib/navigation-*.test.ts`, and per-area component tests (`*.test.tsx`, `*.a11y.test.tsx`). ## 4. Decisions that shape everything (need the founder)

1. **Cookie/session scope.** Options: (a) separate host-only sessions (recommended default: least blast radius, a staff token never travels to marketing/patient host, but every staff member logs in once again at cutover); (b) a shared parent-domain cookie (no re-login, but every subdomain and any XSS on marketing or patient pages could reach a staff session, and patient and staff share cookie lifetime). Because the invariants treat staff clinical access as the most sensitive surface, the recommendation is (a), with a one-time, announced re-login.
2. **Domain name.** `console.tarragonhealth.ng` versus something on the same registrable domain. Creating a Vercel project and DNS is a production action and needs the founder's explicit go-ahead.
3. **How to share the 279 shared files.** There is no way to satisfy "move to `packages/`, no copy-paste" for all of them in one session. Options: (a) extract in tiers, only what a given area needs, into new packages (`@tarragon/auth`, `@tarragon/supabase`, `@tarragon/staff-ui`, `@tarragon/queries` …) as each area moves, smallest area first, so each PR is reviewable; (b) do one big shared-package extraction first. Recommendation (a).
4. **How far S01d goes this session.** Full migration of all 12 areas (about 108k LOC, over 70 server-action files, 279 shared files) is many sessions of work, not one. Recommendation: this session delivers the map, the empty-but-deployable `apps/console` shell, the shared auth/session/headers packages, and the **smallest area** end to end, `lab-liaison` (2 files), then stops. Follow-up sessions move the rest in the order below.
5. **Do not touch RLS or role checks.** Nothing here changes a policy or a role function. Staff read scope (OQ-02, OQ-03) is untouched and out of scope; the clinical-table reads listed for `clinician` above are what that later work will convert to SECURITY DEFINER read functions.

## 6. Risks specific to this split

- **Silent auth failure on the new host.** A missing `NEXT_PUBLIC_SUPABASE_*` var or a cookie domain mismatch would look like "everyone is logged out". Add a startup assertion and a Playwright test that a fresh staff login lands on the right home.
- **Role gate drift.** `proxy.ts` and `ROLE_HOME_PATH` live in shared code today; if the console gets a copy they will diverge. `lib/auth/roles.ts` moves to a package once, used by both.
- **Redirect loops.** `apps/web` redirects `/clinician/*` to the console, the console redirects unauthenticated users to a login that is on a third host. Decide where staff log in (recommended: the console has its own `/login`, and the platform `/login` redirects staff-role users there after auth) before building step 1.
- **Vercel limits.** A second project doubles preview deployments toward the free-plan daily cap (see memory: Vercel daily deployment cap). Do not add crons to the console project.
- **Server Actions bodySizeLimit** and `transpilePackages` from `next.config.ts` must be replicated deliberately in the console, not copied.

## 9. Session and cookie scope (final: S01d-1)

- Supabase's `@supabase/ssr` sets no `domain` on its auth cookie, so cookies are host-only. `console.` and `app.` therefore never share a login and a patient token can never be presented to the console. This was proven, not assumed: `sign-in.spec.ts` asserts no auth cookie has a leading-dot domain.
- The console refuses to keep a session for any role that has no console area. A correct password for a patient or for a staff role whose area still lives in `apps/web` is signed out again on that host and shown a plain message. The account-role rule is unchanged: the console never adds a role, and authority is still `clinical_staff.doctor_tier` enforced in the database.
- Each area's cutover means one re-login on the console for that area's staff. Announce it. No existing session is invalidated on the main app.
- **Local development trap:** browsers scope cookies by host, not port, so `localhost:3000` and `localhost:3001` SHARE cookies. Use `app.localhost:3000` and `console.localhost:3001` (Chrome resolves `*.localhost` to loopback) when testing isolation by hand.

## 10. Per-area extraction recipe (use for every remaining area)

1. Re-run the import graph for that area (section 2's method) and list every non-route file it reaches.
2. For each shared file, move it into the package it belongs to (`ui`, `auth`, `staff-core`, or a new one), leave a one-line shim in `apps/web`, and repoint any `jest.mock` of the old path to the package specifier (mocks of a shim do not reach code that now lives in the package: two web tests failed this way and were fixed).
3. `git mv` the routes into `apps/console/src/app/(console)/<area>`, rewrite `@/` imports to package specifiers, add the area to `CONSOLE_AREAS` in `packages/auth/src/console-areas.ts` (this is what makes both apps agree), and add a console Playwright flow.
4. If the area has live users, follow OQ-36's four-step rollout and do NOT delete the web routes in the same deploy as the console going live.
5. Run typecheck, lint, tests and both builds; then `/code-review high` naming auth/session and silent-failure classes.
