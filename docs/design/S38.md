# S38 Design: outcome snapshots, analytics schema, the 90-day BP control report

Spec 4.10, Module 22 (22.1, 22.2, 22.7, 22.8), safety case 22. Depends on S26 (entitlements, branched from `s26/entitlements-care-packs-refunds` while PR 955 is open) and S12. Invariants touched: INV-07, INV-10, INV-13, INV-14, INV-15, INV-16. Research: `docs/research/S38.md`.

## 1. What exists (extend, do not rebuild)
- **No `outcome_snapshots` and no `pathway_enrolments` table.** S12 notes the server treats every patient as self-guided; care packs arrived with S25/S26.
- **Org-level outcomes already exist** (July 2026): `outcome_measure_specs` (versioned measure definitions with numerator, denominator, exclusions, limitations, `min_denominator`, a `bp_control` v1 for payers: most recent reading in a period under 140/90), `outcome_reports`, `outcomes_contracts`, `lpe_programme_outcomes`. Those answer "how is this insurer's covered population doing in a period". S38 answers a different question: "how is each person doing at days 0, 30, 90 and 180 after they joined". The two BP control definitions are both kept and named apart (OQ-230). S38 adds `bp_control_90d` as a new row in `outcome_measure_specs` so the definition is versioned and published the same way.
- **Data it reads**: `observations` (type `bp`, systolic, diastolic, `measured_at`, `created_at`), `patient_bp_targets` (home targets, S07 and earlier), `private.weekly_adherence(patient, now)` (S08: doses taken or late over doses due, with a minimum dose count, `medicine_config` versioned), `patient_memberships` (S22b, S25) and `entitlements` kind `care_pack` (S25/S26), `profiles.is_test`.
- **Analytics schema**: `analytics.rpc_snapshots` only (the warehouse-lite layer, 2026-09-18). S38 adds de-identified outcome views beside it.
- **Event bus**: S10; `outcome.snapshot_computed` is new.

## 2. Decisions taken in this build
1. **Day 0 is the date a person joined** (earliest `patient_memberships` start, or `care_pack` entitlement start, test or not). Stored on each snapshot as `anchor_date`, so a later change never rewrites history. Free users have no snapshots (no pathway, no anchor).
2. **Windows**: day 0 uses the first 7 days (days 0 to 6) because nobody has a reading before they join; days 30, 90 and 180 use the 7 days ending on that day. A snapshot is computed once the window closed plus a grace period for offline-synced readings (PROPOSED 3 days). A reading that syncs later is counted in a data-quality measure, never added to a past snapshot (snapshots are append-only).
3. **Which readings count**: readings the platform has cleared, plus readings flagged only for a missing arm or position (the value is not in doubt, and many home readings carry no arm or position). A reading flagged as a duplicate or a sudden change waits for a clinician and is not counted (OQ-232). **Controlled** means the 7-day average is under the patient's own target, else under 140/90 (PROPOSED default), with at least 3 readings (PROPOSED). Fewer readings is `insufficient_data`: not controlled and not uncontrolled, shown separately, never dropped. The target actually used and where it came from are stored.
4. **Adherence is stored beside BP, never inside it** (22.2): S08's weekly adherence as of the window end, with its dose count and `medicine_config` version.
5. **The 90-day BP control report is strict first.** Headline: controlled at day 90 divided by EVERY person whose day-90 snapshot is due, so a person who stopped logging counts as not controlled (the HEARTS rule; survivor-only rates flatter a programme). Second figure: among those measured. Third: among those whose baseline was uncontrolled. Missing share is always printed next to a rate.
6. **Small numbers are never shown** (research: 11 is the usual rule, 20 for two-attribute cuts): a cohort under the minimum shows only that it is under the minimum; if any category count is 1 to 10 the whole cohort's counts and rates are withheld (so subtraction cannot reveal it); months under the minimum are left out. PROPOSED, CMO owned.
7. **Test accounts never appear in a view or a report** (INV-13, safety case 22): every analytics view and the report filter `is_test` themselves, and the proof removes the filter to show the check can fail.
8. **No individual is ever listed.** The report is aggregate only; patients read their own snapshots through RLS; staff get no row-level read (no new INV-10 surface).
9. **Risk scoring (22.3) and the personal monthly report (22.5)** are Release 4 in the spec and are not built (OQ-231). `risk_scores`, `risk-model` and the accuracy dashboard (22.4) wait.

## 3. Data model (one migration, real timestamp, `list_migrations` checked live)
- `outcome_config` (versioned, one active row; PROPOSED values mirrored as `outcomes.snapshot_rules` in the registry, drift test): snapshot days, window days, grace days, minimum readings, default target, adherence-as-of rule, minimum cell sizes, report spec code.
- `outcome_snapshots` per spec 4.10 plus: `organisation_id`, `anchor_date`, `window_start`, `window_end`, `bp_readings_7d`, `bp_status` (`controlled`, `uncontrolled`, `insufficient_data`), `target_sys/dia`, `target_source`, `adherence_doses_due`, `config_version`, `is_test`. Unique `(patient, pathway, day)`, append-only trigger, RLS (patient reads own, nobody writes directly).
- `analytics_subjects` (private): a random pseudonym per patient. The de-identified views expose the pseudonym, never the patient id.
- Views in `analytics`: `v_outcome_snapshots` (pseudonymised rows, service role only, no test rows) and `v_bp_control_90d_by_month` (aggregates with suppression). Nobody but the service role can read the schema.
- A new `outcome_measure_specs` row `bp_control_90d`.

## 4. Functions
- `private.compute_outcome_snapshots(now)`: for each joined patient and each due day without a snapshot, compute and insert; idempotent; bounded per run; daily cron; emits `outcome.snapshot_computed` (ids only).
- `public.bp_control_report(from, to)`: admin or the active CMO; aggregate JSON (cohorts, rates, suppression flags, data-quality block, definition text and limitations, no causal claim); the access is written to `audit_log`.

## 5. Screens
`/admin/outcomes` in `apps/web` (the console cannot serve it yet; S36 moves staff areas): the report with the strict rate first, the missing share beside every rate, and the limits printed under it. Nav and search entry. English only (staff pages, OQ-102 precedent).

## 6. Safety rules
1. A test account never reaches a view or report (INV-13); proved with a sabotage.
2. Missing data is never counted as controlled; a person with no day-90 readings stays in the denominator.
3. Small cells are withheld, and complementary cells with them.
4. The report states what it is not: no causal claim, no ranking of clinicians, not for denying care.
5. Snapshots are append-only and carry the config version they used (INV-16).
