# S10x Design: event bus operations

Builds on S10 (bus and outbox, live). Decision D5 (`docs/plans/S06-S10-cmo-decisions-2026-10-07.md`): stay in-house, no hosted queue or webhook vendor, revisit after the DPO review. Plan: `docs/plans/S06-S10-competitor-gap-and-build-plan.md` section 3.5 and the S10x entry. Invariants touched: INV-05 (an urgent event must not wait), INV-10 (events carry ids only), INV-13 (`is_test`), INV-16 (versions).

## What is live (re-read 2026-10-13)
- 65 event types, 17 events, 0 deliveries so far (the processor has not been running). 7 active subscribers: `triage.grade_observation` (observation.recorded), `queue.create_from_triage` and `paging.on_red` (triage.graded), `lead.on_order_paid` (order.paid), `lead.on_suspended`, `lead.on_reinstated`, `lead.on_competency_changed`.
- Handlers registered in `supabase/functions/process-events/handlers.ts`: `bus.noop`, triage, queue, two lead handlers, paging. Every one is thin: the database function decides, the handler passes ids.
- Partner webhooks: `partner_webhook_endpoints`, `integration_outbound_events` (claim with `SKIP LOCKED`, backoff 30 s doubling to 1 h, dead letter), drained by `integration-outbound-drain` every minute. Live: 0 endpoints, 0 events.
- `event_bus_config` version 1 active, with S10's `event_bus_health()` and audited `replay_event_delivery` / `requeue_dead_event_deliveries`.

## What S10x adds

### a. See it and trust it (migration `s10x_a_bus_operations`)
- **Attempts.** `domain_event_delivery_attempts` (one row per try: done, retry or dead, with the error and the attempt number), written by `complete_event_delivery` and `fail_event_delivery`. A stale-token call writes nothing. Pruned after 30 days by the lag sweep.
- **Explorer.** `event_bus_explorer(status, subscriber, event_type, limit, before)`, `event_bus_delivery_attempts(delivery)` and `event_bus_subscriber_status()` are admin-only (`private.is_admin()`, 42501 otherwise). The payload comes back as ids only: `private.event_payload_ids` keeps keys ending `_id` or `_ids` and drops the neutral facts (grade, days). `patient_id` is not returned. Page `/admin/ops/event-bus`: subscriber heartbeat table (waiting, dead, done in 24 h, oldest waiting, last success, last failure, open lag incident), filter, delivery list with lag and error, attempts for one delivery, and **Replay** through the existing audited `replay_event_delivery` (a running delivery answers 55P03 and the page says so). It is in the admin menu and the global admin search (a test fails if it drops out).
- **Health tile.** `EventBusTile` on the operations board (`/admin/ops`, admin account only, because the reads are admin-only) and on the founder's go-live dashboard (`/admin/go-live`). It says dead, lagging and waiting in words, and says so when its own read fails.
- **Lag alert.** `event_bus_lag_sweep()` (cron every 2 minutes, plain SQL so it still fires when the processor is down). For each subscriber, the oldest due and unclaimed non-urgent delivery (pending past `next_attempt_at`, or an expired lease) older than `lag_alert_seconds` opens ONE `ops_incidents` row (technical, sev3, `external_reference = event_bus_lag:<subscriber>`), none while one is open, a new one after it is resolved. A delivery waiting in backoff is not lag. Urgent events are the dead-urgent incident's job. Test events are ignored unless asked (`p_include_test`). An urgent delivery waiting counts after a tenth of the limit (at least 30 s). The summary names the subscriber and counts, never a payload. An advisory lock stops two sweeps racing into a duplicate.
- **Config (PROPOSED, versioned).** `event_bus_config` version 2 adds `lag_alert_seconds` = 600 with a database floor of 120; mirrored as `events.bus_rules` version 2 in `packages/shared/src/proposed-config` with a test that fails if the migration and the registry drift.
- **Contention test.** `packages/db/tests/s10x_bus_contention.sh` (registered in `ci.manifest`, run by the "Supabase migration replay" job against the local stack): two real sessions, A holds a claim open for 3 s, B claims 1 s later. Proves B finishes while A is still open and takes only the rest (`SKIP LOCKED`), nothing handed to both, and, for an ordered type, exactly the chain heads in flight. Its control runs a picker with no `SKIP LOCKED` and must block, or the script fails as vacuous.

### b. Ordering and partners (migration `s10x_b_partner_webhook_subscriber`)
- **Ordering key, opt-in.** `event_types.ordered` (default false; nothing is opted in by this change). For an ordered type, a delivery is not claimed while an earlier one (by `occurred_at`, `created_at`, `id`) for the same subscriber, patient and aggregate is pending or processing. Safe under concurrency: a concurrent claimer sees the earlier row pending or locked, never free. **A dead earlier delivery does not block**: freezing a patient's chain silently is worse than a gap, and a dead delivery is already counted, visible and (if urgent) an incident. A replayed dead delivery therefore runs out of order, by design. Cost: one `NOT EXISTS` per ordered candidate; throughput for that type drops to one in flight per chain. Which types to opt in (candidates: `observation.recorded`, `triage.graded`) is a clinical decision, left open.
- **`partner.webhook` subscriber.** `partner_event_map` (bus event type to partner-facing `integration_event_type`) is data and is empty. `set_partner_event_mapping` (admin, audited) writes a mapping and creates `partner.webhook.<type>` in `event_subscribers`. The handler calls `partner_webhook_enqueue_for_delivery`, which builds an ids-only envelope (`bus_event_id`, `bus_event_type`, `event_version`, `aggregate_type`, `aggregate_id`, `occurred_at`, `ids`) and calls the existing `enqueue_integration_event` with dedupe key `bus:<event id>`. No patient id, no name, no reading, no result: a partner that needs more reads it through the partner API and its consent checks. A test event goes to sandbox endpoints only. A removed mapping sends nothing. The row is inserted directly, not through `enqueue_integration_event`, so an event emitted while an endpoint is auto-switched-off is queued and waits (the claim skips it) instead of being lost, and replaying the bus delivery puts a dead-lettered or cancelled partner row back in the queue (a delivered one is not sent twice).
- **Signing.** The drainer keeps the original `X-Tarragon-Signature` and adds `X-Tarragon-Timestamp` and `X-Tarragon-Signature-V2: t=<unix>,v1=<hmac>` over `<t>.<body>` (shared code in `_shared/integrations/webhook-signature.ts`, with a reference `verifyV2`). Receivers should reject a timestamp more than 5 minutes old.
- **Key rotation.** `rotate_partner_webhook_secret(endpoint, grace_hours = 24)` (integrations.manage, same organisation) returns the new secret once, keeps the old one for the grace window (1 to 168 h), and the drainer then adds a second `v1=` signed with the old key. The audit row records the key version and grace period, never a secret. The grace window covers the V2 header only: the legacy `X-Tarragon-Signature` is always signed with the current secret, so a receiver that wants a rotation without a cutover must verify V2. A second rotation inside an open window is refused (55000), so a leaked key cannot be replaced until the window ends or is shortened by hand.
- **Auto-disable.** After `partner_disable_after_failures` (PROPOSED 20, database floor 5) consecutive failed attempts, `record_integration_delivery_result` sets the endpoint inactive with a reason and opens ONE incident (`partner_webhook:<endpoint>`, none while open) and an audit row. `claim_integration_outbound_batch` no longer claims inactive endpoints (this also applies to endpoints an admin switches off by hand, which previously kept receiving queued events). `reenable_partner_webhook_endpoint` resets it. Queued events wait.

## Deployment order (merging auto-applies the migrations)
1. Both migrations are additive and the old functions keep working against them (the claim gains two columns the old drainer ignores).
2. **Redeploy `process-events`** (adds the `partner.webhook` handler) and **`integration-outbound-drain`** (new headers, previous secret). Neither is deployed by this change. Until `process-events` is deployed, do not create a partner mapping, or its deliveries go to the dead letter as "no handler registered" (visible, replayable).
3. The lag alert starts working as soon as the migration applies; if `process-events` has never run, expect lag incidents for each subscriber that has a backlog, which is correct.

## Known limits (from the code review)
- Partner ids are an allow-list per mapping (`partner_event_map.id_keys`, chosen by the admin, never a person id); `aggregate_id` is sent only when the mapping lists it. Mapping a clinical event type to an external party still needs the DPO and CMO view of consent first; nothing is mapped.
- `enqueue_integration_event` (the older direct path) still skips endpoints that are inactive, so an event raised on that path while an endpoint is switched off is not queued. Only the bus path queues for auto-disabled endpoints. The direct path has no live caller.
- Endpoints switched off by hand now stop being claimed (before, queued rows were still sent); their backlog waits and is not in any lag measure.
- Ordering is by `occurred_at`, `created_at`, then emission order, not commit order: two concurrent transactions can commit out of order, so ordering is best effort under that race.
- The lag and auto-disable incident inserts log a warning and carry on if they fail, so one bad insert cannot stop other alerts or lose a delivery result.
- Lag incidents take the organisation of the oldest waiting delivery (subscribers are shared across organisations). A replay restarts attempt numbers at 1 while keeping the earlier history. Auto-disabled endpoints keep queueing bus events with no prune. The attempts and chain indexes assume modest volume; revisit at scale.
- Rotation refuses a second rotation while the previous grace window is open; the expired previous secret is not cleared automatically.

## Not built, on purpose
- No UI for endpoint rotation, re-enable or mapping yet; they are callable functions (admin and integrations.manage).
- No payload search and no PHI view in the explorer.
- No hosted queue (D5).

## Design note only: a FHIR Subscription facade over the bus (no code)
Goal: let a FHIR client subscribe to platform events in the standard way, over the same bus and the same partner path, adding no second delivery system.
- **Shape.** FHIR R5 Subscriptions (with the R4B backport) are topic based. A `SubscriptionTopic` resource is a published view of one `event_types` row (canonical URL `…/SubscriptionTopic/<event_type>`, resource trigger = the aggregate type, `canFilterBy` limited to ids the event already carries). Only event types with a partner mapping are published as topics, so the list a client sees is exactly the list a person approved.
- **Subscription resource.** A client `POST`s a `Subscription` (`channel-type` rest-hook, endpoint URL, payload content `id-only`, heartbeat period). The facade stores it as a `partner_webhook_endpoints` row plus a `partner_event_map` row, owned by the authenticated partner integration (`api_keys`), `requested` until the handshake succeeds, then `active`. `off`, `error` and `entered-in-error` map to `is_active`, the auto-disable state, and delete. Rotation of the shared secret is the existing rotation; the facade never returns the secret after creation.
- **Notifications.** A `Bundle` of type `subscription-notification` with a `SubscriptionStatus` (event number, type `event-notification`, topic) and `focus` as a bare reference to the resource (`LabResult/<id>`), which is exactly the ids-only envelope. The client reads the resource through `GET /api/v1/fhir/*`, whose consent and category-scoped access checks apply. `id-only` is the only payload mode ever offered; `full-resource` is never offered because it would put a record in an outbound message.
- **Protocol parts.** Handshake (a `handshake` notification must be acknowledged before `active`), heartbeat (a timer on the endpoint, answered by the existing success and failure counters), `$status` and `$events` operations (served from `integration_outbound_events` and the attempts table, so a client can recover missed events by event number, which needs a per-subscription sequence added to the outbound row).
- **Why not now.** It depends on a real partner asking for it and on counsel's view of the consent basis (D9). The bus work above is its prerequisite and is complete without it.
