# S36e Design: reliability and SLA dashboard

Spec 9.5 (reliability and SLA dashboard for the clinical lead), 9.4 (ops view of queue health). Depends on S16 (clinical tasks), S17 (queue, reliability), S18 (rota, cover), S19 (red-event pages). Invariants: INV-10 (no patient reference is read), INV-13 (`is_test` excluded), INV-05 (a page needs a reachable person, so unacknowledged pages and no-cover pages are shown first-class).

## What it shows
Tasks waiting by priority class with the oldest wait and how many are past their due time; red-event pages in the 90-day reliability window acknowledged within the configured first escalation time, acknowledged at all, median and slowest-tenth time to acknowledge, pages with nobody on call, and every page still unacknowledged (time waiting and ladder level only); on-call cover now and the gaps in the next 7 days; hand-back rate over the same window; reliability as three bands. The CMO door also shows who is on call and each clinician by name, ordered by name, never by score.

## Two doors (S37 pattern)
`/clinician/reliability` (CMO, `canAssignCases`) and `/admin/ops/reliability` (`ops.console.view`; admin holds it). One component, `viewer` decides only what is drawn; the database function decides what is returned, so the ops answer carries no names, no scores tied to anyone, no patient ids (proved).

## Data
One function, `public.reliability_dashboard(p_gap_days, p_min_group)` (no table, no column). Reads `clinical_tasks`, `pages`, `paging_config`, `on_call_rota` via `private.rota_gaps`, `clinician_reliability_events`, `clinical_staff.reliability_score`. Display numbers (7 days, minimum group 5, bands) are in `reliability.dashboard` in the proposed-config registry. A failed read is a load failure on screen, never zeros. See OQ-225 to OQ-229.
