# S06z design note: data cost in naira, and sync on Wi-Fi only

Extends the S06x data-use meter (`docs/design/S06x.md` section 5). Reconciled against `origin/main-dev` on 2026-10-20. No migration, no new native module, `runtimeVersion` untouched, no AI.

## 1. What existed, what was missing (verified, not assumed)

| Piece | State on `main-dev` | S06z |
|---|---|---|
| Data meter | `data-usage.ts` counted every byte the sync code sent or read, in one monthly total, shown in the sync banner only while something was waiting, in MB | Kept. Now also split by connection, and priced. |
| Connection type | NetInfo used only for "connected or not" (`reachability.ts`) | `connection-kind.ts` reads the type (Wi-Fi, mobile data, other, unknown, none). |
| Low-data mode | A Settings toggle that thins the background READ (`offline-budget.ts`) | Unchanged. Wi-Fi only is a second, separate choice, and the explanation points at both. |
| Cost in naira | none | Built, from PROPOSED config. |
| Wi-Fi only | none | Built for ordinary readings, dose logs and the history read. |

The meter before this change would have shown a patient on Wi-Fi at home "data used" and no price, so it could not honestly claim anything about mobile data. That is the first thing fixed: bytes are attributed to the connection they went over.

## 2. The estimate (honest by construction)

- `offline.data_cost` (`packages/shared/src/proposed-config/registry.ts`, owner Founder, PROPOSED): `price_per_mb_kobo` = 80 (N0.80 a MB, about N800 a GB) and `max_hold_hours` = 6. The founder must confirm the price against current Nigerian prepaid bundle rates (OQ-S06z-1). A guard pattern fails the repo scan if either number is typed into application code.
- `estimateCostKobo(bytes, price)`: exact integer arithmetic (BigInt), whole kobo, half rounds up, 1 MB = 1,000,000 bytes (the unit the meter already shows). Zero, negative, NaN and infinite give 0; a result beyond the safe integer range is capped.
- `formatNaira(kobo)`: kobo in, naira out, never floating point.
- What counts: bytes sent while the phone is on mobile data. Wi-Fi and "no connection" cost nothing on a plan and are left out of the figure. **Bytes the phone could not place** (NetInfo missing or silent, an older binary, Jest) are counted INTO the figure, so the estimate leans high rather than low, and are reported on their own line so they are never hidden.
- "Last sync" is a run of uses less than 60 seconds apart (a flush sends many rows, a pull reads many pages); `addDataUsage` needed no caller changes.
- Every figure sits beside a note that it is an estimate, the price used, and that the phone's own data screen is exact. A phone with nothing counted says so in words ("Nothing used on mobile data this month so far") rather than showing a measured-looking N0.
- The count is the app's own sync traffic. It is not the whole app (calls, photo uploads, web content in the browser, background fetches by other libraries). The note says "syncing".

## 3. Sync on Wi-Fi only

A per-phone switch (`wifi-only.ts`, AsyncStorage; only a literal "true" turns it on; any unreadable value means off, which means send).

**What can be held** (`data-cost-rules.ts`, exhaustive `Record<OutboxKind, boolean>` so a new outbox kind fails to compile until classified):

| Entry | Held on mobile data? |
|---|---|
| `dose` log | yes, with the deadline below |
| `vital` of type weight (no red-flag rule on the server) | yes |
| any other `vital` (blood pressure, glucose, pulse, temperature, oxygen), flagged or not | never. The phone's danger flag is only as good as its classifier: a pulse logged with a blood pressure is never flagged, and a classifier error leaves a reading unflagged, so "not flagged" cannot be read as "ordinary". An unknown vital type is also urgent. |
| anything the phone classed danger or emergency (`danger`), of any kind | never |
| `symptom`, `red_care`, `kick_session`, `contraction_session` | never (a symptom may be urgent in words the phone cannot score; a red-alert answer, and kick and contraction logs, are safety signals) |
| BLE device reading queue, Apple Health / Health Connect sample queue, written questions | never touched: they can carry a value the phone cannot classify, and the server's red-flag engine reads them |

**When an entry is held:** Wi-Fi only is on AND the phone is KNOWN to be on mobile data (`unknown` and `other` send) AND it is not urgent AND the patient has not tapped "Send now on mobile data" AND it is inside its deadline. The deadline is the earlier of (a) `max_hold_hours` (6) after it was logged and (b) for a scheduled dose log, the server's missed window (`serverMissedAfterMinutes`, 12 hours, from the medicines config) after the dose was due, less a one hour slack for a late background flush. (b) is what stops a late dose log (taken 10 hours after it was due) from sitting past the moment the server writes "missed" and raises a false miss for the care team; a scheduled dose whose due time cannot be worked out, or a missing missed window, is never held. An entry stamped in the future or with an unreadable time is never held.

**Wipes.** The "one last upload attempt" before a lost-phone or lapsed-lease wipe uses `flushOutboxIncludingHeld`, so a held row is never destroyed unsent.

**Arriving on Wi-Fi.** The reconnect watcher also fires when the connection type changes to Wi-Fi from mobile data (the phone never stopped being "connected", so the old trigger would not fire), so held rows go at once.

**One rule, two readers.** `wifi-hold.ts` is the single place that decides per row; the flush and the banner's count both use it, so what the banner says is waiting is exactly what the flush leaves. The "Send now" override is a parameter of one run, not a global.

**The history read** (`pullChanges`): the readings, symptoms and dose pages wait for Wi-Fi once the phone has read before. The very first read is never skipped (the patient would see an empty app). Medicines and tasks are small and can change what the patient should do (a stopped medicine), so they are always read.

**Never silent.** The sync banner says "N waiting for Wi-Fi. They send when you are on Wi-Fi, or within 6 hours" with a one-tap "Send now on mobile data" (`flushOutboxIncludingHeld`, for that one flush only). The held rows are durable on the phone exactly as any queued row is; a held row is never dropped, and it never reaches the "stuck" notice (6 hours < 12).

**Never blocks urgent.** A danger-flagged entry is classified urgent before the hold rule looks at anything else, and a test sweeps every kind with `danger` set. Sabotage: removing the `danger` term, flipping `symptom` to ordinary, or treating every vital as holdable each fails tests.

## 4. Screens

- Phone, Settings: a "Mobile data" group (`data-use-section.tsx`): this month and the last sync in MB and naira, the unplaced line when present, the estimate note, a link to the web explanation, the Wi-Fi-only row (a 28 point switch inside a full-width row, so the tap target is the row, 44 points or more), the plain statement of what is never held, and three "Ways to use less data" lines (low-data mode, Wi-Fi only, photos and calls on Wi-Fi).
- Phone, sync banner: the cost line (labelled an estimate) replaces the MB-only line; the Wi-Fi waiting card above.
- Web: the patient Help and support FAQ carries the same explanation, built from the same config price (never typed).
- All strings are in `packages/i18n` under `datacost.*`, English only. A test scans every one for em dashes, fear wording and medicine or condition names.

## 5. Not built, recorded

- The count is the app's own sync use, not the operating system's per-app figure (React Native exposes none). The estimate is labelled.
- Wi-Fi only does not cover the BLE and health-sample queues (see section 3). It does not reduce data used by calls, photos or the web.
- Which connection a byte used is read once per run (one NetInfo read per flush or pull, one meter write per run). A phone that changes network mid-run can be off by a few requests.
- Holding a normal blood pressure (the commonest reading) would need the phone's positive "classified, normal" result stored with the row, which today is not distinguishable from "not classified". It is a follow-up (OQ-S06z-2), so Wi-Fi only today saves most through the history read, not through held writes.
- No device run. NetInfo's type value on real Android and iOS hardware, and the Settings screen's look, were not exercised here.
