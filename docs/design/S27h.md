# S27h Design: lab lifecycle and partner quality

Plan: `docs/research/S26-S30-competitor-review-and-build-plan.md` section S27h. Depends on S27 to S27g, S19, S74. Invariants: INV-03, 04, 07, 10, 12, 13, 14.

## 1. What was already there (verified, reused)
Corrections with supersession (kinds corrected, amended, appended; a reason; one neutral "updated" notice; history kept; replace while held; withdraw), release authority for a critical value (Senior Medical Officer or CMO, OQ-180 closed), disclosure attempts and the CMO incident (3 attempts or 72 hours, never released by default), one neutral "under review" state with an expected time from `escalation_slas`, specimen ids, rejection reasons, the automatic re-collection chain, turnaround alerts and the partner dashboard, the explain gate and its scan test, licence columns and the S74 expiry hard stop.

## 2. Decisions
1. **Nothing in S27h can release a result.** Hold-aging, the critical call, the delta check and the fallback are alerts, clocks and flags. Release stays a clinician act through `release_lab_result` / `record_lab_disclosure`, and the state machine (`private.guard_lab_result`) is not rewritten. Each rule has a test that proves the state is unchanged afterwards, and a sabotage that makes the code release so the test must flip.
2. **Preliminary / final** is a column (`report_status`) plus two small triggers, not a new state. A preliminary result is held and unreleasable on every route; the final is a correction of kind `finalised` against it, which supersedes it through the existing held-supersede path. The one writer, `private.submit_lab_result`, is patched in place from its live definition at apply time (same technique as S27g), because later migrations have already patched it.
3. **Critical call** is its own table (`lab_critical_calls`), opened by a trigger on the first critical item, using the S19 rota, the S19 escalation times (`paging_rule`), the incident helper and the push, in-app and email channels. Not the `pages` table: that is bound to a triage event, and widening it would touch the red-event ladder. A failure to open the call is audited and raises an incident; it never undoes the held result and is never silent.
4. **Hold-aging** is a sweep (`private.sweep_lab_holds`, every 15 minutes) with a side table (`lab_hold_state`) so each step happens once. The patient gets one neutral line after the expected time; the clinical lead is told at a PROPOSED threshold, repeated up to a cap.
5. **Disclosure fallback**: one neutral message after the failed attempts, the CMO escalation and the configured wait, and only once the CMO has signed the wording (`lab_fallback_wording_signoffs`). The words are fixed in code and lint-tested; the signature names a version. Ships unsigned.
6. **Delta** is computed on read for the tied reviewer (`lab_result_review_context`, an audited read). Baseline: the patient's latest released, current, same-unit numeric value inside the window.
7. **Partner onboarding**: a trigger on switch-on (insert active, or inactive to active) requires a licence number, a verified date, a future expiry and an accreditation. The placeholder-contact CHECK is unchanged. A laboratory that is already live is not re-checked.
8. **Patient trend**: `my_lab_trends()` returns two released values and a direction word per coded numeric analyte, plus the care team's note (`lab_trend_notes`, append only, written by a tied clinician, 3 to 300 characters). It returns no range and no flag; a range is shown to a patient only with its source (S05b) and that is the results list's job.

## 3. Not built
Item 7 of the brief (wire `canExplainLabResult` into audio and AI): no audio or AI path reads structured lab results (the scan test in `explain-gate.test.ts` proves it). The first one that does must call the gate. A recorded follow-up.
