## 3. The targets gate (the safety design)

`public.my_nutrition_target_gate()` is the only way a patient receives a number. It returns `{state:'withheld'}`, `{state:'not_active'}` or `{state:'ok', config}` and never says why. The app treats `withheld`, `not_active`, a failed call and anything it does not understand identically: `hidden`, which the screen renders as nothing at all (no empty card, no "not available for you"), so the absence tells nobody anything.

`private.nutrition_targets_withheld(patient)` is true if any of: `profiles.is_pregnant`; `patient_pregnancy.is_pregnant`; `reproductive_health_profiles.life_stage` in (pregnant, postpartum); a `postnatal_profiles` delivery in the last 365 days; an open `nutrition_target_holds` row; a positive `obesity_ed_screens` row; date of birth under 18. It runs with owner rights on the caller's OWN record only (`auth.uid()` inside the public function; there is no patient parameter), is not executable by `authenticated` or `anon`, and adds no caregiver or supporter path. This follows the standing rule about reproductive data: written fresh, not copied from an older sibling table's policy.

Signing: `sign_nutrition_target_config` is Chief Medical Officer only (same shape as `sign_my_health_config`). Config validity (floors of at least 1,000 kcal, minimum age 18) is a database CHECK and is re-checked in code (`parseNutritionTargetConfig`), and the phone refuses to show any energy target under 1,000 kcal even if one were sent. Targets are not cached on the phone: whether they may be shown can change, so offline the answer is "show nothing".

The clinician hold is `set_nutrition_target_hold(patient, hold, reason)`: an active clinician (not a care coordinator) with a tie (`staff_may_write`); the reason is never shown to the patient and the patient has no policy on the table. **There is no clinician screen for it yet** (OQ-S49A-3).

## 4. What is deliberately not done

- No water logging (S47a). No meal planner or shopping list (S50-1). No fasting timers. No overseas barcode database. No weight-loss target anywhere.
- No dietitian review of any food row. No portion photo. No barcode rows.
- The CMO has not signed anything and no go-live guard was touched.

## 5. Order of release

Apply the two migrations FIRST, then deploy the code. The migrations are purely additive (new columns, tables, a view, new enum values, rows), so the code now in production keeps working against them. The reverse order would break meal logging: the new web code writes `client_id`, `source` and `client_recorded_at` on every diary insert, and those columns do not exist until the migration is applied. (Targets themselves would fail safe, hidden, but the diary insert would not.) Nothing was applied by this build; CI does not apply migrations (apply before merging).
