## 2. Data model (migration `20261006183147_s37_go_live_guards.sql`)

- `go_live_guards` (7 rows, spec 14, all off): `key`, `label`, `blocks`, `condition_text`, `switch_role` (`admin` | `cmo`), `enforced_in text[]`, `not_enforced_in`, `is_on`, `changed_at/by`, `change_note`. A trigger refuses any change to `is_on` and its attribution columns unless a `go_live_guard_log` row for the same guard and direction was written **in the same transaction** (`txid`). A bare UPDATE, DELETE, TRUNCATE or INSERT-as-on is refused for every role including the table owner that runs migrations (proved, with a sabotage run). Residual risk: the owner can still forge by inserting a log row first; that leaves a permanent attributed record, and `ALTER TABLE ... DISABLE TRIGGER` is a superuser act no table design can prevent.
- `go_live_guard_log`: append-only (trigger refuses update, delete, truncate): guard, direction, actor, role, note, the conditions as they stood, txid.
- `go_live_attestations`: append-only human assertion for a condition the database cannot see. Latest row per guard and condition counts; a later `met = false` withdraws it. **Nothing is seeded.**
- `proposed_config_signoffs`: append-only; key, version, sha-256 of the value, owner, decision (`confirmed` | `changes_requested`), note, signer. A later edit of the value changes the hash and the old sign-off shows as "changed since". **Nothing is seeded.**
- All four tables: RLS on, no write grant for anyone (the project's default privileges grant `authenticated` insert/update/delete on a new table, so the migration revokes explicitly), no anon access. Guards are readable by every signed-in role (a deployment fact, like `platform_modules`); log, attestations and sign-offs by admin and the CMO.
- Functions (all `revoke ... from public`, `anon` has no execute, verified with `has_function_privilege`): `set_go_live_guard`, `attest_go_live_condition`, `go_live_guard_status`, `record_proposed_config_signoff`, `proposed_config_signoffs_current`, `go_live_guard_is_open` (client check for the signed-in person only), `private.go_live_guard_on` (the one lookup; fail closed: unknown key or off is closed) with `private.go_live_open` (patient and clinician, the test pair rule) and `private.go_live_open_patient` (a request with no clinician yet) built on it, `private.go_live_conditions`. `record_proposed_config_signoff` is callable by the server only (service role, naming the signer whose session the server has just checked; the database re-checks the signer's role); a signed-in browser session, including an admin, cannot call it, so nobody can name an owner or a hash of their choosing.

## 3. The seven guards: conditions, live state, what is wired

Live read-only checks 2026-10-06: appointments 0 rows ever, encounters 0, scribe consents 0, transcripts 0; protocols 0; triage rule sets 2 drafts, 0 approved; 1 active SMO and 1 active CMO (credentialing level 2); 4 pharmacy partners none active; SYNLAB active with manual integration; rota empty.

| `public_signup_enabled` | Stage 2 exit criteria met (attested) | no | none |

Every guard starts off. An unwired guard says so on the dashboard ("Not enforced anywhere yet, so switching it on or off changes nothing today") so nobody believes a feature is protected when it is not. **Scope of "consultation":** any remote clinician appointment (the two consultation types, or any type booked with the telemedicine method), so a `gp` or `follow_up` video visit cannot go around the guard. **A switch-off never ejects a call under way:** a consultation with one person in, or in progress, stays joinable (so a patient who drops can reconnect); only new bookings, new joins to a scheduled consultation and new requests are refused. A guard on whose condition has since lapsed shows a red "drift" notice; it is not switched off automatically (OQ-182).

**Test pair rule (OQ-181):** a booking where the patient and the clinician are both `is_test` passes the guard. `profiles.is_test` is changeable only by an admin or a service context (`guard_is_test_flag`), so a real person cannot become one. It lets test accounts exercise the whole consultation flow in the one production database before launch, and keeps the existing proofs (all test accounts) meaningful.

## 4. Screens

`GoLivePage` is one server component with two doors, as the task-types page is: `/admin/go-live` (the founder is the admin account) and `/clinician/go-live` (the CMO, whose clinician login cannot open `/admin`; gated by `canAssignCases`). **Not in `apps/console`**: `CONSOLE_AREAS` lists only `/ngo`, and `/admin` and `/clinician` are not extracted (S01d), so this follows the same placement as the S16 to S19 staff pages. No cookie `domain` is set. Both pages have a nav entry and an `admin-search.ts` entry with a test. The notice after an action travels in an httpOnly same-site cookie set by the action (`flash.ts`) together with a random id that the redirect repeats as `?n=`; the page shows it only when the two match and then cleans the address, so a link cannot put words in the banner and a reload shows nothing. Switching ON also needs a tick-box (the browser will not submit without it and the action checks it again), so a stray Enter in the note field cannot make a clinical feature live. In every other form the safe button comes first in the page (Enter submits the first button): "Ask for a change" before "Confirm", "Withdraw" before "Record as met".

Each guard card: state, what it blocks, where it is enforced, conditions (met or not, where each comes from), attestation forms for human-recorded conditions, the switch (on only for the named role and only when every condition is met; off for both roles with an optional note), the last five changes. Below: every proposed value with owner, version, current value, status (waiting, confirmed by, changes asked for, changed since confirmed, confirmed in the configuration) and confirm / ask-for-change controls only for the owner's viewer. A confirmation records a decision; it does not change the value in use (a confirmed value still becomes a new version in `registry.ts`, a code change). Staff strings are in `packages/i18n` (en and pcm); guard labels and condition text come from the database in English, like task types.

Patient side (INV-14 client): the booking card shows a calm "Consultations are not open yet" and no times, Book buttons or waiting list while the guard is closed (fails closed on an error); the consultation room shows the same text if a join is refused with `not_live`.

## 5. Safety rules

- Switching on needs: the right role (`switch_role`), a note, and every condition met at that instant, evaluated in the database. There is no other way to turn a guard on (proved: direct update, wrong role, no note, unmet condition all refused). Switching off needs only an admin or the CMO and never waits for paperwork.
- Nothing here touches red events or paging (INV-05) or the offline emergency content (INV-06): those stay outside every guard.
- The guard never reads or writes patient clinical data (INV-10 not engaged). Test data is `is_test` (INV-13). Sign-offs record the value version and hash (INV-16).
- An agent never signs, attests or switches anything: no sign-off, attestation or switch is seeded or performed by this session.
