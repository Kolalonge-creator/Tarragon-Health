# S85-D3: SMS has one named exception

Founder decision (binding, 2026-10-07): SMS is allowed for (1) phone verification codes, (2) clinician paging, and (3) a content-free alert to the patient's own consented emergency contact when the patient triggers an emergency. Exact text: `Tarragon: please call {name} now.` (no condition, result or reading). This reverses part of Part C.2 and D-12, so it needs the founder's explicit approval to merge.

## Design

- **One pure rule** in `supabase/functions/_shared/notifications/delivery.ts`: `smsPurpose()` returns `clinician_page`, `emergency_contact` or `none`; `decide()` refuses `none` (`sms_not_allowed`) and refuses `emergency_contact` while the guard is closed (`sms_exception_off`). An emergency-contact row is never deferred overnight or counted against the daily cap.
- **A refused critical row is marked failed, not suppressed.** `private.escalate_unconfirmed_critical_notifications()` advances (and at the last rung raises the exhausted-ladder alarm to admins) only on a failed row. Suppressing would have ended a patient's ladder with nobody told. A refused routine row is suppressed with the reason on the row and a delivery event.
- **The signed ladder is not edited.** `escalation_slas` v8 still names `sms`; the code refuses it for non-clinicians and the CMO-signed change is OQ-330.
- **The exception waits for a go-live guard**, `sms_emergency_contact_enabled`, in `public.go_live_guards` (S37 pattern). It is data: born off, two attestation-only conditions (`live_sms_delivery_proven`, `founder_approval_d3_recorded`), switched only by `set_go_live_guard`. The sender reads `is_on` with the service role once per run; a read error or a missing row is treated as OFF. The migration replaces `private.go_live_conditions` and `public.attest_go_live_condition` (live bodies read 2026-10-07, repeated plus the new branch).
- **Consent is re-checked at send time**, not only at queue time: the sender re-reads the patient's profile and suppresses the row if consent is gone or `to_phone` no longer equals the number on file.
- **Reachability without SMS.** The sender matches the contact's number to a Tarragon profile (exactly one match, never the patient) and queues push, in-app and (if the account has an email) email rows with the same text, idempotent per source row. A contact who is not a Tarragon account (the usual case: the profile stores only name and phone) is reached only by SMS, so until the guard is on they get nothing. That is OQ-332.
- **Review fixes (code-review high):** the contact is matched only through a confirmed auth phone (ambiguity alerts nobody by push or email and says so on the row); the fan-out outcome is written into the SMS row's `last_error` so a missing alert is never reported as sent; the copies for the contact re-check consent at their own send time; the emergency template is exempt from the digest fold; a failed role lookup leaves SMS rows pending instead of refusing a page on a guess; a unique index backs the idempotency; the patient's button reports "can't text yet" and does not mark the contact notified while the guard is off; the migration aborts if the live go-live functions are not the bodies it repeats.
- **Text lives once**, in `_shared/notifications/emergency-contact.ts`. The template, the fan-out and the tests read it from there. A missing name becomes "them" (the DB trigger's own placeholder is treated as no name).

## Ship order

1. Code first: sender (edge function), screens, mutations. A sender that does not know the guard refuses every emergency-contact SMS, so deploying it opens nothing.
2. Then the migration `20261007214217_s85d3_sms_emergency_contact_guard.sql` (adds the guard row and two replaced functions; nothing else). Not applied by this change. Re-read the live bodies of the two functions right before applying: other branches have migrations live that are not in this tree.
3. Switching the guard on is a later, human act (OQ-332).
