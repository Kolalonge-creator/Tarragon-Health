## 3. Safety rules
- All routing is deterministic SQL from configuration; no model anywhere near it (INV-01). The 12 hour, 3 day, 7 day, 48 hour and every threshold are config, PROPOSED, never signed here.
- EPDS item 10: ANY non-zero answer is a crisis whatever the total and whatever the client sent; the existing emergency path opens the event. Not behind the guard.
- A lifecycle stage changes only through a confirmed event and a configured transition. Wrong-stage, future and over-400-day dates are refused.
- Reproductive-category access: every new reproductive-adjacent table is written fresh: the person; staff through `private.maternal_staff_may_read` (one-function seam for S39b's tied reads; today `is_org_staff`); a caregiver only with an explicit `reproductive_health` category grant AND not for an adolescent. The loss note has no caregiver branch at all. Sponsor, employer, NGO, payer and Care Circle functions and views reference none of these tables (proved by a schema scan).
- Notifications name no reading or condition ("child growth check"); alerts say "not a diagnosis".
- Retention: deletion by who recorded it (B3). Sealed = clinician-recorded, a growth row that raised an alert or a trajectory alert, a baby check linked to an appointment.

## 5. Go-live guard coverage (`maternal_enabled`)
The row exists OFF. It gates: child malnutrition alerts and paging, the feed log insert, `record_lifecycle_event`. It does NOT gate the growth chart, z-scores, EPDS (crisis must never wait on a switch; the new review alerts widen a route that is already live), or the hooks on the existing pregnancy and delivery records. S67 owns the pregnancy BP wiring and the guard's conditions. Nothing was switched on.
