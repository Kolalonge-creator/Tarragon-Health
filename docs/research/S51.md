# S51 research: AI health assistant, conversation, explanations and hand-offs (7.1 to 7.7)

Date: 2026-10-07. Sources: the reference products named in spec B.7 as described in their public product pages and help centres, plus `docs/research/competitor-review-*.md` and `docs/research/S51-S55-review-and-build-plan.md`. Vendor claims are vendor claims; nothing here was run against a competitor's product. The design lens was not verified from screenshots.

## 7.1 Text conversation (voice and local languages are out of scope)
- **Best products:** Lark Health and Wysa keep a short, scripted-feeling turn rhythm, a visible "what I can do" line and quick-reply chips so a low-effort tap replaces typing.
- **Complaints:** long replies, repeated disclaimers, and chatty text that buries the one useful sentence. On shared phones a visible history is also a privacy problem.
- **Unsafe or unsuitable for Nigeria:** voice and Pidgin are deferred or removed by founder decision (D7, D-14); this session builds text only and routes strings through `packages/i18n` (English). Low bandwidth means short replies and no streamed attachments.
- **Premium Tarragon version:** short answers, one chip for the next step (symptom check, medicine education, appointment prep), and the same fixed copy for emergencies on web and mobile.

## 7.2 Built on a model, restricted to reviewed knowledge and the user's own record
- **Best products:** retrieval-grounded assistants show the source under the answer and decline when nothing was found. Microsoft and OpenAI both publish "grounded in your data" patterns with citations.
- **Complaints:** fluent answers that are not in the source, and "reviewed" content that has quietly gone out of date.
- **Unsafe or unsuitable:** a prompt rule alone ("do not answer from general knowledge") is a request, not a control. Content with no owner or a lapsed review date looks authoritative and is not.
- **Premium Tarragon version:** structural, not prompt-only. A row is usable only with an owner clinician, a version and a future review date (read through `assistant_knowledge_sources`). A health-information question with nothing reviewed behind it is refused in code with fixed copy. The API returns `sources`.

## 7.3 Answers about the user's own results, readings and medicines
- **Best products:** K Health and One Medical show the patient's own number with a plain sentence and a "what to ask your clinician" line.
- **Complaints:** a result explained in chat that differs from the explanation on the result card; sensitive results appearing with no clinician in the loop.
- **Unsafe or unsuitable:** explaining a positive HIV, hepatitis B or hepatitis C result (INV-04). The live read path had no filter at all, so this was fixed first (own migration, see design note).
- **Premium Tarragon version:** the chat reads the cached AI-003 explanation where one exists and says the same thing; screening analytes are excluded by a deterministic list in versioned config, enforced in the database (views) and again in code, and the reply is screened.

## 7.4 Explains readings within protocol limits, general medicine information, never dose changes
- **Best products:** Lark and Medisafe state limits ("outside the range your care team set") and stop there; they route a dose question to the prescriber.
- **Complaints:** assistants that say "you could try lowering the dose" when asked sideways ("is it fine to skip tonight").
- **Unsafe or unsuitable:** a model is told not to change doses and then does, in a polite paraphrase. Only code can promise this.
- **Premium Tarragon version:** two deterministic screens. The request screen refuses a change, skip, stop or double before any model call. The reply screen replaces any drafted reply that proposes a dose number, an increase, a stop or a double. Protocol LIMITS come from a function that returns the approved protocol's params and never its step table, so the assistant cannot see a next step to propose.

## 7.5 Food swaps, habit ideas, motivation, one daily nudge, weekly reflection
- **Best products:** Noom and Lark send one calm daily prompt and a short weekly recap.
- **Complaints:** nudges that name the condition on the lock screen (a privacy problem on a shared phone), guilt framing, and several pings a day.
- **Unsafe or unsuitable:** a notification that names a condition, reading or medicine (INV-07); free text from a model in a notification.
- **Premium Tarragon version:** one nudge a day and one recap a week, built from the patient's own data by fixed rules (no model), delivered as a keyed generic notification ("Your check-in for today is ready"). The text is shown only inside the app. The existing AI-002 nudge free text is now linted against the INV-07 term list (closes OQ-94 for that path).

## 7.6 Hand-off to the symptom checker
- **Best products:** Ada and Ubie take new symptoms to a structured question flow and do not let a chat assess them.
- **Complaints:** a chatbot that guesses a cause from two words.
- **Unsafe or unsuitable:** the assistant assessing symptoms itself; Tarragon's own symptom engine is deterministic and signed.
- **Premium Tarragon version:** a `symptom_check` action opens the symptom screen on web and mobile. The model classifies; a deterministic floor sets the same action when the message plainly describes new symptoms. Each hand-off writes an `assistant.handoff` event through the outbox.

## 7.7 Pre-consultation summary
- **Best products:** K Health and Ping An Good Doctor assemble a summary and a question list for the clinician.
- **Complaints:** an AI-written summary dropped into the record without the patient or clinician checking it.
- **Unsafe or unsuitable:** writing AI output into the record without a clinician signature (INV-11).
- **Premium Tarragon version:** deterministic prep with "changes since your last review" and a question list, each line traceable to a row in the patient's own record, plus a draft message the patient can edit and choose to send. The assistant never sends it and never writes it to the record.
