# S10 research: event bus and outbox processor

Reference platforms studied for behaviour only (public docs and published engineering write-ups). Nothing copied.

**Transactional outbox (microservices pattern literature, Debezium outbox docs).** The event row is written in the same transaction as the change, so a change without its event, or an event without its change, cannot exist. Delivery is at least once, so every consumer must tolerate a repeat. Adapted: the event row and the per-subscriber delivery rows are both written in the producer's transaction (by a trigger on the event row), so a subscriber added later never silently misses an event that existed when it was written. Unsuitable: tailing the write-ahead log (needs infrastructure Supabase does not give us); polling with claim is enough at this scale.

**Queue claiming (Postgres `FOR UPDATE SKIP LOCKED` as used by Que, GoodJob, pgmq, Supabase Queues).** Workers claim a batch and skip rows another worker holds, so two workers never take the same row. Adapted: claim sets a lease (`locked_until`) and a lease token; completion only succeeds with the matching token, so a worker that was slow and lost its lease cannot mark a row another worker now owns. An expired lease is claimable again, which is how a crashed worker is recovered. Unsafe for us: holding a database transaction open while a handler runs (handlers call other services); the lease replaces it.

**Retry and dead letter (AWS SQS redrive policy, Stripe webhook retries, Sidekiq).** Exponential backoff with a cap and jitter, a maximum attempt count, then a dead-letter state kept for a person to inspect and requeue. Adapted: values (base, cap, attempts, lease) are PROPOSED and live in a versioned `event_bus_config` row, never in code. A permanent failure (unknown handler, malformed payload) goes to dead at once rather than burning retries. Unsuitable: silently dropping a poison message; a dead delivery stays visible and countable.

**Idempotency and replay (Stripe idempotency keys, Kafka consumer offsets).** The producer supplies an idempotency key and a second write with the same key is a no-op that returns the first event. Handlers get a stable effect key and record each side effect once. Replay re-runs a delivery on purpose; it is safe because effects are keyed. Nigeria-specific: a patient on a weak connection retries writes, so producers will see duplicates routinely. Also, events never carry readings or conditions beyond ids and the neutral fact that something happened (INV-07 spirit); a handler reads the record through the audited path (INV-10).

**Schema evolution (Confluent schema registry, CloudEvents `dataschema`).** Every event carries a type and a version; a subscriber declares the version range it understands; a new version is a new row, not a migration. Adapted: `event_types` and `event_type_versions` are data, so Section 18's "new event types without schema change" is an insert.

**Immediate wake for urgent work (Postgres LISTEN/NOTIFY, Supabase database webhooks).** pg_cron is the guaranteed backstop; a best-effort `pg_net` call right after an urgent event is written removes the wait. The nudge must never fail the producer's transaction, and nothing may depend on it landing (the same posture as the platform's existing critical-notification nudge).
