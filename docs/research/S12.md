# S12 research: wiring triage into the app and server

Sources are the public product pages, help centres and published clinical guidance for the reference platforms named in spec 1A (Omada, WellDoc, Glooko, BeatO, Health2Sync, DarioHealth, Lark, Noom, Oviva, Twin, Propeller, Kaia, Sidekick), read as described publicly, not from their code. Nothing was copied. Where I could not confirm a behaviour from public material I say so.

## 1. Grading a reading the moment it is saved
- Remote blood pressure programmes (Omada, Lark, Glooko-style diabetes apps) publicly describe an instant in-app message after a reading, with a different path for "high" and "very high" readings. A short plain message beats a number table.
- Home blood pressure guidance (AHA, ESH, ISH, all public) says to rest 5 minutes and repeat a high reading before acting on it. Spec 6.2 follows this, so the first elevated reading asks for a repeat and does not alarm.
- Unsafe for Nigeria: a message that says only "call emergency services". Many places have no working emergency line, so the wording is "go to the nearest hospital" and prints no number (PR #785).

## 2. Red readings and emergency guidance offline
- Apps that depend on a server round trip for the "go to hospital" message fail exactly when data is poor. Public descriptions of BeatO and DarioHealth show readings captured through a device and graded in the app; the safe shape is the rule set bundled in the app and graded on the phone first.
- Our choice: the same pure engine runs on the phone from the bundled rule set, with a hard budget so slow local storage can never delay a red result (1 second, INV-06). The server grades again as the authority.
- Unsafe: grading on the phone with a different rule set from the server. A shared fixture set and one source file prevent drift.

## 3. Repeat-reading prompt and the task behind it
- Hypertension programmes publicly describe "measure again in a few minutes" prompts. I found no public description of what they do when the second reading never comes. Spec 6.2 settles it: after 15 minutes the first reading is graded as if repeated.
- Our choice: the phone shows the prompt at once and keeps the pending reading; the server keeps its own pending row and a one minute sweep, so the answer does not depend on the app being open. The Today list carries a task with no clinical wording.
- Unsafe: a repeat prompt that stays on screen all day, or a reminder notification that says why. The task closes itself and the notification text stays generic (INV-07).

## 4. Handing work to the care team
- Care-team tools (Omada, Oviva, Twin) publicly describe coaches and clinicians working from queues, with urgent items surfaced first. Pages for urgent items are described for hospital paging, not for these apps.
- Our choice: S12 does not write queue rows or page anyone. It records the graded result and emits `triage.graded` with the actions; the task queue (S16) and paging (S19) subscribe. Red always carries `page_on_call` (INV-05, enforced by a table check).
- Unsafe: acting on a draft rule set. Until the CMO signs, results are marked shadow and subscribers must ignore them (OQ-88); the live pipeline keeps covering patients.

## 5. Neutral notices and no shaming
- Behaviour-change apps (Noom, Kaia, Sidekick) publicly lean on encouraging, non-judgemental language. Missing a repeat is never framed as a failure: the task simply expires.

## 6. Competitor comparison, S12 scope only (follow-up, 2026-10-05)
Thin evidence: two web searches plus general public knowledge; thresholds and escalation times are mostly private. Directional, not verified. Sources: Livongo HT900 guide (content.teladochealth.com), Teladoc hypertension page, Penn ConnectedBP, PMC8760617 (clinician decisions after elevated-BP notifications), Omron Connect store listing.
- Instant colour grade with a message: common (Livongo, Omron, Withings, Qardio, Hello Heart). We match.
- On-device offline emergency guidance: not publicly documented anywhere. We have it.
- In-app guided repeat with the first reading regraded after 15 minutes: not found. Neutral notifications that never name a condition: not found. Shadow mode until a clinician signs: not found. These look like real differentiators, though absence of public evidence is not proof.
- Urgent hand-off to a clinician: coaching and nurse escalation exist (Omada, Penn, Dozee) but response times are not public; PMC8760617 shows clinicians vary in how they act on notifications.
- Unsafe for us: naming the condition in a push or lock screen text, AI-decided urgency, WhatsApp or SMS-first escalation, US emergency numbers, one cut-off for everyone.
