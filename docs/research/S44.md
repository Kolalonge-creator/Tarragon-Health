# S44 research: interoperability (spec 2.10 to 2.14)

Evidence caveat: public product pages, help centres and standards sites only (searched 2026-10-07). No vendor account, sandbox or store review was read. Treat every competitor statement as "re-verify before a decision".

## 2.10 Records on the FHIR standard (Epic, Oracle Health, InterSystems, Dedalus)
- Large EHR vendors expose FHIR R4 read APIs for Patient, Observation, Condition, MedicationStatement or MedicationRequest, Immunization and DocumentReference. Apple Health Records pulls the same set into a phone.
- Complaints from implementers (background knowledge, secondary): units and codes arrive loosely coded, a Quantity with no unit is common, and a bundle that "validates" can still carry a value in the wrong unit.
- Unsafe or unsuitable for Nigeria: partner systems often send free text and local codes; a hospital export that silently drops reproductive or mental health sections is a privacy risk in the other direction (a person's whole record leaving without scope).
- Standards status: the Nigeria Core IG is a continuous build marked draft version 0.0.0 (published by NDHI); the NPHCDA Immunization IG is a CI build 1.0.0 built on the WHO SMART approach. Neither is a stable, citable release. Sources: build.fhir.org/ig/digitalhealth-gov-ng/Nigeria-Core, build.fhir.org/ig/Nigeria-FHIR-Community/NPHCDA-ImmunizationIG.
- Tarragon decision: export first (the person owns the file), mappings are versioned configuration (`fhir.mapping`), no profile URL is claimed until a stable release names one, units are checked on the way in (the existing import filed a number without reading its unit: a glucose of 126 mg/dL would have been stored as 126 mmol/L), and a round-trip test proves a value and its unit survive.

## 2.11 Nigerian hospital records such as Helium Health (Helium Health, Lifen)
- Helium Health is a widely deployed Nigerian EHR. Whether it offers a documented public API to a third party, on which plan, is not established by anything public I could find. The only search result on the point says to ask the vendor.
- Lifen (France) is a messaging layer that moves documents between facilities: the lesson is that the useful unit is a consented document or summary, not a database sync.
- Tarragon decision: build the adapter seam (interface, a "not configured" Helium adapter that does nothing) and a one-facility pilot plan. Do not promise integration. Inbound records are evidence and a proposal a clinician files, never the record on arrival, and need the person's per-system consent.

## 2.12 Partner lab structured results (Eka Care; Tarragon decision)
- Eka Care ingests lab reports as documents with extraction; labs that send coded results use LOINC and UCUM.
- Risk: a lab's own local codes and units. A wrong mapping is a wrong clinical value, so a mapping is per laboratory, proposed by staff, confirmed by the CMO, and an unmapped item rejects the whole push instead of being guessed.
- Tarragon decision: reuse the S27 writer so release rules (INV-03, INV-04) are unchanged; the lab hears "received" and "released or held", never why; idempotent on the lab's message id; a go-live guard (INV-14) starts off.

## 2.13 Health Connect and HealthKit (Apple Health, Samsung Health)
- Both platforms keep data on the device and gate reads behind an operating-system permission. Consumer wearable values are estimates and the platforms say so.
- Tarragon decision: the OS permission says what the app may read; the platform's own `wearable_device_data` consent says whether TarragonHealth may store it. The route now refuses (fails closed) without it. Wearable observations are tagged as estimates in exports. A real-device test is still a precondition for calling any of it working.

## 2.14 Labels, notes, corrections (CareClinic)
- Symptom and medication trackers let people add a note and a label to an entry and edit their own entries. Complaint: edits that rewrite history without a trace.
- Tarragon decision: notes, labels and a "date I mean" are a private annotation that never changes the item (allowed on device and clinician items too); a locked item is changed only through a correction request that names it; nothing is silently deleted; vitals, medicines and allergies get no patient delete because they feed safety engines (OQ-S44-6).
