# S85 research: end-to-end practice for low-end Android and offline

Public documentation only (Maestro, Playwright, Chrome DevTools, Android emulator and Firebase Test Lab docs).
Nothing copied. Written 2026-10-07. Verify tool versions before relying on a flag.

## Maestro (mobile flows)
- YAML flows driving the real app by visible text or accessibility id. Fast to author, readable by non-engineers, which
  suits a clinical team reviewing a safety flow. This repo already has three flows in `apps/mobile/.maestro/flows`.
- `setAirplaneMode` works on Android only, so offline proofs (INV-06) must run on Android; that matches the phones that
  matter here (Tecno, Infinix, Itel, Samsung A-series).
- Selectors by text are brittle against copy changes and locale. This codebase has no testID convention, so every
  flow targets i18n strings; keep them in step with `packages/i18n` and prefer accessibilityLabel where one exists.
- Maestro Cloud runs real devices but not in Nigeria and not on throttled radios; use it for regression, not for
  proving low-end behaviour. Never point cloud runs at production accounts.
- Unsuitable as is: flows that need an SMS code (no inbox to read); use an email test account on a local or staging stack.

## Playwright (web flows)
- Real browser against a local Supabase stack (as `apps/web/e2e-browser` already does). `context.setOffline(true)` gives a
  genuine offline test for the web form guard. Service-role seeding gives fast fixtures; global setup refuses non-local URLs.
- Serial mode inside one file for journeys, one worker in CI (documented in `playwright.config.ts`).
- Throttling: Chromium only, through a CDP session (`Network.emulateNetworkConditions`) and `Emulation.setCPUThrottlingRate`.
  Firefox and WebKit ignore it. Use it to approximate a slow 3G phone, but treat results as a floor, not a measurement.
- Unsuitable: running journeys against the live project (creates real accounts and rows, breaks metrics even with is_test).

## Throttling profiles for Nigeria
- Chrome's built-in "Slow 4G" and "Fast 3G" presets are tuned for other markets. A Nigerian low-end profile is closer to
  ~400 kbit/s down, 300 to 600 ms round trip, 5 to 15 percent loss, with long dead spells when the user moves. Define it once
  (named constants in a test helper) and keep it versioned like PROPOSED config; do not scatter numbers across specs.
- CPU: 4x to 6x slowdown approximates a 2 GB Cortex-A53 handset. Pair with a small viewport and a 2 GB, API 30 emulator image.
- Also test the failure that matters more than slowness: the radio dropping mid-request. A red reading must show guidance
  from on-device rules with no network at all.

## Android devices and emulators
- A 2 GB RAM, API 30 emulator image with limited storage and the emulator's network speed and latency flags is the cheapest
  stand-in. A real Tecno or Itel handset bought locally is the only honest proof of cold-start time and background-kill
  behaviour (aggressive OEM battery managers kill reminder jobs).
- Firebase Test Lab or similar farms offer a few low-end models but with fast datacentre networks; they prove it installs and runs,
  not that it works on a bad link.
- Unsafe or unsuitable: relying on iOS simulator results for offline claims, or on a flagship emulator for performance.

## Offline-first checks worth automating
- Queue then sync: reading saved with the radio off appears in the outbox, syncs once, and is idempotent on retry.
- Emergency content is bundled: assert guidance text renders with airplane mode on, from a cold launch with cleared state.
- Reminders fire from local notifications without network (already in `medicines-add-remind-take-offline.yaml`).
- Clock skew: a phone with a wrong clock must not mis-grade or mis-order readings; test with a shifted device time.

## What none of this can prove
- Real delivery of push to a dormant low-end phone, the paging chain end to end through the console, and anything touching real
  money. Those stay manual or staging checks with a named owner (see release blockers checklist).
