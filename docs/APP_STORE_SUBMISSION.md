# Apple App Store submission: TarragonHealth iOS app

> First public release: **v0.1.0** (Expo SDK 54, iOS bundle id `com.tarragonhealth.mobile`).
> Prepared 2026-09-18 as part of a combined Android + iOS release-readiness audit — see
> `docs/PLAY_STORE_SUBMISSION.md` for the Android side, which is materially further along.
> This file is the single place the App Store Connect answers are written down so they can be
> re-entered consistently on every future release, mirroring the Play Store doc's structure.

## Where this stands: three real blockers found and fixed, one genuinely open

Before this pass, **no non-simulator iOS build had ever succeeded, and no simulator build had
succeeded since 2026-09-11** — not because of an app-code bug, but because of three separate,
previously-undiagnosed problems in the local build tooling itself. All three were found and fixed
in this pass; the fourth is a real gap only the founder can close.

1. **FIXED — every local `eas build --platform ios` crashed before it could even start compiling.**
   `pnpm-workspace.yaml`'s 2026-09-16 security bump of `@xmldom/xmldom` to `0.9.12` (closing 23 real
   Dependabot alerts — correct and not to be reverted) has an undocumented behavioural regression:
   its `DOMParser.parseFromString` no longer applies the JSDoc-documented default `mimeType` when
   the caller omits it, and throws instead. Every bundled copy of `@expo/plist`
   (`expo-updates`' native-config-sync step, which every iOS build runs) calls it with no second
   argument, so the crash was 100% reproducible, on every single iOS build, regardless of app code.
   Fixed with a `pnpm patch` (`patches/@xmldom__xmldom@0.9.12.patch`) that restores exactly the
   documented default and nothing else — every actual security fix in 0.9.12 is untouched.
2. **FIXED — the project archive (3.8 GB) exceeded EAS's 2.0 GB upload cap.** No `.easignore`
   existed. The largest single contributor was `apps/mobile/ios/build/` (2.3 GB of local Xcode
   build output, which has its own nested `.gitignore` entry but wasn't reliably excluded by
   eas-cli's archiver) plus the root `node_modules/` and this session's own ~51 GB
   `.claude/worktrees/` fleet. Added a root `.easignore` (see that file for the itemised list).
   This affects **both** platforms equally — it would have blocked the next Android build too.
3. **FIXED — `TarragonHealth.entitlements`' `aps-environment` was hardcoded `development`.** This
   project checks in a bare `ios/` project (not regenerated by Continuous Native Generation), so
   whatever static value is in that file is what every build — including an eventual App Store
   archive — ships with. An App Store or ad-hoc distribution certificate requires
   `aps-environment: production`; shipping `development` is a well-documented, common cause of
   Xcode/App Store Connect rejecting the binary during code signing. Changed to `production`.
4. **STILL OPEN, needs the founder — no Apple Developer Program credentials exist.** Confirmed via
   `eas device:list` (`"No Apple teams found for account worldbest"`) and the checked-in Xcode
   project itself (`project.pbxproj` has no `DEVELOPMENT_TEAM` and no `CODE_SIGN_STYLE` at all,
   meaning no team was ever assigned even locally). `eas build:list --platform ios` shows exactly
   one build in this project's entire history: a `development-simulator` build from 2026-09-11,
   which needs no code signing at all. **No ad-hoc, TestFlight, or App Store build has ever been
   attempted with real Apple credentials.** This needs the founder to run `eas credentials -p ios`
   interactively (Apple ID + 2FA, or an App Store Connect API key) — this is genuinely not
   something an agent session can do: it's an interactive-only CLI flow, and entering an Apple ID
   password on the founder's behalf would fall under the credential-entry prohibition regardless.
   **This is the actual, singular blocker to producing a real App Store-distributable build.** It
   also implies: no App Store Connect app record has been created yet (that itself needs an active
   Apple Developer Program membership, $99/year, enrolled under the founder's own Apple ID).

With items 1-3 fixed, a **development-simulator build was kicked off in this pass** (no credentials
needed — simulator builds are unsigned) to produce real screenshots for this doc's Store Listing
section; see that section for the outcome.

## Pre-submission checklist, once Apple credentials exist

1. Founder runs `eas credentials -p ios` interactively from a real terminal (not an agent session):
   sign in with the Apple ID that will own this app, either let EAS generate a distribution
   certificate + provisioning profile, or supply an App Store Connect API key (recommended — avoids
   2FA prompts on every future build).
2. Create the app record in App Store Connect: bundle id `com.tarragonhealth.mobile`, name
   "TarragonHealth", primary category **Medical** (matches the Play Store category choice).
3. Build: `eas build --profile production --platform ios` (uses `pnpm-workspace.yaml`'s pinned
   Node 22.13.0 via `eas.json`'s `build.base.node`, not whatever Node happens to be active locally
   — the xmldom/DOMParser crash above reproduced identically on Node 22.13.0 and 24.18.0, so this
   was never a Node-version issue, only ever the dependency bug).
4. Submit via `eas submit -p ios` (needs `submit.production.ios` filled in `eas.json` — currently
   empty; either pass `--asc-app-id`/App Store Connect API key flags manually the first time, or
   fill those fields once the app record exists) or upload the `.ipa` through Transporter/Xcode
   Organizer manually.

## App Review information

Apple App Review needs a working login to review a patient-facing app gated behind sign-in.

- **Demo account (dedicated, 2026-09-18):** `appreview.demo@tarragon.test` /
  `TarragonReview2026!`. Deliberately **not** one of the shared `*.test@tarragon.test` QA fixtures
  (e.g. `patient.complete.test`) — those are actively used and reset by every concurrent QA/test
  session on this project (see `CLAUDE.md`'s standing note on the shared-worktree fleet), so their
  state and even their password can drift without warning, which is exactly the kind of thing that
  strands a reviewer mid-review. This account exists for App/Play Store review only — don't reuse
  it as a general QA fixture, and don't "fix" its data to match the shared roster's conventions.
  Created via the real signup endpoint (not a direct DB row), fully onboarded (DOB/sex/state/all 3
  current consents — `data_processing` 2026-09-08-v1, `telehealth` 2026-08-12-v2,
  `terms_of_service` 2026-09-02-v1, so it won't hit the re-consent nudge either), role `patient`,
  org `00000000-0000-0000-0000-000000000001`. **Verified working directly against the Supabase
  Auth API** (`POST /auth/v1/token?grant_type=password` returns a real access token) — see the
  note below on why that verification method was necessary.
  It has no clinical history (no vitals/medications/care plan) — a reviewer will see a real,
  functional dashboard rather than a fully populated one. Populating it with sample data was
  deliberately not attempted in this pass: the schema for a "Complete"-tier patient record spans
  dozens of interdependent tables (care plans, medication logs, vitals) with triggers this session
  didn't have full visibility into, and getting that wrong risks a subtly-broken fixture that's
  worse than an honestly-empty one.
- **Resolved — the "email and password don't match" error from the previous pass was chased down
  further, not left as a guess.** Two independent login attempts through the iOS Simulator (this
  account, and separately `patient.complete.test`) had failed that way, even though both accounts'
  credentials were separately confirmed correct via the Auth API. A third attempt, typed the same
  way but with an extra beat between each step (tap, type, zoom-screenshot to confirm the field's
  exact rendered value, then submit), **succeeded** — landing on the real Home dashboard
  (`apps/mobile/store-assets/ios-submission/02-dashboard.png`). Zoomed-in screenshots of both the
  email field and the revealed (eye-icon) password field showed byte-for-byte correct values on
  every attempt, including the two that failed — ruling out corrupted text injection. The
  successful attempt also surfaced an iOS "Save Password?" Keychain prompt immediately after
  signing in, which only appears once iOS's password-autofill system has taken an interest in a
  login form. Best explanation: the first couple of interactions with a freshly-(re)connected
  dev-client's login form race against iOS Keychain/AutoFill (or the JS bundle's own post-connect
  hydration) in the Simulator specifically — not a deterministic app or backend bug, and not
  something a real person typing at human speed on a real device should hit. If App Review ever
  reports a login failure with these credentials, verify the account directly via the Auth API
  (`curl .../auth/v1/token?grant_type=password`, see above) before assuming the credentials
  themselves are wrong, and consider whether it's this same class of first-load race rather than
  anything account-specific.
- **Sign-in with Apple:** not required. The app has no third-party sign-in of any kind (Google,
  Facebook, etc.) — email/password only — so Apple's "must also offer Sign in with Apple" rule
  (guideline 4.8) does not apply. Confirmed by searching the mobile source for any social-auth
  SDK: none present.
- **Review notes to include:** "This is a patient-facing chronic-disease and preventive-care app.
  The demo account above has completed onboarding; it's a fresh account so its own clinical
  history is empty, but every core screen (vitals logging, medications, messaging, bookings) is
  fully functional. Doctor consultations are billed per booking via an external Paystack checkout
  opened in the system browser (`expo-web-browser`'s `openBrowserAsync`, never an embedded
  webview) — this is a real-world clinical service, not a digital good, so it is exempt from
  Apple's in-app purchase requirement under guideline 3.1.1 (physical goods and services)."

## Permissions and usage-description strings already in Info.plist

All confirmed present and worded to explain the specific feature, per Apple's requirement that a
usage string can't be generic boilerplate:

| Key | Present | Wording |
| --- | --- | --- |
| `NSBluetoothAlwaysUsageDescription` | Yes | Pairing a BP cuff/glucometer/scale |
| `NSCameraUsageDescription` | Yes | Photographing a lab result |
| `NSPhotoLibraryUsageDescription` | Yes | Picking an already-photographed lab result |
| `NSFaceIDUsageDescription` | Yes | App Lock |
| `NSHealthShareUsageDescription` | Yes | Reading Apple Health into the record |
| `NSHealthUpdateUsageDescription` | N/A (`false` in the plugin config) — app never writes to Health, read-only |
| `ITSAppUsesNonExemptEncryption` | `false` | Correct: the app only uses standard HTTPS/TLS, no custom encryption requiring an export-compliance filing |

**Known gap, not a submission blocker but a real functional one:** `Info.plist` has no
`UIBackgroundModes` entry at all. `expo-background-task`'s periodic health/offline-queue sync
(`src/lib/background-sync.ts`) therefore has never been able to fire on iOS — its registration
call is defensively wrapped in try/catch (won't crash the app), but the feature is silently
inert. This mirrors the already-documented HealthKit background-delivery gap in `CLAUDE.md`
(the installed `@kingstinct/react-native-healthkit` version never wires its native wake to a JS
callback either). Not fixed in this pass: the correct `UIBackgroundModes`/
`BGTaskSchedulerPermittedIdentifiers` values depend on exactly how `expo-background-task`'s native
module registers its identifier, which — like everything else in this section — has never been
exercised on real hardware; a guess risks being subtly wrong in a way that can't be verified
without a device. Needs the same real-device pass `CLAUDE.md` already calls for on this whole
background-sync/wearables area before it's trusted.
